### 2. Answers to the Four Targeted Questions

#### (1) Do `HexExt`, `SizeLineOf`, and `ChunkedBody` uniquely determine the payload from the bytes?

* **For a fixed `bytes`, `HexExt`, `SizeLineOf`, and `ChunkedBody bytes payload` DO uniquely determine `payload`**:
  * In [`HexExt ds ext n`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L35-L37), every `d ∈ ds` has `(hexVal? d).isSome = true` (hence `d ≠ cr` and `d ≠ lf`), and every `b ∈ ext` has `b ≠ cr ∧ b ≠ lf`. Therefore `ds ++ ext` contains no `cr` or `lf`.
  * Consequently, in [`SizeLineOf n line`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L43-L44) (`line = ds ++ ext ++ [cr, lf]`), `[cr, lf]` is the *first* occurrence of `cr` or `lf` in `line`, so `line` is self-delimiting as a prefix of any byte stream.
  * Within `ds ++ ext`, `ds` is non-empty, consists solely of hex digits, and `ext.head?` is not a hex digit, so `ds` is uniquely determined as `(ds ++ ext).takeWhile (fun b => (hexVal? b).isSome)`, which uniquely fixes `n = hexValue 0 ds`.
  * In [`ChunkedBody bytes payload`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L292-L294), `bytes = pre ++ line₀ ++ trailers` with [`Chunks pre payload`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L274-L280) and `SizeLineOf 0 line₀`. Every chunk in [`Chunks.snoc`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L278-L280) requires `data ≠ []` (so `data.length > 0`). Reading from the left of `bytes`, each size line is uniquely delimited at its first `[cr, lf]` and yields a unique size `m`: if `m > 0`, it cannot be `line₀` (`SizeLineOf 0 line₀`) and must consume the next `m` bytes as `data` plus `[cr, lf]`; if `m = 0`, it cannot be a chunk in `Chunks` (`data ≠ []`) and must be `line₀`. By induction, `pre`, `line₀`, and `payload` are uniquely determined by `bytes`.
* **What DOES break in [`ChunkedBody`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L292-L294) when embedded in [`response_sound`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L670-L672) (`bytes.data.toList = pre ++ hb ++ body ++ extra`)**:
  While `pre` and `line₀` (and hence `payload`) are uniquely determined from the start of `body`, the end of `body` (`trailers` vs `extra`) is **not** uniquely determined by `ChunkedBody body payload`! [`TrailersOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L285-L286) is `∃ fields lines, FieldLines fields lines ∧ trailers = lines.flatten ++ [cr, lf]`. Because [`FieldLineOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L28-L30) allows `f.name` to contain `[cr, lf]`, `trailers` can swallow the `[cr, lf]` that ended the chunked body and absorb bytes from `extra` (if `extra` contains `: ...\r\n\r\n`) as a bogus trailer field.
  Furthermore, [`HexExt`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L35-L37) and [`TrailersOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L285-L286) throw away almost all of the parser's strictness: `HexExt` allows any `ds.length` (not `≤ 16`) and arbitrary non-CRLF garbage in `ext` (not `; name = val`), and `TrailersOf` allows [`forbiddenTrailers`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Chunked.lean#L53-L55) and arbitrarily many trailers.

#### (2) Do `FieldLineOf` and `HeadBytesOf` determine the fields from the bytes?

* **No.** [`FieldLineOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L28-L30) is:
  ```lean
  def FieldLineOf (f : Field) (line : List UInt8) : Prop :=
    ∃ v, line = f.name ++ [58] ++ v ++ [cr, lf] ∧ (∀ b ∈ v, isFieldContent b = true) ∧
      trimWs v = f.value
  ```
  Because there is **no constraint on `f.name`**, `HeadBytesOf http10 code reason fields hb` ([`HeadSound.lean:605-608`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L605-L608)) fails to determine `fields` from `hb` in two distinct ways:
  1. **Ambiguity within a single line (colons in field values)**: The byte `58` (`':'`) satisfies `isFieldContent 58 = true` (`isVChar 58 = true`). For the wire line `line = ascii "Host: localhost:8080\r\n"`, both
     `f₁ = { name := ascii "Host", value := ascii "localhost:8080" }` (with `v = ascii " localhost:8080"`) and
     `f₂ = { name := ascii "Host: localhost", value := ascii "8080" }` (with `v = ascii "8080"`)
     satisfy `FieldLineOf fᵢ line`.
  2. **Ambiguity across multiple lines (`cr` and `lf` in `f.name`)**: Because `f.name` is not even forbidden from containing `cr` or `lf`, two wire lines `line₁ = ascii "Transfer-Encoding: chunked\r\n"` and `line₂ = ascii "Content-Length: 5\r\n"` satisfy `FieldLines [f₁, f₂] [line₁, line₂]`, **and** their concatenation `line₁ ++ line₂` *also* satisfies `FieldLineOf f₁₂ (line₁ ++ line₂)` for the single field `f₁₂ = { name := ascii "Transfer-Encoding: chunked\r\nContent-Length", value := ascii "5" }`, so `FieldLines [f₁₂] [line₁ ++ line₂]` holds for the exact same flattened bytes `hb`!
  Adding `f.name ≠ [] ∧ ∀ b ∈ f.name, isTChar b = true` to [`FieldLineOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L28-L30) would eliminate both ambiguities, since `isTChar 58 = false`, `isTChar cr = false`, and `isTChar lf = false`.

#### (3) Could `response_sound`'s existential be satisfied trivially?

* **Yes, in two ways:**
  1. **When `h.framing = .untilClose`**: [`BodyOf .untilClose body (bodyBytes obs)`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L428) is just `bodyBytes obs = body`. Because `body` and `extra` in `bytes.data.toList = pre ++ hb ++ body ++ extra` are both existentially quantified and `extra` is completely unconstrained, `∃ body extra, post = body ++ extra ∧ BodyOf .untilClose body (bodyBytes obs)` is equivalent to `∃ extra, post = bodyBytes obs ++ extra`. If the parser emitted no body bytes at all (`bodyBytes obs = []`), this existential is trivially satisfied by `body := []` and `extra := post`.
  2. **When `h.interim > 0`**: In [`InterimHeads pre h.interim`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L612-L620), the `fields` of each interim head are existentially quantified. Because `f.name` in `FieldLineOf` is unrestricted, `pre` can absorb arbitrary wire bytes (including `\r\n\r\n` boundaries) whenever `h.interim ≥ 1`.

#### (4) Could "observations" equality (`obsOf`) hide a real difference in events?

* **Yes, for empty `.body` events (and for how `.body` chunks are grouped relative to callers)**:
  [`Event.obs`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Feed.lean#L38-L42) maps `.body ByteArray.empty` to `[]`, and [`obsOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Feed.lean#L47-L48) is `es.toList.flatMap Event.obs`.
  Therefore, `obsOf es₁ = obsOf es₂` cannot distinguish `#[.head h, .done]` from `#[.body .empty, .head h, .body .empty, .done, .body .empty]`. While [`Parser.stepByte`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Response.lean#L130-L151) and [`Parser.feedLoop`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Response.lean#L168-L200) never actually emit `.body .empty`, no theorem states `∀ bytes ∈ es, Event.body bytes ∈ es → 0 < bytes.size`. Every theorem stated via `obsOf` (or `Reach`) would remain true if `feed` emitted empty `.body` events before `.head` or after `.done`/`.error`.

### 3. Ranked Gaps in the Specification and Proofs

1. **No head or status/field-line completeness (acceptance) theorems (`Shape.lean`, `Chunked.lean`, `HeadSound.lean`)**:
   Every theorem about parsing heads ([`head_sound`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L856-L859), [`received_length_declared`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L879-L887), [`response_sound`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L662-L672)) or decoding bodies after a head ([`roundtrip_length`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Shape.lean#L201-L207), [`roundtrip_untilClose`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Shape.lean#L227-L234), [`roundtrip_chunked`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Chunked.lean#L238-L249)) *assumes* as a hypothesis that `(Parser.start config method).feed head` emitted `.head h` or reached `.body ...`. Not a single theorem in the repository proves that [`stepStatusLine`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Lines.lean#L98-L123), [`stepFieldLine`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Lines.lean#L201-L227) (for non-blank lines), [`stepHead`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Head.lean#L83-L103), or [`toResponseHead?`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Fields.lean#L168-L177) ever succeeds on well-formed wire bytes within the `Config` limits. If `stepStatusLine` always returned `.bad` or `toResponseHead?` always returned `none`, all 31 main theorems would still hold vacuously (only [`Parser.feed_encodeChunked`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Chunked.lean#L210-L217), which starts from an assumed `.body (.chunked (.line {}))` state, is non-vacuous).

2. **`Parser.reusable` (`!p.extra`) is never proved to mean `extra = []` on the wire (`Certain.lean`, `ResponseSound.lean`, `Exchange.lean`)**:
   [`Exchange.reusableNow`](file:///tmp/codec-review-snapshot/LeanHttp/Exchange.lean#L562-L564) requires `!ex.machine.hasBufferedInput` so a pooled connection is never reused when leftover bytes followed the response. In the codec, [`Parser.reusable`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Response.lean#L260-L261) checks `!p.extra`, and [`Parser.reusable_feed`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Certain.lean#L108-L109) proves only that *subsequent* `feed` calls after `p` is already `reusable` set `reusable = false`. Neither [`Certain.lean`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Certain.lean) nor [`response_sound`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L662-L672) proves that if a run reaches `p.extra = false` (or `p.reusable = true`), then in `bytes.data.toList = pre ++ hb ++ body ++ extra`, the trailing wire slice `extra` is `[]` (even when extra bytes arrive in the *same* `feed` call that finishes the response).

3. **`response_sound` does not constrain `extra = []` for `.untilClose` framing (`ResponseSound.lean:428, 670-672`)**:
   As shown in Question (3), because `extra` is unconstrained in `response_sound`, for `h.framing = .untilClose` the theorem only proves `bodyBytes obs <+: post` (a prefix) rather than `bodyBytes obs = post` (`extra = []`), directly contradicting its docstring at [`ResponseSound.lean:22`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L22). Fixing [`BodyProgress`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L434-L441) for `.done` to include `(p.extra = false ↔ extra = [])` (or `(framing = .untilClose → extra = [])`) resolves both Gap 2 and Gap 3.

4. **`FieldLineOf` lacks `f.name ≠ [] ∧ ∀ b ∈ f.name, isTChar b = true` (`HeadSound.lean:28-30`)**:
   As shown in Question (2), omitting token constraints on `f.name` means [`FieldLineOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L28-L30) allows `58` (`':'`), `cr`, and `lf` inside `f.name`. Consequently, [`HeadBytesOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L605-L608) does not uniquely determine `fields` from `hb`, [`received_length_declared`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L879-L887) does not rule out `Transfer-Encoding` lines merged into adjacent fields under `FieldLines`, and [`InterimHeads`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L612-L620) and [`TrailersOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L285-L286) (which existentially quantify `fields`) are not self-delimiting across `\r\n\r\n`.

5. **Nothing is proved about `h.response : Std.Http.Response.Head` (`Basic.lean:235`, `Fields.lean:168-177`)**:
   The exchange layer ([`ExchangeAction.deliverHead`](file:///tmp/codec-review-snapshot/LeanHttp/Exchange.lean#L255)) hands `Std.Http.Response.Head` (`h.response`) to the caller, not the codec's own `Head` fields (`h.code`, `h.http10`, `h.reason`, `h.fields`). Neither [`HeadOK`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Body.lean#L63-L70) nor [`head_sound`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L856-L859) records that `toResponseHead? h.code h.http10 h.reason h.fields = some h.response`, nor proves that `h.response.status`, `h.response.version`, and `h.response.headers` faithfully represent `h`. Moreover, [`toResponseHead?`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Fields.lean#L165-L167)'s docstring claims that the line automata rule out `toResponseHead?` returning `none`, which is unproved (and false if `Std.Http.Status.ofCode` rejects status codes in `600..999`, which [`stepHead`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Head.lean#L91) lets through).

6. **Missing keep-alive and framing guarantees for interim (1xx) heads (`Body.lean:69, 883-885`, `HeadSound.lean:612-620`)**:
   [`Head.keepAlive`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Basic.lean#L221-L225) and [`Parser.reusable`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Response.lean#L256-L259) state that *every* head (including interim 1xx heads) allowed the connection to stay open, and [`Fields.lean:20-22`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Fields.lean#L20-L22) states that malformed or contradictory framing fields on 1xx responses are rejected. However, [`reach_keepAlive`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/Body.lean#L883-L885) only proves `keepAliveOf` for the final head, and [`InterimHeads.snoc`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L617-L620) records neither `declared http10 fields ≠ .invalid` nor `(h.keepAlive = true → keepAliveOf http10 fields = true)`.

7. **Strictness mismatch with `vendor/` on status-line validation order (`Head.lean:90-94` vs `vendor/.../Parser.lean:518-557`)**:
   In `vendor/`, [`parseStatusCode`](file:///tmp/codec-review-snapshot/vendor/LeanHttpProto/Http/Protocol/H1/Parser.lean#L518-L530) validates `Status.ofCode` during status-line parsing (before version check and before reading headers), and [`processSendingStartLine`](file:///tmp/codec-review-snapshot/vendor/LeanHttpProto/Http/Protocol/H1.lean#L1595-L1597) enforces `maxStartLineLength`. In [`stepHead`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Head.lean#L90-L94), only `sl.code < 100` is checked after the status line; `toResponseHead?` (which calls `Status.ofCode`) is deferred until [`endOfHead`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Head.lean#L74) (after all headers are read, and skipped entirely on 1xx interim responses).

8. **Soundness predicates drop chunk-extension, trailer, and header limits (`ResponseSound.lean:35-37, 285-286`, `HeadSound.lean:605-608`)**:
   [`HexExt`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L35-L37) omits `ds.length ≤ 16`, `line.length ≤ config.maxChunkLineLength`, and the chunk-extension grammar; [`TrailersOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/ResponseSound.lean#L285-L286) omits `lines.length ≤ config.maxTrailerHeaders` and `∀ f ∈ fields, f.name.map toLower ∉ forbiddenTrailers`; and [`HeadBytesOf`](file:///tmp/codec-review-snapshot/LeanHttp/Codec/Proofs/HeadSound.lean#L605-L608) omits `fields.length ≤ config.maxHeaders` and `(lines.map List.length).sum ≤ config.maxHeaderBytes`.
