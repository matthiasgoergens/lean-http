Fresh-context Claude (Opus) review of the exchange core at a75c6da, 2026-10-28, read-only, asked to refute the guarantees of LeanHttp/Exchange.lean.  Its report as returned (line numbers refer to a75c6da):

I found one real violation in the core (guarantee 5, while draining), one check in the checker that can never fire, and one overclaim in the docstring about guarantee 1. The other guarantees held under every sequence I traced. I did not edit or build anything, so nothing below was run.

1. Draining ignores the read gap, so a deadline that has passed is never acted on (guarantee 5).  Confidence: high from reading the code.
- In expireOne's .draining branch (Exchange.lean:838-840), only deadline and drainBy are acted on. readBy is kept when entering draining (:822) and still counts in nextDeadline (:548).
- Event sequence: config {keepAlive := true, gapMs := 50, drainMs := 50}, GET.
  - t=0: begin, then written <all>. Phase becomes awaitingHead and a read is issued with readBy=50.
  - t=0: wantBody 1000000.
  - t=0: received "HTTP/1.1 200 OK\r\nContent-Length: 5\r\n\r\nhe". The machine is now stalled, so a new read is issued with readBy=50.
  - t=10: abandon. The exchange starts draining with drainBy=60.
  - t=50: tick. It is not stale (due=50), but expire does nothing, nextDeadline stays 50, and no action is emitted.
- Every tick between readBy and drainBy then "changes nothing" while being past the due time. A shell that sleeps until nextDeadline (as drive does, wait = 0) spins until drainBy.
- It happens on every abandon when gapMs < drainMs. With the random generator's settings (gap 50, drain 50) it happens whenever the read was issued before the abandon.
- The read gap ("for one read to return") is also simply not enforced while draining.
- Client.request cannot reach it: keepAlive is false and it never abandons.
- Fix: clear readBy on entering draining, or end the drain (finish with reusable=false) when readBy passes.

2. Checker: "a live exchange has a deadline" can never fire (Check.lean:238-241).  Confidence: high.
- nextDeadline is some (foldl min deadline) for every live state (Exchange.lean:544-549), so it is never none and never greater than deadline.
- Apart from the overall deadline, no property checks that a deadline which has passed gets acted on, or that nextDeadline > now after a step. That is why finding 1 passes props and explore.
- explore reaches it with tickBefore -> abandon -> tickDue.
- Suggested check: after any step, a live exchange must have nextDeadline > m.now.

3. Overclaim: "Bytes that arrive earlier are never parsed: the exchange fails" (docstring :24-26, handler :771-773).  Confidence: high.
- The core issues no read while sending, so a conforming shell never reports received in that phase. Early bytes wait in the kernel buffer and are parsed as the response once the head is written.
- Guarantee 1 in its narrow form (no deliverHead before the head is written) does hold.
- The "unsolicited" test cases only exercise events a real shell cannot produce.
- This matters once connections are reused: a 408 or close sent by the server on an idle connection before the next request goes out gets attributed to that request.

4. A write failure before the response head discards a waiting early response (:799-803).  Confidence: medium as a design gap, low-to-medium that it happens in practice.
- writeFailed with no head calls failNow .peerClosed at once, even though a read is in flight that may already hold an early 413 from a server that answered and then closed or reset.
- In drive, whether the read or the write completion is handled first is a timing race. If the write wins, you get maybeDelivered/peerClosed instead of the 413.
- This contradicts "Early responses are delivered" in the close/reset case. An alternative: stop the upload and arm readBy, as is already done once the head has arrived.

5. Latent: the endHeaders handler doesn't check whether the exchange already ended (:638-659).  Confidence: low, not reachable today.
- After a failNow (interim limit exceeded, 101, body over the limit), a final endHeaders later in the same event batch would set the phase back to .receiving. It would then emit deliverHead and even finish true after the fail.
- It is safe today only because the machine handles at most one interim response per step: processReaderCompleteState (H1.lean:1698-1714) does not carry on into the next head.

6. Other checker blind spots.
- It checks safety only. A core that failed or timed out every valid response would pass props and explore; only the fixed traces would catch it. "Early responses are delivered" and "finish once complete" are not properties.
- It never checks that no read is emitted before the head is written.
- It never checks that finish true happens with no read outstanding. By my tracing that state is unreachable today, because a read in flight while receiving implies the machine is stalled.
- The write and read gap timers are not checked at all.
- The stale-tick check is true by construction, since step returns ex unchanged. It only guards that one line.

7. Shell (Client.drive/request).  I found no hang: a deadline always exists and every live state in the Client has a read or a write pending.
- A pending receive is cancelled on both the finish and fail exits. A read is never emitted in the same batch as an ending action, because schedule runs last and returns once the exchange has ended.
- A write that completes after the end is harmless. The pending write that keeps the socket open is documented.
- The finish-without-head branch (Client.lean:243) is unreachable.
- Minor: Client's Error has no written field, so Failure.written is dropped (:318) despite the core docstring's "Errors say how far the request got".
- I could not check what cancelRecv does to a pending recv? (rather than a selector) or to a receive that has already completed: the native code is not in the toolchain sources.
- Edge case: with gapMs = 0, timers armed by schedule are already due and are only acted on at the next event (one tick later).

What held, by tracing: guarantee 2 (write slices and partial written; the write still in flight after the upload stops); guarantee 3 (every term of reusableNow, and the leftover-byte check after resetForNextMessage); interim responses (one per step, counted, closeBody not emitted for them); 101 (the machine turns keep-alive off and closes the reader; the core fails); HEAD, 204 and 304 (same framing in the machine and in Framing.ofResponse); close-delimited bodies with no credit (settle waits, the caller pulls the final chunk); the machine failing mid-body (the .failed event is always caught via takeEvents, including a failure on feed overflow); pullBodyStalled is cleared by feed and by noMoreInput; guarantee 4 (delivery values match their definitions); guarantee 6 (the exchange only ends through failNow/finishNow, both of which emit an action); the absorb loop terminates.
