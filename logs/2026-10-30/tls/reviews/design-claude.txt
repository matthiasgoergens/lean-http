Fresh-context Claude review of DESIGN.md "## TLS" at ed47c37 (general-purpose subagent, same prompt lenses as design-prompt.txt, with read access to the worktree and the upstream clone).  Its report, as returned:

# Lens 1: break it (most severe first)

1. HIGH: the per-connection mutex can deadlock against Lean's event-loop mutex.  DESIGN.md:113 holds the mutex around every OpenSSL call together with handing ciphertext to the TCP socket.  lean_uv_tcp_send takes event_loop_lock, a recursive mutex that the loop thread holds for the whole of uv_run (event_loop.cpp, event_loop_run_loop): order TLS mutex, then loop.  libuv callbacks resolve promises on the loop thread, and dependents marked sync := true run inline there (object.cpp enqueue_core: LEAN_SYNC_PRIO leads to run_task), so a TLS receive continuation chained with sync := true takes the TLS mutex while holding the loop mutex: the opposite order.  lean_uv_tcp_cancel_recv (tcp.cpp:420-446) drops the read promise inside event_loop_lock; deactivate_promise resolves the task, so sync dependents run inline on the cancelling thread, which per :114 holds the TLS mutex: self-deadlock with a non-recursive mutex.  The shell's style is Task.map (sync := true) on TCP tasks (Body.lean:133,136; Wait.lean:43,45).  Instead: forbid taking the TLS mutex in sync continuations, or better remove the mutex (alternative A).

2. HIGH: the TLS transport hides received bytes from the exchange core, which breaks the reuse rule.  SSL_read returns at most one record; further records stay in the read BIO.  A HEAD/204/304 response followed by stray bytes in a second record: the core finishes reusable, waitReadable sees an empty kernel buffer, the stray bytes are parsed as the next response.  tests/net/evil.py head-stray would hit this over TLS.  A close_notify with the last body record goes unnoticed; SSL_pending misses ciphertext in the read BIO; upstream's tryRecv comment (pr/14066 Connection.lean) names this trap.  Fix: a read returns all plaintext from every buffered complete record up to n; before pooling and in the idle check, BIO_ctrl_pending(rbio) > 0 || SSL_has_pending(ssl) means unclean.  Side benefit: about 1,000 instead of 3,700 driver turns for a 60 MB body.

3. MEDIUM-HIGH: a cancel can race a TCP receive that has already completed (callback ran, continuation queued), losing or reordering ciphertext; cancelRecv is then a no-op.  Fix: after cancelling, await the TCP task and feed its bytes before reuse; better, give the idle check's read no timer at all.

4. MEDIUM: "every Lean toolchain ships the same static OpenSSL 3.6.0" holds only on Linux.  v4.34.1 script/prepare-llvm-linux.sh builds the pinned 3.6.0 from flake.nix and forces -Wl,-Bstatic -lssl -lcrypto; prepare-llvm-macos.sh copies brew --prefix openssl@3 (unpinned); prepare-llvm-mingw.sh copies MSYS2's libssl.a.  Windows has no bundle file: every https call fails with a setup error unless a CA file is given; say so, or enumerate the ROOT store (-lcrypt32 is on Windows' link line).  Better CI: read the version string from each toolchain's libcrypto.a in the matrix.  Nothing in v4.34.1 references OpenSSL (nm: no SSL_/OPENSSL_ symbols used by libleanrt, libleancpp or libLake): the libraries ship ahead of the unmerged PRs, so packaging could change.

5. MEDIUM: OpenSSL's global init.  By default OPENSSL_init_crypto registers OPENSSL_cleanup with atexit; an SSL_free from a finaliser or a late continuation during shutdown then runs after cleanup (NOTES.md already records exit segfaults from late callbacks).  Auto-init loads OPENSSL_CONF or the Nix openssl.cnf; a user's OPENSSL_CONF can load provider modules from the Nix MODULESDIR.  Fix: OPENSSL_init_ssl(OPENSSL_INIT_NO_ATEXIT | OPENSSL_INIT_NO_LOAD_CONFIG, NULL) first.  Trade-off: RHEL crypto-policies not honoured.

6. MEDIUM: trust-store discovery copies Go's paths but not Go's semantics.  Go reads every file in /etc/ssl/certs and /etc/pki/tls/certs; OpenSSL's directory lookup needs c_rehash <hash>.0 links, which Fedora's /etc/pki/tls/certs lacks: a store that exists but holds no anchors, failing as verify not setup.  SSL_CERT_DIR may be colon-separated.  Prefer bundle files.  Smaller: X509_V_FLAG_PARTIAL_CHAIN when caFile is given (curl's default); X509_CHECK_FLAG_NEVER_CHECK_SUBJECT to match Go; strip IPv6 brackets for X509_VERIFY_PARAM_set1_ip_asc, zone ids fail there; a client per request re-parses ~140 PEM certificates: consider a process-wide cache.

7. MEDIUM (process): the Verification section has no TLS plan: test CA; no close_notify for a close-delimited body and after a complete Content-Length body; late session tickets; KeyUpdate with update requested (openssl s_server, interactive K); head-stray over TLS; exit test with TLS connections in every closing state; idle connection closed by the server with and without close_notify; interop with nginx, Go and s_server.

8. LOW-MEDIUM: error classification.  Recognising "closed" from SSL_R_UNEXPECTED_EOF_WHILE_READING via ERR_GET_REASON (a static inline in 3.x err.h, uncheckable by a static assertion) is fragile; the transport knows it fed an end of input.  A handshake cut by the call's deadline should be timeout .deadline.  Retrying closed also retries deterministic resets (SNI blocking), at most twice per hop: acceptable.  Fatal alerts after the handshake become peerClosed and are retried for idempotent methods: acceptable, write it down.

9. LOW: releasing with close_notify: idle connections are let go inside withState under the pool mutex (giveBack/forget); collect the transports and send after unlocking.  The send is fine: Lean ignores SIGPIPE (io.cpp:1668), and a pending write does not delay exit.

10. LOW: hand-declared prototypes.  The check only covers what both declare.  Function-like macros (SSL_set_tlsext_host_name, SSL_CTX_set_min_proto_version, BIO_set_mem_eof_return, set_mode) must be rewritten as *_ctrl calls with named constants.  Deprecated functions get no warning: prefer SSL_CTX_load_verify_file/_dir.  SSL_set_alpn_protos returns 0 on success.  The runtime major-version check is late (static linking fixes the version) but fine as a backstop.  Neither bin/lean nor libleanshared.so contains OpenSSL, so #eval or lean --run reaching tls.c fails unless a shared native library embeds libssl.a (the objects are PIC); document it.

11. LOW: "none of them changes" is not quite true: retryableCause and the cause type; Client.plan; Plan.target (changes every error's target and the record Call.validate checks); Body.lean's types.  The planner's proofs use simp [retryableCause] and should survive; pool and exchange proofs unaffected.

12. Checked, no defect: truncation semantics match RFC 9112 section 9.8; a complete Content-Length or chunked body never meets the end of input (the core finishes on its last byte with no read pending); a truncated close maps to readFailed then peerClosed, which keeps redispatch? working for a server that closes an idle connection without close_notify.  Expect servers that "work with Python requests" to fail here (suppress_ragged_eofs=True); name the cause in the error.

13. Probably not worth it: the idle check's "reads them once".  Tickets come right after the handshake; the extra receive brings the race in 3.  Simpler: anything readable or buffered means unclean.

# Lens 2: alternatives

A. Recommended: run the TLS pump in the shell's driver, not as a separate transport object.  The driver is one logical thread per connection (Live.perform/Live.next, ownership through the pool mutex).  On a .write: SSL_write, drain, send, synchronously.  On a TCP read completing: feed, SSL_read until it wants more (up to n), send any replies, then report .received or re-issue the TCP read without stepping the core, keeping today's order (register first, then check .released, Body.lean:350,450).  Handshake and idle check are short sequential loops in the calling task (upstream's runHandshake shape).  Removes the Lean mutex and its deadlock, the cancelled-flag protocol and the race in 3, the ordering argument, and one continuation per TCP read.  Costs: Live, the idle check and the handshake learn about TLS through a plain-or-TLS sum type.  Keep the C-side mutex only as a cheap guard, or drop it.

B. The whole read loop in C: rejected rightly; lean_uv_tcp_socket_object is private (include/lean/lean_libuv.h exposes nothing); C would chain Lean tasks with manual reference counting.

C. Reusing upstream's session.cpp: the stated reasons are weak (rename the lean_ssl_* symbols; register the class lazily; headers are the same problem), but the conclusion holds: its pending-writes queue is dead weight with memory BIOs; its Lean side (withConnection around a whole recv?/send pump) serialises reads and writes, incompatible with the full-duplex exchange.  Better: shape tls.c after upstream's primitives so it can be replaced once a toolchain ships them, keeping our own trust loading.  Upstream's Linux context uses SSL_CTX_set_default_verify_paths, which points at the Nix store path: worth reporting upstream.

D. The other rejections hold (headers at build time, system OpenSSL, own TLS, blocking threads; system OpenSSL confirmed by the forced -Bstatic).  rustls-ffi holds.  mbedTLS is weaker than it looks: the only option not depending on upstream keeping OpenSSL in the toolchain; record it next to rustls as the fallback.  The thin binding over memory BIOs is right; the Lean/C split is the part to change (A).
