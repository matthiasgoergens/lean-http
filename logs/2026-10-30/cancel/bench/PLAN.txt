Written before the run.

Question: does watching for cancellation (one Selectable.one per call over the client's token, the
checks and the bells) make a call slower when no token is given?
Estimand: the ratio of the median time of a reused GET over loopback (net-client's "summary later
calls" p50, 2000 calls through one client to evil.py's /ok), this branch over main 27a0d86.
Unit: one block = one run of each binary, in random order; 30 blocks.  Server pinned to CPU 100,
clients to CPU 101; load average recorded per run.
Primary analysis: the median of the per-block ratios, with a 95% bootstrap interval (10000
resamples of the blocks).  An effect that would matter: 5% or more.
Nuisance: the shared host's load (handled by the blocks, recorded); code layout (one build of each,
so effects of a few per cent cannot be told from placement; not randomised here).

Added after the first run (first/), before the second: the second run measures cc23d5c and adds a
third variant, the same binary with a token that is never cancelled (cancelon=none), so that the
cost of watching a caller's token is measured too; the primary analysis is the same, per variant
against main.  30 blocks, 2000 calls, CPUs 100 and 101, as before.

Added after the second run (second/), before the third: the third run measures the commit that
fires a call instead of chaining on its signal; same variants and analysis.

Added before the final run: after the runs in third/, fourth/ and ablate/ (each with a README), the
final run measures the final commit with the same three variants and analysis, 40 blocks.
