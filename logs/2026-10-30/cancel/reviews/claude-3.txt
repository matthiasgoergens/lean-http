WHAT HOLDS (briefly)

- Cancel.finish and the bell: fixed.  finish replaces the bell, so the last one is dropped, its continuation runs with `none`, and the cycle is broken whatever the closure captures.  The closure now captures only `c.tokens`: the IR of the same code shows `pap race._lam_0._boxed x_5 x_2`, where x_5 is `proj[0]` of the Cancel (claude-3-probes/out3.txt).  So it would not form a cycle even without finish.  The unit check is valid: holding `P.result?` does not keep the promise alive, since the promise points to its task and not the other way round.  The control cancel-keeps-last-bell shows the check fails without the fix.
- Cancel.race's check after the wait: correct.  Turning `.done` or `.timedOut` into `.cancelled` is safe for every caller.
  - In Connect.round, a won socket stays in the slot and the post-loop code drops it.
  - In the handshake, cancelRecv on a receive that has already ended is harmless.
  - In resolve, the answers are just dropped.
  - In acquire and sleepUntil there is nothing to release.
- Live.next's check after the wait: correct, and the state it leaves is fine.
  - The replaced completion has already been taken out of the inbox and is dropped.
  - `reading`, `writing` and `pulling` keep their numbers, but the core's cancel ends the exchange.  perform's `.fail` then calls cancelRecv (with `pending = true`), which stops a receive that may already have ended (harmless, errors caught) and poisons a TLS session on a connection that is being dropped anyway.
  - Nothing calls Live.next on a terminal exchange, so the watch's later `.cancelled` in that mailbox is never read.
  - As NOTES already says, a write completion lost this way is not counted in `written`.
- Attempt.acquire's `.closed` branch and Connect.resolve's checks: correct.  This closes the window between acquire's check and takeConn, and the one left by the CA loading, before any lookup starts.
- cancelon and cancelfrom, and the scenarios: they discriminate.
  - cancel-follow cancels inside observe at the `.decide`, before discardBody.  So abandon's cancelNow? sees the token: no drain (idle=0 and not 1), and no GET /chain/0 in the evil log, whose format `conn{cid} req{n} GET /chain/1 ` matches the grep.
  - cancel-wait, with `within 0 300` against a back-off of 3670 ms, can fail.
  - cancel-deliver exercises the path between the head and the callback; /ok has a 2-byte body, so the exchange is still live.
  - cancel-cap-waiter is deterministic about who holds the connection.  `start` runs call 0 inline up to takeConn before call 1 starts, and only the cancellation can end call 1's wait before about 1000 ms.  The control shell-cap-uncancellable is caught there.
- Host-name case: I agree it is refuted.  Std/Http/Data/URI/Parser.lean:157-159 lowercases names, and DomainName carries IsLowerCase.

WHERE A VERDICT IS WRONG, OR CLAIMS TOO MUCH

1. [Low-Medium, tests and documentation] The round-one fix that checks ask the tokens has no socket-level check that catches its removal, and the controls log shows it.  In out.txt the control "shell-checks-signal-only" deletes the token loop from `reason?`.  It was run against `net shutdown cancel-cap`, and the result is "26 passed, 0 failed".  So shutdown-cap, added in round two for exactly this defect, passes with the defect planted.  The reason: close's wake resolves the waiter's race on the shutdown thread, but the waiter's own continuation (after `await winner.result!`) is a new task.  It is queued behind the signal's deliver task, which `cancel` queued first, so in practice the signal is usually resolved by the time the waiter checks again.  My round-one estimate that `localClose` was likely was too high: the window is real but narrow.
   DESIGN.md says the real-socket runs come "each with a planted defect that the checks catch (logs/2026-10-30/cancel/controls/)".  For this defect the cited log says the opposite.  The unit check added this round ("a check right after cancel sees it", Tests/Unit.lean cancelChecks) should catch it in most runs.  Even with a signal-only check, the check could still pass, if a worker resolves the signal before the main thread checks, but that is unlikely.  run.sh maps this mutation to `net …` only, so the control never ran the unit tests.  Fix: add `unit` to the mapping for shell-checks-signal-only (run.sh `checks`), rerun, and either record that the unit check catches it or soften the DESIGN sentence.  The same goes for the round-three checks after a wait (Cancel.race, Live.next): they have no control.  They are hard to plant observably, but DESIGN should not imply that they have one.

2. [Low] "Accepted: the token mutex on each body read; not changed (two uncontended locks per read)."  "Uncontended" holds only for one call at a time.  `client.closing` is the same token for every call of a client, so concurrent streaming calls all take its mutex.  This round adds one more acquisition per wait in Live.next, so per socket read in collect/drive as well as per BodyStream.read.  Each hold is short, so this is unlikely to matter, but the reason given for accepting it is not right.  The verdict should say "a mutex shared by all calls of the client, taken a few times per read".

3. [Low] The controls do not cover the new scenarios cancel-steps and cancel-redirect.  shell-abandon-drains was run against `net cancel-body` only, but cancel-follow (pool idle=0 after a redirect cancelled at follow) is the scenario that mutation should break.  Adding cancel-steps to its mapping would show it.

MISSED BY ALL ROUNDS (small)

4. [Low, test tooling] With trace=0, `cancelon` silently does nothing.  `withTraces` returns the config unchanged when trace=0, so the hook is never installed.  cancelOf then gives a token whose delay is 2^62, and `arm` skips it, so the call runs uncancelled and nothing says so.  No scenario combines the two today.  Install the hook regardless of trace=0, or refuse that combination in net-client.

5. [Nit] The race docstring's new line is longer than the file's wrap width, unlike the lines around it ("…would not hear of the cancellation.  The timer is stopped when it loses; tasks that lose keep running,").

VERDICT: NO DEFECTS FOUND in the code of fixes.diff.  The open items are about whether tests can fail and what the documentation claims: item 1 should be fixed before DESIGN's controls sentence stands.
