Review of the cancellation change (lean-http), fresh-context Claude reviewer

Scope: review.diff against the tree snapshot, with Std.Sync.CancellationToken, Std.Async.Select and Std.Async.Basic of v4.34.1 read for the claims about them (CancellationToken.lean and Select.lean are identical in v4.35.0, so the "v4.34.1 and v4.35.0 alike" claim in DESIGN.md holds).  Nothing was built or run; every finding below comes from tracing code.  Line numbers are in the tree.

How the pieces fit, as traced (the basis for the findings):
- Cancel.watch (Cancel.lean:64) runs Selectable.one over every token's selector plus promiseSelector(ended).  A token cancelled already is caught inline by combine.tryFn, so the signal is resolved before watch returns: that claim holds.  A token cancelled later resolves the call's signal only asynchronously: CancellationToken.cancel races the waiter and resolves the per-selector waiterPromise, and combine's IO.bindTask (sync := false) then runs `cont` (signal.resolve) on a worker.  So `Cancel.reason?` can still say `none` for a while after `token.cancel` has returned.
- When the call ends first, finish resolves `ended`; promiseSelector's sync chain wins the waiter, and Selectable.one's finally calls each token's unregisterFn, which drops the finished `.select` entry.  So a shared token holds nothing of ended calls (after an asynchronous hop).  Confirmed against the source: CancellationToken.wait leaves `.normal` entries until cancellation, as NOTES says.
- The mailbox path is sound.  The onCancel closure from Live.begin pushes `.cancelled` and rings the bell; Live.next sets a fresh bell before it looks in the inbox, so nothing is lost; takeCompletion ranks the cancellation first; the core fails; perform's `.fail` cancels the pending receive.  Live.abandon, advance and readAll poll cancelNow? first, and the handshake cancels its receive on a cancellation.  I found no path that pools a connection after its exchange was cancelled, and none that leaves a receive pending.

SURE (traced end to end)

1. [Medium] Client.shutdown can report `localClose`, not `cancelled .shutdown`, for a call waiting at the active cap (and, in a narrower window, for a call between hops).  Client.lean:343-345, 278, 740, 747-750; Cancel.lean:128-130.
   Path: shutdown calls `closing.cancel .shutdown`, which (see above) only schedules the resolution of each call's signal on a worker, then calls `client.close` straight away in the same thread.  close -> withState -> wake (Client.lean:278) resolves `freed` synchronously.  The waiting call is inside `a.cancel.race #[freed.result?] left`, whose `BaseIO.chainTask (sync := true) task fun r => winner.resolve (.done r)` (Cancel.lean:128) runs right there in the shutdown thread, so the race returns `.done` unless the worker has already resolved the signal.  That worker has to wake, take the token mutex and resolve the signal within the few microseconds the shutdown thread takes to reach `wake`; usually it will not.  acquire then recurses (line 750) -> takeConn -> `.closed` -> `notSent .localClose "the client was closed"` (line 740).  No cancellation check lies on this path: Attempt.run's check (line 803) is reached only with a connection in hand.  The planner fails localClose, and the error's cause is `localClose`.  That contradicts shutdown's docstring (Client.lean:337-341: calls in flight "fail with Cause.cancelled .shutdown"), README "Cancelling a call" and DESIGN.md.  The same window exists for the pool-off check (line 794), and for a call that has just finished a hop (redirect or retry) when its loop check (Client.lean:939) runs before the signal has caught up.
   Not tested: the `shutdown` scenario (run.sh:1519) has three calls inside their exchanges and none at a cap.  `cancel-cap` uses a token, not shutdown.
   Fix: before reporting localClose (lines 740, 794), read the client's token synchronously (`client.closing.getCancellationReason`), or better, make `Cancel.reason?` read the tokens' state directly, besides the signal, so that polling checks never depend on the bindTask hop.  Add a shutdown run with maxactive=1 and concurrent=2.

2. [Medium, documentation contradicts code and its own test] The withResponse docstring (Client.lean:1120) says "A body that had arrived in full before the cancellation is unaffected."  It is affected.  A small response arrives with its head, and the core holds the body until the caller asks for it, so the exchange has not ended.  After a cancellation, Live.abandon (Body.lean:410), advance and readAll call cancelNow?, which fails the exchange: a read raises the call's error, and on release the connection is dropped.  The new scenario cancel-return (`/ok`, cancel=100, idle=400) asserts exactly that (pool idle=0), against a control with idle=1.  For `Client.request`, a response that arrived in full just before the cancellation (but before readAll ran) becomes a `cancelled` error.  DESIGN.md and README state it correctly ("once the whole body has been taken").  Fix the docstring, or deliver a body whose parser is complete.

3. [Low-Medium] A long wait at the active cap adds one continuation to the call's signal per wake, and keeps it until the call ends.  Cancel.lean:130; Client.lean:747-750, 278.
   Every Cancel.race calls `c.onCancel`, a chainTask on `signal.result?` that is released only when the signal resolves, which happens when the call is cancelled or ends.  For waits that happen a bounded number of times per call (a handshake read, a stagger step, a back-off sleep) this is bounded.  The cap wait is different: `wake` runs on every giveBack and dropConn for any origin in the client (a global wake-up), and each one makes the waiting call re-race.  Each re-race adds a closure that holds a promise to the signal, along with a fresh libuv timer, which is stopped.  A call waiting minutes for a busy origin (deadlineMs defaults to 5 min) on a client with heavy traffic to other origins accumulates one closure per connection returned anywhere.  awaitFirst, which this replaced, chained only on `freed`, which is replaced at each wake, so this growth is new.  Fix: race once across the whole cap wait, or give Cancel a small mutable registry (an IO.Ref holding the current waiter) that each race replaces or clears, instead of a chainTask per wait.

4. [Low] A name lookup can be started after the call is already cancelled, and then abandoned at once.  Connect.lean:244; Client.lean:672-674.
   `resolve` does `start (DNS.getAddrInfo host "0")` before `cancel.race`, and only the race checks `reason?`.  Attempt.connect guards the deadline before a lookup ("an abandoned one can delay exit"), but not a cancellation.  It is reachable when the cancellation lands after the loop's check and before connect: during a slow `Config.observe` callback, during the idle check, after a cap race that returned `.done`, and on the re-dispatch path (`again`, which runs a.run false -> acquire -> connect on a pooled origin this call never looked up).  The lookup is then abandoned at once, with the exit delay and crash risk NOTES documents.  Fix: check `cancel.reason?` in `resolve` (or at the top of Attempt.connect) before starting the lookup.

5. [Low, documentation] Claims about reads after a cancellation are slightly too strong.
   - "a read in progress, and every later read, raise the call's error" (README, DESIGN, Client.lean:1116-1119): `BodyStream.read` takes from `pending` without polling the cancellation (Body.lean:613, `| _, _, _ => pure state`), so a read after the cancellation can still return bytes already held (the rest of a piece cut by a small `max`).  Only the next read that has to drive the exchange raises.
   - "before `k` is entered, the call fails" (Client.lean:1117): nothing checks the cancellation between the planner's `.deliver` and entering `k` (Client.lean:994-1003).  A cancellation that arrives after the final head and before `k` runs enters `k`, and its first read raises.  The behaviour is fine; the sentence is not quite true.
   - Cancel.onCancel "in the thread that cancels it" (Cancel.lean:89): the callback runs in the worker that runs Selectable.combine's deliver, not in the thread that called `token.cancel` (except when the token was already cancelled when the watch started).

6. [Low] "A call of the producer still running is left to finish, and what it returns is dropped" (Client.lean, withUpload/request docstrings; README; DESIGN) holds only for a producer that has reached its first `await`.  Live.perform starts the producer with `start live.produce` (Body.lean:232), which runs it inline in the shell's task up to its first wait.  A producer doing blocking IO, or computing a chunk synchronously, holds up the shell, and with it the processing of the cancellation (and the deadline), until it yields.  The test producer (Tests/Net.lean:428-437) yields through `Std.Async.sleep`, so cancel-upload cannot see this.  Document it, or run the producer with `async` / on a dedicated task.

7. [Low] Theorem docstrings say slightly more than the statements.
   - step_cancel (Exchange/Proofs.lean:3467): the prose describes a dichotomy by phase ("it fails ...; or, while an abandoned body is being drained, it finishes").  The statement proves `fails ∨ (draining ∧ finishes false)`: it does not exclude a failure while draining, nor show that a drain finishes.  Both outcomes are non-reusable, so the property that matters holds; the gap is only in the wording.  Otherwise the statement is strong (no Inv hypothesis, exact actions, delivery and written equal to the pre-state's) and not vacuous (`ex.terminal = false` is satisfiable).
   - step_cancel_not_reusable (line 3494): "In every run, once a cancel has been reported, the exchange has ended and its verdict is not reuse."  The theorem is a one-step statement with the hypothesis `ex.phase ≠ .finished true`.  A cancel reported after a reusable finish leaves the verdict at reuse, which is the intended behaviour ("once the exchange ended, cancelling changes nothing"), but not what the docstring says.
   - plan_cancelled and redispatch?_cancelled match their prose exactly (the planner's state is kept and the step is `.fail (.failure f .cause)` whatever was sent; redispatch? gives `none` for any method and replayability).

8. [Low] Test gaps: places where a cancellation can happen with no real-socket test, and checks that are missing.
   - No shutdown with a call at the cap or in back-off (this would have caught finding 1).
   - No cancellation while following a redirect ("before the redirect was followed" appears in no scenario; Unit.lean covers only the retry wait and the first request), and none while an abandoned body is drained (core traces only).  None during the handshake's final write wait, with pooling off, or on a reused pooled connection: cancel-head uses a fresh one.
   - cancel-write (run.sh:1420) has no `pool idle=0` check.  It is the scenario with a request written in part (the 32 MB body), the very case the change promises never to pool; cancel-upload checks it only for a streamed body.
   - No positive control is recorded for the new checker property "a cancel ends the exchange at once" (the planner side has the `retryCancelled` mutation; NOTES' RUNS line is still a placeholder).  The property can fail in principle, but no run shows that it does.
   - dns-cancel runs only inside dns-timeout, as root; elsewhere it is skipped together with that scenario.
   - README.md:30, "it cancels calls at every point where one can wait", and the matching DESIGN sentence say more than the scenarios cover (see the points above).
   The tests that do exist can fail when the behaviour is wrong.  Each cancel-* scenario has a lower and an upper time bound against a server that would otherwise answer seconds later, a cause regex, and a pool or connection count.  cancel-return has a control that pools.  dns-once checks lookups=1 against three rounds, which the old per-round lookup would fail.  I found no regex that matches the wrong line.

9. [Nit] `Error.lookups` and `CallInfo.lookups`, "each host once at most" (Error.lean:337, Client.lean:106), is false on one path.  A lookup that throws is mapped to `connect #[]` (Client.lean, Attempt.connect `.error detail`), the planner retries that cause, and the next round looks the name up again because failures are not cached.

SUSPECTED (plausible, not certain)

10. [Low] cancel-cap (run.sh:1509) may be flaky.  When the shared token is cancelled, call A (in its exchange) drops its connection and wakes `freed`.  If that happens before call B's signal is resolved, B's cap race returns `.done`, and B goes on to connect.  It then fails with "cancelled while connecting" or "cancelled before the request was written" instead of the cap detail the test expects.  A needs at least two task hops to get there and B one, so B usually wins, but under load the order is not guaranteed.

11. [Low, cost] Each call registers in `client.closing` and the caller's token, and each call's end runs that token's unregisterFn, a filterM over the whole consumer queue under the token's mutex.  With n calls in flight on one client, that is O(n) per call end and O(n²) per wave of calls.  Probably fine at realistic concurrency; worth a note.

12. [Low] For each exchange of a call, Live.begin's onCancel closure keeps that exchange's mailbox (including any read completion left in its inbox, up to one read's bytes) until the call ends.  It is bounded by the exchanges per call (redirects, retries, re-dispatches), so it is not a leak, but "for as long as the exchange lasts" (Body.lean docstring of Live.begin) is not accurate: it lasts as long as the call.

DESIGN DECISIONS

- A Cause of its own (`cancelled reason`) rather than localClose: right.  The caller giving up and the client being closed are different facts, and prior art keeps them apart (Go's context.Canceled versus net/http's errors for a closed transport; OkHttp's "Canceled" IOException).  One wrinkle to document: a token cancelled with CancellationReason.deadline (as a CancellationContext with a deadline would do) surfaces as `Cause.cancelled .deadline`, not `Cause.timeout .deadline`, and callers that switch on "timeout" will miss it.
- The exchange-core event: right.  It puts delivery, written and reuse under the existing theorems, and step_cancel shows the step does what the prose says.
- Reporting a cancellation before a request goes out to the planner as a failure with nothing sent: acceptable.  plan_cancelled shows the planner is constant on such a failure, so the round trip decides nothing; it only keeps the record uniform, at the cost of a case in Call.validate that accepts a `decide` with no `send`.  That case is narrow (cause cancelled, notSent, written 0) and has negative unit tests.  Failing directly with `notRetried := .cause` would be just as sound; neither is clearly better.
- Client.close graceful plus Client.shutdown that cancels: the split is right (Go and OkHttp separate the two intents, as NOTES says).  The name is a hazard, though.  In Java's ExecutorService, and in the JDK 21 HttpClient (close / shutdown / shutdownNow), `shutdown` is the graceful stop and `shutdownNow` the one that aborts in-flight work, the opposite of this API.  `shutdownNow`, `abort` or `cancelAll` would not mislead readers who come from there.  There is also no way to wait until the cancelled calls have returned (NOTES lists this as open).  Fixing finding 1 matters more if shutdown is meant as the single "stop everything" call.
- Looking names up once per call: reasonable, and well argued.  OkHttp's per-call RouteSelector is the closest prior art; a process-wide cache without TTLs would be worse.  Finding 4 is the one place where the reasoning (abandoned lookups are expensive) is not carried through to the cancellation.

VERDICT: DEFECTS FOUND
