### Confirmed Defects

#### 1. `BodyStream.read` and `BodyStream.readAll` still hand out held body bytes after cancellation whenever the remaining body fit in the socket read (`LeanHttp/Body.lean:562-566`, `611-617`, `681-683`)
- **Severity**: Medium (correctness bug in a round-1 fix; contradicts docstring/design claims)
- **Where**: [`BodyStream.advance`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L554-L566), [`BodyStream.read`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L611-L617), [`BodyStream.readAll`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L679-L684), and [`BodyStream.new`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L497-L508).
- **What goes wrong and code path**:
  In `fixes.diff`, [`BodyStream.read`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L611-L617) was changed to:
  ```lean
    let next ← match pending, failure, live with
      | [], none, some live => s.advance live
      | _, none, some live =>
        -- Bytes the stream holds are not handed out once the call is cancelled: the cancellation
        -- ends the exchange, and the read raises.
        if (← live.cancel.reason?).isSome then s.advance live else pure state
      | _, _, _ => pure state
  ```
  This check only runs when `live` in `BodyStream.State.open live failure pending offset` is `some live`.
  However, trace what happens when a response has a body that fits in a single socket read (any body up to `readChunkBytes` = 64 KiB, e.g. 1,000 bytes with `Content-Length: 1000`) and the callback `k` first reads part of it (`resp.body.read 1`):
  1. `s.advance live` calls `live.stepNow (.wantBody 1)` ([`LeanHttp/Body.lean:559`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L559)).
  2. In the exchange core, [`Exchange.releaseList`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Exchange.lean#L719-L724) releases *all* of `ex.held` into `.deliverBody` actions whenever `credit > 0`, setting `ex.held := []`.
  3. Because all 1,000 bytes of the body have already been fed to the parser (`ex.parser.complete == true`) and `ex.held` is now `[]`, [`Exchange.bodyDone`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Exchange.lean#L624-L625) (`ex.parser.complete && ex.held.isEmpty`) is `true` in that same step, so [`Exchange.settle`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Exchange.lean#L805-L810) calls `finishNow true`, making `live.verdict == some true`.
  4. [`BodyStream.advance`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L562-L565) sees `live.verdict == some true`, calls `s.settle true`, and returns `.open none none [1000 bytes] 0` (`live` is now `none`!).
  5. `resp.body.read 1` takes 1 byte and stores `.open none none [1000 bytes] 1`.
  6. The call is now cancelled while 999 unread bytes remain held in `pending`.
  7. On the next `resp.body.read` (or `resp.body.readAll`), `live` is `none`, so `read` matches `| _, _, _ => pure state` (and `readAll` matches `| none, none =>`) and returns the remaining 999 held bytes instead of raising `Cause.cancelled`.
  - The new test `cancel-held` in [`tests/net/run.sh:1454`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/tests/net/run.sh#L1454) only passed because it used `/bigbody?n=10000000` (10 MB, which spans multiple 64 KiB socket reads so `ex.parser.complete` stayed `false` after the first read). With `/bigbody?n=1000`, `cancel-held` fails.
  - For the same reason, when a response has an empty body (`Content-Length: 0`, `204`, `304`, `HEAD`), `ex.bodyDone` is already `true` when [`Live.begin`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L378-L389) delivers the head, so [`BodyStream.new`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L502-L507) sets `live := none` and pools the connection before `k` is even entered. A cancellation after the final head and before `k` is entered is therefore *not* seen by `k`'s first read (`resp.body.read` returns `none`, and `Client.request` returns `.ok`), contradicting [`NOTES.md:343`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/NOTES.md#L343) (*"A cancellation that comes after the final head and before the callback is entered is seen by the callback's first read, not before the callback"*).

#### 2. `Attempt.acquire` checks `a.cancel.reason?` before `takeConn` instead of on `.closed`, so `Client.shutdownNow` can still fail an in-flight call with `Cause.localClose` (`LeanHttp/Client.lean:741-748`)
- **Severity**: Medium (race in the round-1 fix for `shutdownNow` vs `localClose`)
- **Where**: [`Attempt.acquire`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L741-L748), [`Client.shutdownNow`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L342-L344).
- **What goes wrong and code path**:
  [`Client.shutdownNow`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L342-L344) runs `client.closing.cancel .shutdown` and then `client.close`.
  In `Attempt.run` when `config.pool == false` ([`LeanHttp/Client.lean:803-807`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L803-L807)), the code reads `s.pool.closed` under the mutex *first* and then checks `a.cancel.reason?`:
  ```lean
  let closed ← a.client.withState (β := Bool) fun s => pure (s, s.pool.closed)
  if let some reason ← a.cancel.reason? then
    pure (.error (notSent (.cancelled reason) "cancelled while taking a connection"), progress)
  else if closed then
    pure (.error (notSent .localClose "the client was closed"), progress)
  ```
  Because `shutdownNow` cancels `client.closing` *before* `client.close` sets `s.pool.closed := true`, checking `a.cancel.reason?` *after* observing `s.pool.closed == true` is guaranteed to see `.shutdown`.
  In [`Attempt.acquire`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L741-L748) (`config.pool == true`), however, the check was placed *before* `takeConn`:
  ```lean
  if let some reason ← a.cancel.reason? then
    return (.error (notSent (.cancelled reason) "cancelled while taking a connection"), progress)
  let left := a.deadline - (← IO.monoMsNow)
  if left == 0 then ...
  match ← takeConn a.client a.target reuse with
  | .closed => return (.error (notSent .localClose "the client was closed"), progress)
  ```
  If a call in `Attempt.acquire` passes line 741 (`a.cancel.reason?` is `none`), and another task calls `client.shutdownNow` before `takeConn` acquires the pool mutex at line 747, `takeConn` sees `s.pool.closed == true` and returns `.closed`, and line 748 returns `Cause.localClose` instead of `Cause.cancelled .shutdown`. Checking `a.cancel.reason?` in the `| .closed =>` branch eliminates this window completely.

#### 3. `Live.next` / `Live.takeCompletion` and the end of `Cancel.race` do not check `Cancel.reason?`, so a wait ended by another event in the `IO.bindTask` window after `token.cancel` misses the cancellation (`LeanHttp/Body.lean:247-267`, `306-343`; `LeanHttp/Cancel.lean:170-172`; `LeanHttp/Transport.lean:278-305`; `LeanHttp/Connect.lean:247-255`)
- **Severity**: Medium (race between `token.cancel` and concurrent socket/timer completions; can cause wrong `Cause`, an unwanted retry/re-dispatch, or an inaccurate doc claim)
- **Where**:
  - [`Live.takeCompletion`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L247-L267) and [`Live.next`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L306-L343)
  - [`Cancel.race`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Cancel.lean#L170-L172)
  - [`Transport.handshake`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Transport.lean#L278-L305) and [`Connect.resolve`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Connect.lean#L247-L255)
  - [`Attempt.run`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L838-L873) and [`CallSpec.loop`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L987-L1000)
- **What goes wrong and code path**:
  [`LeanHttp/Cancel.lean:16-19`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Cancel.lean#L16-L19) states:
  > *"`reason?` says whether the call has been cancelled, by asking the tokens themselves, so that a check made after a token was cancelled sees it at once, whatever has been scheduled since: the shell checks it before each step it takes ... and after any wait that something else ended."*

  In fact, neither `Live.next` nor `Cancel.race` checks `reason?` when a wait ends:
  1. **In `Live` (`LeanHttp/Body.lean`)**: During `Live.until` (used by `Live.begin`, `BodyStream.drive`, `BodyStream.collect`, `Live.abandon`), cancellation only enters `mailbox.inbox` via [`cancel.onCancel`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Body.lean#L383-L385), which is chained on `c.signal.result?` — the signal that lags `token.cancel` until `Selectable.combine`'s `IO.bindTask` worker runs. `Live.next` and `Live.takeCompletion` never call `live.cancel.reason?`.
     - If `token.cancel` returns and, before the `Selectable.one` worker runs, a socket read/write completes (e.g., the caller cancels the token and closes the peer/server, or loopback I/O finishes on the libuv thread), `Mailbox.watch` (`sync := true`) pushes `.read`/`.wrote` and rings `mailbox.bell` immediately.
     - `Live.next` wakes up, sees only `.read`/`.wrote` in `mailbox.inbox`, and steps the core with `.endOfInput`/`.readFailed`/`.received` instead of `.cancel`.
     - When `Live.begin` then returns `.ok (live, none)` with `f.cause = .peerClosed`, neither [`Attempt.run`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L838-L873) nor [`CallSpec.loop`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Client.lean#L987-L1000) checks `cancel.reason?`:
       - If the connection was reused and the request replayable, `Attempt.run` re-dispatches it (`redispatch?` returns `some .closedBeforeResponse`).
       - Otherwise `CallSpec.loop` passes `.failure { cause := .peerClosed, ... }` to `Call.plan`: if retries remain, `Call.plan` plans a retry (incrementing `st.retries` by 1 before the next iteration of `CallSpec.loop` fails with `Cause.cancelled`, making `Error.retries` 1 too high); if no retries remain (e.g. a POST after bytes were written, or `maxRetriesPerHop = 0`), the call fails with `Cause.peerClosed` instead of `Cause.cancelled`.
  2. **In `Cancel.race` (`LeanHttp/Cancel.lean:170-172`)**: While `Cancel.race` awaits `winner.result!`, cancellation only resolves `winner` via `bell.result?`, which is rung by `c.signal.result?` (after the `IO.bindTask` hop). If a raced task or timer resolves `winner` in the window after `token.cancel` and before `c.signal` resolves, `Cancel.race` returns `.done r` or `.timedOut` without checking `c.reason?`.
     - [`Connect.round`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Connect.lean#L211-L212) added a manual post-loop `if let some reason ← cancel.reason?` check to compensate for this, but [`Transport.handshake`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Transport.lean#L278-L305) and [`Connect.resolve`](file:///home/matthias/prog/lean-http-notes/cancel/review2/tree/LeanHttp/Connect.lean#L247-L255) did not.      - Checking `c.reason?` at the end of `Cancel.race` (when `result` is not already `.cancelled`) and in `Live.takeCompletion` / `Live.next` fixes all of these in one place.

### Suspicions and Minor Observations

1. **`Transport.idleClean` does not race `Cancel` (`LeanHttp/Client.lean:769-770`, `LeanHttp/Transport.lean:229-235`)**:
   In `Attempt.acquire`, when an idle connection is taken from the pool, `idle.transport.idleClean window` waits with `awaitFirst #[waiter.result?] ms` rather than `cancel.race`. With the default `idleCheckMs = 1` this is imperceptible, but if a caller configures a larger `Config.idleCheckMs` (or has several stale idle connections in a row to discard), cancellation waits out the idle check window(s) before being noticed at the next `Attempt.acquire` iteration or at `Attempt.run` line 816.
2. **Untested cancellation points**:
   As noted in `verdicts.txt` line 14, there is no real-socket test for cancelling during a response-body drain (`Live.abandon` while draining a redirect/retry body) or for cancelling an `https` call after a pooled TLS connection fails and is re-dispatched. Also, `cancel-held` only tests a 10 MB body (where `live` is still `some live`), missing the single-read body case where `live` becomes `none` while `pending` is still non-empty (Defect 1 above).

### Evaluation of the Design Decisions and Prior Art

1. **A new `Cause.cancelled (reason : Std.CancellationReason)` vs. reusing `Cause.localClose`**:
   - **Verdict**: Good decision.
   - **Why & Prior Art**: Closing a client (`localClose`) is a lifecycle error of the pool/client resource, whereas cancelling a call (`cancelled reason`) is per-call control flow initiated by the caller (often carrying a specific `CancellationReason` such as `.deadline`, `.shutdown`, or `.custom`). Callers routinely branch on whether *they* cancelled a request vs. whether they accidentally used a closed client. Go (`context.Canceled` / `context.DeadlineExceeded` vs. `http.ErrServerClosed` / pool close), Java `HttpClient` (`CancellationException` vs. `ClosedChannelException`), Rust `reqwest`/Tokio, and OkHttp (`IOException("Canceled")`) all distinguish caller cancellation from transport/pool closure.

2. **Modelling cancellation as an exchange-core event (`ExchangeEvent.cancel`)**:
   - **Verdict**: Good decision.
   - **Why**: Keeping the exchange core the single source of truth for phase transitions, `Delivery` accounting (`notSent` / `maybeDelivered` / `responseReceived`), `written` byte counts, and connection reuse (`step_cancel_not_reusable`) means the existing invariants (`Inv`, `Agrees`, `Observed`) and liveness/safety proofs extend to cancellation with one constructor rather than duplicating state-dependent delivery logic in the `Async` shell.

3. **Reporting a pre-send cancellation to the planner as a `notSent` failure in place of `.send`**:
   - **Verdict**: Reasonable and pragmatic tradeoff.
   - **Why**: Because `plan_cancelled` proves `Call.plan` always transitions immediately to `.fail (.failure f .cause)` without modifying `st` (`hops`, `retries`, `attempts`), feeding a synthetic `notSent (.cancelled reason)` failure to `Call.plan` preserves single-planner authority and trace replayability (`Call.validate`) without adding a third constructor to `Call.Outcome` that would have to be case-split in every theorem in `LeanHttp/Call/Proofs.lean`.

4. **Keeping `Client.close` graceful and adding `Client.shutdownNow`**:
   - **Verdict**: Good decision, especially after renaming `shutdown` to `shutdownNow`.
   - **Why & Prior Art**: Separating "stop accepting new work / evict idle connections" from "abort in-flight requests" matches Java's `ExecutorService.shutdown()` vs. `shutdownNow()`, OkHttp's `ConnectionPool.evictAll()` vs. `Dispatcher.cancelAll()`, and Go's `Transport.CloseIdleConnections()` vs. cancelling a root `context.Context`. Using an internal `closing : Std.CancellationToken` on `Client` that every call watches alongside its own token is clean and avoids maintaining a separate registry of in-flight calls in `Client`.

5. **Looking up each host name once per call (`Progress.resolved`)**:
   - **Verdict**: Good decision given Lean v4.34.1's un-cancellable `uv_getaddrinfo`.
   - **Why & Prior Art**: Because an abandoned `DNS.getAddrInfo` holds a libuv worker thread until the OS resolver times out and can delay or crash process exit on v4.34.1, minimizing lookups per call directly reduces exposure to runtime exit bugs while saving latency across connect retries and same-host redirects. Prior art is split: OkHttp's `RouteSelector` resolves once per call/exchange sequence and steps through the resulting addresses across retries; curl caches DNS entries per handle/share (60 s default TTL); Go's `net.Dialer` resolves on each dial. Given that `getaddrinfo` does not expose DNS TTLs for a cross-call cache and a single call's retries span only seconds, caching per call in `Progress.resolved` is the right point in the design space.
   - **One refinement to consider**: Host names in `Progress.resolved` are keyed by `host : String` as stored in `URI.Host.name`. If `Std.Http.URI` does not normalize ASCII case on host names across redirects (e.g., `http://Example.com/` redirecting to `http://example.com/path`), normalizing `host.toLower` for the lookup key in `Progress.resolved` (as `Origin` comparisons in RFC 9110 §4.2.3 do) would avoid a redundant lookup on a case-changed redirect.
