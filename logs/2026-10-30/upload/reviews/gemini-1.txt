### Answers by Review Area

#### Area 1: Pulling before write / head written; `"not sent"` after a pull
**Nothing broken found.** (Confidence: High)
* **Can the core pull before any write is issued or before the request head is written?**
  No. [`Exchange.pullDue`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L1012-L1014) requires:
  ```lean
  !ex.terminal && !ex.uploadStopped && !ex.complete && !ex.pulling &&
    ex.sentAny && decide (ex.headBytes ≤ ex.written) && decide (ex.known ≤ ex.written)
  ```
  In [`Exchange.begin`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L653-L686), `sentAny` starts `false` and `written` starts `0`. Even for a hand-constructed `PreparedRequest` with `bytes = .empty` (`headBytes = 0`, `known = 0`), [`scheduleWrite`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L1000-L1009) checks `ex.written < ex.known` (`0 < 0`, false), so `sentAny` remains `false` and [`schedulePull`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L1018-L1023) cannot emit `.pull`. For any request with `headBytes > 0`, `scheduleWrite` sets `sentAny = true` and `writeInFlight = some headLen`, so `written` remains `0 < headBytes` (and `0 < known`) until `.written headBytes` arrives. This is also proved by [`step_pulls`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L2941-L2966) and [`observed_pull`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L3125-L3132).
* **Can a failure reported as `.notSent` follow a pull?**
  No, neither in the core nor in the shell:
  * In the core, `Failure.delivery` is computed by [`Exchange.delivery`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L556-L558), which returns `.notSent` iff `!ex.sentAny`. Since `.pull` requires `ex.sentAny = true`, and `sentAny` is monotonic (`step_sentAny_mono`), no `.fail f` with `f.delivery = .notSent` can ever follow a `.pull` (proved in [`observed_notSent_unpulled`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L3139-L3151)).
  * In the shell ([`Attempt.run`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Client.lean#L626-L639)), `live.produce` is only invoked by [`Live.perform`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L155-L157) when the core emits `.pull`, and any uncaught exception in `Live.begin` is wrapped with `delivery := .maybeDelivered`.

#### Area 2: Declared size bounds & RFC 9112 §7.1 chunked framing
* **Can more bytes than a declared size reach the wire?**
  **No.** (Confidence: High)
  In [`Exchange.accept`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L583-L588), when `ex.framing = some (.length size)`, a chunk is only enqueued into `ex.request` if `ex.taken + chunk.size ≤ size` (and `!ex.complete`). Otherwise `accept` returns `.error`, and [`handle`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L906-L911) does not enqueue the chunk and terminates the exchange via `failOrDrop`. Proved in [`observed_length_written`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L3282-L3299).
* **Can a `Content-Length` request end short without failing?**
  * If the producer returns `none` when `ex.taken < size` while the exchange is still in `.sending` or `.receiving`, [`Exchange.accept`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L597-L600) returns `.error (.requestBody ...)` and [`handle`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L911) fails the exchange before any further write.
  * If the server sends a complete response early (`ex.early = true`) and the caller finishes reading that response body before the upload completes, [`settle`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L797-L801) finishes the exchange with `.finish false` (`reusable = false`) and the call returns `.ok response` with fewer than `size` request body bytes written (by design per [`DESIGN.md:83`](file:///home/matthias/prog/lean-http-wt-upload-review/DESIGN.md#L83)).
  * For a producer that yields **more** than `size` bytes (or errors after yielding `size` bytes), see **Finding 1** above.
* **Is the chunked framing RFC 9112 §7.1 compliant?**
  **Yes.** (Confidence: High)
  * [`Codec.Request.chunkFrame`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Codec/Request.lean#L149-L150) is only called by [`Exchange.accept`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L581-L593) when `!chunk.isEmpty` (`chunk.size > 0`).
  * [`Codec.hexDigits`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Codec/Chunked.lean#L87-L96) encodes `n > 0` as minimal non-empty lowercase hexadecimal ASCII (`0-9`, `a-f`) with no leading zeroes (`1*HEXDIG`).
  * `chunkFrame` formats `<hex(data.size)>\r\n<data>\r\n` (`chunk = chunk-size CRLF chunk-data CRLF`).
  * [`Codec.Request.lastChunk`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Codec/Request.lean#L155-L156) is `#[48, 13, 10, 13, 10]` = `"0\r\n\r\n"` (`last-chunk` `"0\r\n"` + empty `trailer-section` + `"\r\n"`).
  * Empty chunks (`chunk.isEmpty`) are skipped in [`Exchange.accept`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L581-L582) so an interior chunk never emits a bogus `"0\r\n\r\n"`.

#### Area 3: Connection reuse & soundness of the `wireDone` rule
**Connection reuse is safe; no framing corruption or desynchronization found.** (Confidence: High)
* **Can a connection be marked reusable when the request body was not fully written, or when the server answered early?**
  No. Both [`Exchange.reusableNow`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L620-L622) and [`worthDraining`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L932-L936) require `ex.wireDone && ex.written == ex.known && !ex.early`. When the final response head arrives in [`onHead`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L728-L735), `ex.early` is latched once to `ex.unsent` (`!ex.wireDone || decide (ex.written < ex.known)`). If the server answered before `wireDone` and `written == known`, `ex.early` is `true` for the rest of the exchange and `reusableNow` is `false`. Proved in [`observed_finish_reusable`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L2851-L2875).
* **Is the `wireDone` rule sound for connection reuse?**
  Yes, for **wire framing and connection reuse** it is sound:
  * When `framing = some (.length size)`, `ex.wireDone` (`ex.taken == size`) plus `ex.written == ex.known` guarantees that the socket has received the request head (`Content-Length: <size>`) followed by `size` body bytes—the exact byte count the HTTP/1.1 framing on the wire expects.
  * Even if the exchange finishes (`ex.terminal = true`) while the final `none`-check pull is still in flight, the shell stops stepping `ex` and never calls [`Live.perform`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L144) on that `Live` again, so even if the orphaned pull task later resolves with `some chunk`, nothing can ever write those bytes to the pooled socket.
  * The only downside of `wireDone` is the producer-validation race in **Finding 1** and the `.draining` transition in **Finding 2**, not connection corruption.

#### Area 4: Shell (`Live.next`, pull in flight at end, producer exceptions, retry/redispatch, 307/308, `awaitFirst`)
* **Races in `Live.next` between pull, write, and read**:
  * In the core, `pulling` and `writeInFlight` are mutually exclusive (`Inv.pullIdle`: `ex.pulling = true → ex.writeInFlight = none`), so at most one of `writing` and `live.pulling` is `some` at any time.
  * Similarly, `ex.uploadStopped` can only become `true` when a write fails or times out while `writeInFlight.isSome`, so `live.pulling` is always `none` when `ex.uploadStopped` is `true`.
  * The only race issue between `reading` and `pulling` is the one detailed in **Finding 1**: when `size` bytes have been written and the final `.pull` races against `.read`, `.read` can finish the entire exchange before the final `.pull` is awaited.
* **What happens to a pull in flight when the exchange ends?**
  When `live.ex.terminal` becomes `true`, [`Live.until`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L222), [`BodyStream.drive`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L375), and [`BodyStream.collect`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L474) stop calling [`Live.next`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L167), and [`BodyStream.settle`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L317-L328) closes or returns the socket. Because Lean's `AsyncTask` has no cooperative cancellation token, an in-flight `live.pulling : Option (Task Completion)` continues running in the background until `produce` returns, and its `Completion.pulled` result is simply garbage-collected without touching the socket or `Exchange`.
* **Producer exceptions**:
  `live.produce` has type `Async (Option ByteArray)` (`EAsync IO.Error (Option ByteArray)`). [`Live.perform`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L156) launches it via `start` (`EAsync.toBaseIO`), which catches any `IO.Error` inside the task and resolves the task to `.error err`.
