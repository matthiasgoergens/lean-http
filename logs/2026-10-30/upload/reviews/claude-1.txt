## 1. Memory still grows with the number of chunks while a read is pending (medium; confidence medium)
Where: LeanHttp/Wait.lean (awaitFirst), LeanHttp/Body.lean (Live.next, the pending array).
The core asks for a read as soon as the request head is written; that read normally stays pending for
the whole upload.  Every Live.next races [read, write, pull], and awaitFirst adds one continuation to
each task in a race.  The pending read therefore collects at least two continuations per chunk, each
holding a promise, until the server answers.  The change (resolving with the winner's index) made each
smaller; it did not stop them piling up.  Scenario: the README's producer makes chunks of about 1 KB;
10 GB that way is about 10^7 races.  The 100 MB RSS check uses 16 KiB chunks and 256 MiB (about 32k
races).  Suggested fix: attach one continuation to each operation when it starts (a per-exchange
promise or channel), rather than one per race.

## 2. A checker property flags behaviour the design documents (medium-low)
Tests/Support/Check.lean, "a broken streamed body fails the exchange" demands a fail with cause
requestBody, but while draining failOrDrop emits finish false, as DESIGN.md describes.  Reachable:
declared body given in full (wireDone), final pull in flight, a non-early head with an incomplete
body, abandon passes the drain checks, then pullFailed or an extra chunk.

## 3. How wireDone behaves when a producer misbehaves after its declared size (low-medium; design)
Wire safety is sound (observed_finish_reusable with Framed.length gives acked = start.length + size
on a reusable finish).  The final "does it end here?" check is racy: if the response completes first
the call succeeds and a producer that would give more is never caught; if the pull returns first with
an extra chunk, the call fails even while the caller reads a valid response.  The README overclaims
("A stream that gives more fails the call"); Exchange.lean qualifies it.  Alternative: pull once more
before writing the chunk that reaches the size.
