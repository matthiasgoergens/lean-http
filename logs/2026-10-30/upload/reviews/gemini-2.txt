#### 2. [Low] Checker property `"a broken streamed body fails the exchange"` in `Tests/Support/Check.lean` could pass a broken `.pulled` / `.pullFailed` handler while `pre.phase = .draining` if a deadline expires in the same step
- **Location:** [Check.lean](file:///home/matthias/prog/lean-http-wt-upload-review/Tests/Support/Check.lean#L319-L325) ([`checkStep`](file:///home/matthias/prog/lean-http-wt-upload-review/Tests/Support/Check.lean#L223-L355))
- **Confidence:** High
- **Details:**
  The updated check in [`checkStep`](file:///home/matthias/prog/lean-http-wt-upload-review/Tests/Support/Check.lean#L319-L325) is:
  ```lean
  found := flag found "a broken streamed body fails the exchange"
    (!before.bodyBroken && m.bodyBroken && !wasEnded &&
      !(actions.any fun a => match a with
        | .fail f => (match f.cause with | .requestBody _ => true | _ => false)
        | .finish false => (match pre.phase with | .draining => true | _ => false)
        | _ => false))
    fun _ => s!"{actions.map renderAction}"
  ```
  First, note a minor architectural point: the module comment at [Check.lean](file:///home/matthias/prog/lean-http-wt-upload-review/Tests/Support/Check.lean#L8-L9) states *"It does not look inside the core except for `terminal`, `nextDeadline` and a fingerprint of the state (for the stale-tick property)"*, whereas line 323 now inspects `pre.phase` instead of the model's `before.abandoned` (or a model `draining` flag).
  More importantly, consider what happens if the core has a defect where `handle` ignores `.pullFailed` or a refused `.pulled` while draining (or in general):
  - **Concrete scenario:**
    1. A request with `stream := some (some 3)` writes its 3 bytes; the core issues the final `pull`, receives the response head (`200 OK`, `Content-Length: 10`), and the caller sends `.abandon`.
    2. `pre.phase` is now `.draining` with `drainBy = some (t₀ + drainMs)` (or `deadline` or `readBy`).
    3. At `now ≥ t₀ + drainMs` (e.g., `genEvent` in [Gen.lean](file:///home/matthias/prog/lean-http-wt-upload-review/Tests/Support/Gen.lean#L306-L308) picks `dt = 20` when `drainMs = 10`, or in `explore`), the event `.pullFailed "disk error"` (or `.pulled (some "d")`) arrives.
    4. Suppose `handle` has a defect that forgets to call `failOrDrop` on `.pullFailed` (or on `.pulled` when `ex.phase == .draining`).
    5. In [`Exchange.step`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L1072), `expire` runs immediately after `handle`. In [`expireOne`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange.lean#L954-L958):
       ```lean
       | .draining =>
         if now ≥ ex.deadline || ex.drainBy.any (now ≥ ·) || ex.readBy.any (now ≥ ·) then
           finishNow false
       ```
       `expire` emits `.finish false` because of the timer, **leaving `post.pulling = true`** (if `handle` ignored the event) or masking the ignored error!
    6. `checkStep` sees `.finish false` in `actions` and `pre.phase == .draining`, so `"a broken streamed body fails the exchange"` passes. Even worse, if `handle` completely ignored `.pullFailed` while draining (leaving `ex.pulling = true`), no other property in `checkStep` notices that `post.pulling` disagrees with `m.pullOutstanding` on that terminal step!
  - In a step where `now < drainBy` and `now < deadline` and `now < readBy`, the check **does** catch the defect, because nothing else in `Exchange` can emit `.finish false` during a `.pulled` / `.pullFailed` step (since `settle` and `onBodies` do not run on `.pulled` / `.pullFailed`). And in a non-draining phase (`pre.phase ≠ .draining`), nothing else in `Exchange` can emit `.fail f` with `f.cause = .requestBody _`, because `expire` only emits `.timeout _`. Thus, outside the simultaneous-drain-timeout case, the check is tight.

### Detailed Verification of Items Where Nothing Was Found

#### Item 1: `LeanHttp/Body.lean` (`Mailbox`, `Live`, and TLS integration)

I traced all state transitions and thread interleavings in [Body.lean](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L69-L383) and [Transport.lean](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Transport.lean#L129-L188) and found **no bugs**:

1. **Races between setting the fresh bell, reading the inbox, and a completion arriving on another thread:**
   - In [`Mailbox.watch`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L185-L190):
     ```lean
     m.inbox.modify (·.push (n, f r))
     (← m.bell.get).resolve ()
     ```
   - In [`Live.next`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L291-L298):
     ```lean
     let bell ← IO.Promise.new
     live.mailbox.bell.set bell
     let completion ← match ← live.takeCompletion with
       | some c => pure (some c)
       | none =>
         match ← awaitFirst #[bell.result?] wait with
         | none => pure none
         | some _ => live.takeCompletion
     ```
   - Because `IO.Ref.modify`, `IO.Ref.get`, and `IO.Ref.set` are atomic (sequentially consistent via mutex/atomic pointer exchange in the Lean runtime), the store ordering in the producer is `push to inbox` $\prec_p$ `get bell` $\prec_p$ `resolve bell`, and in the consumer is `set fresh bell` $\prec_c$ `takeCompletion (read/modify inbox)` $\prec_c$ `await bell`.
   - If the first `takeCompletion` returns `none`, then for any current operation $n$, its `inbox.modify` has not yet run at the moment `takeCompletion` executed. Therefore:
     $$\text{set fresh bell} \prec_c \text{first } \text{takeCompletion} \prec \text{inbox.modify} \prec_p \text{bell.get} \prec_p \text{resolve}.$$
     Thus `m.bell.get` in the producer is guaranteed to read the fresh `bell` (since nothing else calls `bell.set` until the next `Live.next` on the single driving task), and `bell.resolve ()` will resolve the exact promise `awaitFirst` is waiting on. No wake-up can be lost.
   - If the producer pushes to `inbox` *after* `bell.set` and *before* the first `takeCompletion`, the first `takeCompletion` takes the item immediately (`some c`) and does not wait on `bell`; the producer also resolves `bell`, which is harmlessly discarded on the next `Live.next`.

2. **Can a completion be lost, reported twice, reported for a cancelled or stale operation, or wake nothing?**
   - **Lost?** No. `Live.takeCompletion` ([Body.lean](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L230-L248)) filters `inbox` by `current`, keeping every completion whose operation number `n` matches `live.reading`, `live.writing` (while `!live.ex.uploadStopped`), or `live.pulling`. When multiple current operations have completed, it selects `best` (lowest rank: `wrote` (0) < `pulled` (1) < `read` (2)) and removes only `best` (`inbox.filter (·.1 != n)`). The remaining current completions stay in `inbox`. On the next call to `Live.next`, the first `live.takeCompletion` immediately picks the next one without waiting.
   - **Reported twice?** No. `Live.takeCompletion` atomically removes `(n, c)` from `inbox` via `inbox.filter (·.1 != n)`. Even before `live.reading`/`writing`/`pulling` is cleared in `Live.report` (or in the TLS `.inr ()` branch), `(n, c)` is no longer in `inbox`, and each operation task completes at most once (`BaseIO.chainTask` runs once).
   - **Reported for a cancelled or stale operation?** No. Every operation gets a strictly increasing `n := live.nextOp` (`nextOp := n + 1`).
     - When a read is cancelled via [`Live.cancelRead`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L176-L179), `live.reading` becomes `none`.
     - When an operation is reported in [`Live.report`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L253-L280), its slot (`reading`, `writing`, or `pulling`) is set to `none` (and in `Live.perform` only scheduled if the core emits a new action, which gets a new `n`).
     - When the core stops the upload (`live.ex.uploadStopped = true`, either on a write failure after the head or a write timeout after the head), `current` in `Live.takeCompletion` checks `live.writing == some n && !live.ex.uploadStopped`, so a late completion of the stalled write is dropped and does not wake `Live.next` with `none` unnecessarily when another operation is ready (or if it wakes `bell` alone, `Live.takeCompletion` after `awaitFirst` returns `none`, which steps the core with `.tick` at `now`—a no-op if before `nextDeadline`, or expiring whatever deadline is due).
   - **Does `bell` stay permanently resolved?** Because `bell` is replaced at the start of every `Live.next` (`live.mailbox.bell.set bell`), a stale operation ringing `bell` at most causes one spurious wake-up of `awaitFirst`, which `takeCompletion` turns into `none` (`.tick`), and the next iteration of `Live.next` installs a brand-new unresolved `IO.Promise`.

3. **Does the TLS ciphertext path restart the receive correctly and keep the read number and `readMax` current?**
   - In [`Live.startRead`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L194-L197):
     ```lean
     let n := live.nextOp
     live.mailbox.watch n (← live.transport.startRead max) Completion.read
     return { live with reading := some n, nextOp := n + 1, readMax := max }
     ```
   - When `Transport.startRead` returns `.cipher raw` (because the TLS session held no plaintext and started a TCP receive), `Live.next` ([Body.lean](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L301-L317)) calls `live.transport.absorb live.readMax raw`:
     - If `absorb` returns `some result` (plaintext, clean EOF, or error), it becomes `Completion.read (.plain result)` and goes through `Live.report`, which sets `reading := none` and updates `received`.
     - If `absorb` returns `none` (`.wantRead`—a partial TLS record or consumed post-handshake message like a TLS 1.3 `NewSessionTicket`):
       ```lean
       let (ex, actions) := live.ex.step (← IO.monoMsNow) .tick
       let live := { live with ex, reading := none }
       if ex.terminal then return (live, actions)
       return (← live.startRead live.readMax, actions)
       ```
       Here:
       1. `live.ex.step (← IO.monoMsNow) .tick` advances the core's clock and expires any deadline that passed, while `ex.readInFlight` stays `true` in the core.
       2. If `ex.terminal` is `true` (a deadline expired during `.tick`), `reading` is `none` (the previous TCP receive already completed!), and `(live, actions)` is returned to `Live.until` / `BodyStream.drive` / `BodyStream.collect`, which performs `actions` (`.fail` / `.finish`, calling `cancelRead` which is a no-op since `reading := none`) and exits without starting a new TCP receive.
       3. If `ex.terminal` is `false`, What actions can `.tick` emit? Since `ex.readInFlight` is already `true` in the core, `scheduleRead` cannot emit `.read`. Could `.tick` expire a stalled write after the response head (`stopUpload`)? Even if it does, `stopUpload` only sets `uploadStopped := true`, clears `writeBy`, and sets `readBy`; `scheduleWrite` and `schedulePull` cannot emit anything when `uploadStopped = true`. Thus `actions` is always `#[]` when `ex.terminal = false` on a `.tick` step!
       4. `live.startRead live.readMax` allocates a fresh operation number `n := live.nextOp`, sets `reading := some n`, `nextOp := n + 1`, and preserves `readMax := live.readMax`.
       5. Returning to `Live.until` / `BodyStream.drive` / `BodyStream.collect` checks `s.state.get matches .released` before the next `Live.next`, so if the `withResponse` callback ended concurrently in another task, `release` cancels the receive and the loop exits cleanly.

4. **Does anything still grow per wait?**
   - **Pending read task continuations:** `Live.startRead` chains **one** continuation on the read task via `Mailbox.watch`. While the read stays pending across thousands of write and pull steps, `Live.next` only creates a fresh `bell : IO.Promise Unit` and chains `awaitFirst` onto `bell.result?`. When `bell` is resolved by a write or pull completion, `bell` and its `awaitFirst` continuation become unreachable and are collected immediately. Nothing is chained onto the pending read task in `Live.next`.
   - **Timer task in `awaitFirst`:** When `bell` wins in [`awaitFirst`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Wait.lean#L38-L51), `sleep.stop` cancels the libuv timer immediately, dropping its promise and freeing the timer task.
   - **`mailbox.inbox`:** Filtered by `current` on every `Live.takeCompletion` ([Body.lean](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Body.lean#L236)). Since at most one read, one write, and one pull are current at any time, `inbox` holds at most 3 elements after `takeCompletion` (and at most 3 + any completions between two `takeCompletion` calls, which is at most 1 per started operation).
   - **`Delivered` in `Live.until`:** `Live.until` is called only in `Live.begin` (with `stop := (·.head.isSome)` and `ex.credit = 0`, so `out.bodies` is always `#[]`) and `Live.abandon` (in `.draining` phase where `onBodies` discards bytes rather than emitting `.deliverBody`, or when `ex.parser.complete` is already true and the held bytes are delivered in `stepNow` before any wait).

#### Item 2: Statements of `accept_length`, `step_broken`, and `handle_broken` in `LeanHttp/Exchange/Proofs.lean`

- **[`accept_length`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L3355-L3358):**
  ```lean
  theorem accept_length {ex : Exchange} {size : Nat} (hf : ex.framing = some (.length size)) :
      (∀ chunk : ByteArray, chunk.isEmpty = false →
        ((∃ cause, ex.accept (some chunk) = .error cause) ↔ size < ex.taken + chunk.size)) ∧
      ((∃ cause, ex.accept none = .error cause) ↔ ex.taken ≠ size)
  ```
  - **Does it say what its docstring claims?** Yes: *"With a declared size, a non-empty chunk is refused exactly when it would take the body beyond the size, and the end exactly when the body falls short of it."* (Note: in every reachable state with `framing = some (.length size)`, `ex.taken ≤ size` holds by `Observed.framed` + `Observed.agrees`, so `ex.taken ≠ size` is equivalent to `ex.taken < size`, i.e., falling short of it.)
  - **Is anything vacuous?** No. Both conjuncts are bidirectional (`↔`), and `ex.framing = some (.length size)` is satisfied by every exchange prepared by `Exchange.prepareStream config head (some size)`.

- **[`handle_broken`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L3395-L3401) and [`step_broken`](file:///home/matthias/prog/lean-http-wt-upload-review/LeanHttp/Exchange/Proofs.lean#L3426-L3432):**
  - **Is anything vacuous?** No. The hypotheses `ht : ex.terminal = false`, `hp : ex.pulling = true`, and `he : (∃ c cause, e = .pulled c ∧ ex.accept c = .error cause) ∨ ∃ d, e = .pullFailed d` are all jointly satisfiable on reachable exchanges (whenever a pull is in flight and the producer fails or violates `size`). Crucially, `step_broken` proves `hs : (ex.terminal || stale ex now e) = false` unconditionally from `ht` and `he` (because `stale` is `false` for `.pulled` and `.pullFailed` regardless of `now`), so the theorem cannot be vacuously bypassed by a stale timestamp.
  - **Do they say what their docstrings claim?** They accurately prove what happens to `ex'.terminal` and `ex'.phase` (either `ex'.phase = .failed f ∧ f.cause = .requestBody d`, or `ex.phase = .draining ∧ ex'.phase = .finished false`), with the caveat noted in **Finding 1** that they state this on `ex'.phase` (`(ex.step now e).1`) rather than on the emitted actions `(ex.step now e).2` or the checker's `Obs` model.
