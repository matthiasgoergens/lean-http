### High Confidence Findings

#### 1. `BodyStream.release` cancels `recv?` only once when entering `.busy`, so a background read that receives an empty read, a chunk-size/trailer line, or a write completion issues a *second* `recv?` that is never cancelled
- **Location:** [`Body.lean:338-346`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L338-L346) (`BodyStream.drive`), [`Body.lean:438-446`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L438-L446) (`BodyStream.collect`), [`Body.lean:513-520`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L513-L520) (`BodyStream.release`)
- **Confidence:** **High**
- **Breaks:** Guarantee 3 (*connection given back or dropped on every path*), Guarantee 4 (*no pending `recv?` outlives the callback, nor does the callback hang*), and the C2/G2 fix (*"the end of the callback cancels the receive pending, so the wait it finds ends at once"*).
- **Mechanism:**
  In [`BodyStream.drive`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L338-L346) (and identically in [`BodyStream.collect`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L438-L446)):
  ```lean
  private partial def drive (s : BodyStream) (live : Live) (actions : Array ExchangeAction) :
      Async (Live × Array ByteArray) := do
    let (live, out) ← live.perform actions {}
    if live.ex.terminal || !out.bodies.isEmpty then
      return (live, out.bodies)
    if (← s.state.get) matches .released then
      return (live, #[])
    let (live, actions) ← live.next
    s.drive live actions
  ```
  Notice the order in each iteration:
  1. `live.perform actions {}` starts any `.read max` action in `actions` (registering a fresh `socket.recv?`).
  2. `if (← s.state.get) matches .released` is checked.
  3. `live.next` waits on `awaitFirst pending wait` and calls `live.ex.step`.

  [`BodyStream.release`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L513-L520) swaps `s.state` to `.released`, calls `socket.native.cancelRecv` **once**, and then blocks on `await done.result?`.
  There are two ways a `recv?` remains uncancelled while `release` is stuck waiting on `done.result?`:

  - **Case A (Wait woken by an event that emits a new `.read` with no body bytes):**
    Suppose the reader task is already inside `live.next` (`awaitFirst`). `release` swaps `s.state` to `.released` and runs `cancelRecv`.
    1. If `cancelRecv` resolves the in-flight `recv?` with `.ok (some ByteArray.empty)` (or if an in-flight request body `.write` completes first in `awaitFirst`, or if the TCP socket had a chunk-size header `"5\r\n"` or trailer line ready just as `cancelRecv` ran):

          That's actually completely airtight for settling the connection! Every single path settles `s` with the pool at most once (`settleOnce`) and at least once!

#### 1. Leaving `withResponse` without reading a response whose body already arrived with the head counts already-received bytes against `drainBytes` and can drop a clean connection
- **Location:** [`Body.lean:203-207`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L203-L207) (`Live.begin`), [`Body.lean:299-309`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L299-L309) (`BodyStream.new`), [`Exchange.lean:513-514`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean#L513-L514) (`Exchange.bodyDone`), [`Exchange.lean:780-791`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean#L780-L791) (`Exchange.handle .abandon`)
- **Confidence:** **High** (Low-to-Medium impact: connection reuse lost and `BodyStream.new`'s docstring slightly inaccurate for non-empty bodies)
- **Mechanism:**
  During [`Live.begin`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L203-L207), `ex.credit` is `0`. If the response head and the entire response body arrive in the same `socket.recv?` call, `Parser.feed` transitions `parser.phase` to `.done` (`parser.complete == true`), but because `ex.credit == 0`, the decoded body bytes remain in `live.ex.held`.
  In [`Exchange.lean:513-514`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean#L513-L514):
  ```lean
  def bodyDone (ex : Exchange) : Bool :=
    ex.parser.complete && ex.held.isEmpty
  ```
  Because `ex.held` is non-empty, `ex.bodyDone` is `false`, so `live.ex.phase` stays `.receiving` and `live.verdict` is `none` (meaning [`BodyStream.new`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L303) only sees `live.verdict == some true` for 0-byte bodies).
  Compare what happens next depending on whether the `withResponse` callback reads 1 byte (`stop=1`) or 0 bytes (`stop=0`):
  - **If the callback calls `resp.body.read 1` and then exits (`stop=1`):**
    `BodyStream.advance` sends `.wantBody 1` to `Exchange`, which moves all of `ex.held` into `BodyStream.pending`. Now `ex.held` is `[]`, `ex.bodyDone` is `true`, and `Exchange` finishes immediately with `reusable = true` (`s.settle true`), regardless of `drainBytes`.
  - **If the callback exits without calling `resp.body.read` (`stop=0`), or on a redirect/retried response (`discardBody`):**
    `stream.release` (or `discardBody`) calls `live.abandon`, which sends `.abandon` to `Exchange` while the already-received body is still in `ex.held`. [`Exchange.handle .abandon`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean#L781-L791) computes `let drained := ex.held.foldl (· + ·.size) 0` and checks `drained ≤ ex.config.drainBytes`. Even when `ex.parser.complete` is already `true` (zero unread bytes remain on the socket), if `drained > ex.config.drainBytes` (for instance when `drainBytes` is configured below `readChunkBytes`), `worthDraining` is `false` and `Exchange` drops a connection that already finished receiving the entire response.

#### 2. Remaining validation gaps in `Call.validate`
- **Location:** [`LeanHttp/Call/Trace.lean`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Call/Trace.lean)
- **Confidence:** **High** (Low-to-Medium impact: trace validator accepts certain malformed shell traces)

  1. **`Event.wait endsAt` logs the target timestamp *before* sleeping rather than the actual wake-up time ([`Client.lean:805-807`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Client.lean#L805-L807), [`Trace.lean:251-254`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Call/Trace.lean#L251-L254)):**

#### 3. In `Live.next`, `live.ex.uploadStopped` is `false` after an early response head until `writeBy` (`readGapMs`) expires, so a fast download still chains a continuation per read onto a stalled write
- **Location:** [`Body.lean:149-152`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L149-L152) (`Live.next`), [`Exchange.lean:597-600`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean#L597-L600) (`Exchange.stopUpload`), [`Exchange.lean:627-632`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean#L627-L632) (`Exchange.onHead`)
- **Confidence:** **High** (Low impact: bounded by `readGapMs`)
- **Mechanism:**
  The comment in [`Body.lean:149-152`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Body.lean#L149-L152) states:
  ```lean
  -- Once the upload has stopped (the response head arrived first), the core makes nothing of the
  -- write still in flight, which may never complete; it is left out of the race, since every race
  -- adds a continuation to each task in it, and a long download would pile them up on that write.
  let writing := if live.ex.uploadStopped then none else live.writing
  ```
  In [`Exchange.lean`](file:///tmp/lean-http-wire-review2/tree/LeanHttp/Exchange.lean), however, `onHead` sets `ex.early := true`, **not** `ex.uploadStopped := true`. `ex.uploadStopped` only becomes `true` when the in-flight write fails (`.writeFailed`) or when `ex.writeBy` expires after `readGapMs` (30 s by default, or 15 min for slow APIs). During that first `readGapMs` window after an early response head arrives, `live.ex.uploadStopped` remains `false`, so every read of the response body still includes the stalled `live.writing` task in `awaitFirst` (and `ex.readBy` is not armed until `writeBy` expires and calls `stopUpload`).
