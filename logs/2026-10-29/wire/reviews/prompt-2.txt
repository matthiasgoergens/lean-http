The brief of the first round is below, unchanged; the first round's two reviews are claude-review-1.txt and gemini-review-1.txt in this directory. What became of the first round's findings (C = the Claude review, G = the Gemini review):

Fixed:
- C1 (408 re-dispatch then a refused connect said notSent): Attempt.run now raises Progress.furthest by the first exchange before sending again; net scenario redispatch-408.
- C2 / G2 (a read in another task outlives the callback): BodyStream.State.busy carries the socket and a promise; release cancels the pending receive and waits for that read to end; the drive loop checks for release after performing actions and before every wait; finishRead drops the connection.  Net scenario stream-race.
- C3 (re-dispatch invisible to validate): new event Call.Event.redispatch, checked against Client.redispatch? (moved to LeanHttp/Wire.lean so Trace can import it), at most one per request, on a reused connection, and a closedBeforeResponse re-dispatch followed by a failure reported notSent is rejected.
- C4 (the head check compared the planner's head with itself): the send event now carries the origin the client connected to and the encoded head; validate recomputes both from State.current with Client.plan (moved to Wire.lean) and Codec.encodeRequest.  The module doc says plainly that the record is the client's own account.
- C5 / G5 (error delivery, hops, retries unchecked; any invalidRequest accepted after a redirect): checked now; the refusal is accepted only when Client.plan refuses the planner's request.
- C6 / G5.4 (no bound on retry waits): new event wait, which must equal min (decision time + delay) deadline exactly, and the next send must come no earlier.
- C7 (stale live in catch): the catches cancel through the socket unconditionally.
- C8 / G12.1 (wall clock throwing while a connection is held): caught, falling back to 0.
- C9 / G14 (unreachable branch leaking): the branch drops the connection.
- C10 (escaped stream keeps the socket): settle is an IO.Ref emptied on first use.
- C11 (continuations pile up on a stalled write): Live.next leaves the write out of the race once the upload stopped.  The case of a read pending through a long upload (one continuation per write slice) is left, bounded by the number of slices.
- C12 / G1 (the stream could hold more than one read; credit max left a read and readBy armed between reads): read gives credit 1 when the core has none, so the core delivers what it holds or reads once and then holds nothing more.
- C14 (dead connect round counts): removed; each round resolving the name again is now documented as a decision (as Go's dialer does per dial).
- C16 (docstrings): fixed.
- G3.3 (body bytes held with the head lost when the exchange failed in the same read): BodyStream.new now keeps live.ex.held as pending; net scenario stream-badchunk, which fails without the fix (checked).
- G6 (read released busy between advance and take): read now takes from what advance returned before leaving busy.
- G7 (a name lookup cut by the deadline counted as a connect round with "could not connect: "): no round counted, its own detail.
- G9 (408 drained before being dropped): cancelled and dropped.
- G10 (https refusal with an empty target and the previous hop's reused flags): fixed.
- G11 (written := 0 on tooManyRedirects): the exchange's count.

Refuted or kept, with the reason:
- G3.1, G3.2, G3.4 (a head and a body failure in the same read reported to the planner as a response; withResponse returning ok when the callback never reads a failed body; the trace ending at deliver when the body then fails): deliberate.  The planner decides on the head, before the body; were a failure in the same read reported as a failure, the outcome would depend on how TCP cut the bytes (a later read gives the head first either way).  A body error surfaces in the read that meets it.
- G4 (request's maxBodyBytes applies to the bodies of redirects and retried responses, so with maxBodyBytes below the drain limit such a body costs its connection): true; it only loses a connection, and only when maxBodyBytes is set below 64 KiB.  Recorded as a known limit.
- G5.3 (causeMatches rejects multi-round connect failures because of a check all.size ≤ last.size): there is no such check; the suffix comparison accepts a call refused in three rounds (net scenario refused-backoff checks its trace).
- G8 (a connection given back after an exchange that timed out before writing gets a new idle time): the pool's behaviour from before this change, kept; the idle check still runs before reuse.
- G12.2 (osSeed throwing makes withResponse throw; request then reports maybeDelivered): withResponse does not promise never to throw; request's catch-all is deliberately conservative.
- G13 (timers up to 1 ms early in Connect.round and acquire): from before this change; the effect is a failure 1 ms before the deadline.
- C13 (Redispatch.notSent unreachable), C15 (small accumulations): kept, documented.

The first round's brief:

Review a change to lean-http, an HTTP/1.1 client library for Lean 4 (v4.34.1).  Read only: do not edit, build or run anything.  Report defects, with file:line, a confidence (high / medium / low) and the concrete scenario that triggers each.  Guilty until proven innocent: assume there are bugs.

The change wires a pure per-call planner (`LeanHttp/Call.lean`: `Call.start`, `Call.plan`, proved in `LeanHttp/Call/Proofs.lean`, not under review) into the client shell, and adds a streaming API.  Files under review (the whole tree is there for context):

- `LeanHttp/Client.lean`: `CallSpec.loop` (the driver of the planner), `Attempt.run` / `acquire` / `connect` (the pool and the re-dispatch of an exchange whose pooled connection turned out closed), `run`, `withResponse`, `request`.
- `LeanHttp/Body.lean` (new): `Live` (an exchange in progress on a socket: drives the pure exchange core `LeanHttp/Exchange.lean`), `BodyStream` (the body the caller pulls inside the callback of `withResponse`).
- `LeanHttp/Call/Trace.lean` (new): `Call.Event` and `Call.validate`, which replays a record of what the shell did through the planner and checks the shell did what the planner said.
- `LeanHttp/Connect.lean` (now one round of connect attempts per call; the planner owns retries and backoff), `LeanHttp/Config.lean`, `LeanHttp/Error.lean`.
- Tests: `Tests/Net.lean` (driver), `tests/net/run.sh` (real-socket scenarios), `tests/net/evil.py`, `Tests/Unit.lean`.

The diff against the base is `wire.diff` (it does not show the two new files, read them in `tree/`).  `tree/DESIGN.md` and `tree/NOTES.md` give the design and the decisions so far (they are not yet updated for this change).

Things the shell must guarantee; try to break each:

1. The shell is a thin driver of the planner: each request it sends is the planner's `State.current` (with the body its `HopBody` says), it reports how each exchange ended truthfully (the final response head before its body is read, or the exchange's `Failure`), it waits a retry's delay from the time the planner decided and never past the deadline, and it delivers or fails exactly as the step says.  `Call.validate` should reject any trace where it does not; can it be fooled (a shell bug it would accept)?
2. A response that is followed or retried has its body drained within the drain limit (connection kept) or its connection dropped, before the next request.
3. Every connection a call takes from the pool is given back or dropped exactly once, on every path (failures, exceptions, the 408 re-dispatch, the callback raising, the stream used after the callback or from another task).
4. No receive registration (a pending `recv?`) outlives the callback of `withResponse`, nor a call of `request`: on v4.34.1 a pending receive can keep the process from exiting.
5. Streaming: each `read` gives the exchange core credit; what the shell holds never exceeds one read; leaving the callback normally or by an exception abandons the rest (drained or dropped, never pooled unless the core says it is reusable); using the stream after the callback raises an error.  An error the stream raised that leaves the callback becomes the call's `Error`; any other exception is raised again.
6. `Error.delivery` must never say `notSent` when any request of the call may have reached a server (retries, redirects, re-dispatch).
7. A POST (or any request that is not idempotent with a replayable body) is never sent again once a byte of it may have reached the server, except after a 408 on a reused connection (which says the server did not process it).
8. Values carried across an asynchronous wait are never updated in place by the runtime (they are shared between threads), so nothing may grow across waits by appending (`NOTES.md`, "Nothing carried across a wait is updated in place").

Also look for: races between the callback ending and a read in another task; anything that can make a call hang or exceed its deadline; misleading docstrings; dead code; complexity that buys nothing.  Keep every informed concern, with its confidence.
