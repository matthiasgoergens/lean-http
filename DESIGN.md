# lean-http: design

An HTTP/1.1 client for Lean 4 (v4.34.1), built so that its decisions can be tested exhaustively and, where it pays, proved.  It uses `Std.Http`'s data types as shipped in the toolchain and a codec of its own: a response parser written for proof and a small request serialiser (`LeanHttp.Codec`).  The HTTP/1.1 machine of the proposed upstream client stack (a renamed copy of its protocol layer; see `NOTES.md`) is not part of the library: the tests and the fuzzer use it as the oracle the codec is compared with.  Of that client, what the library replaces besides the codec is the part that went wrong: connection management.

## Position

lean-http is a library of its own, a Lake package that depends only on what ships in the toolchain.  An HTTP client does not belong in the standard library: it needs to release on its own schedule, carry its own codec, TLS and policy, and change faster than `Std` can (Matthias, 2026-10-28).

It started from a review of the client proposed for `Std.Http` (leanprover/lean4 #14546-#14548), which held up well where its tests were thorough (parsing, framing, limits, redirect rewriting) and failed in its connection loop and pool (`~/prog/lean-speed/notes/http-client-review.md`).  The review and fixes for most of those defects were offered upstream (leanprover/lean4#14548, review 5665985837), independently of this library.  Two aims shape the design:

1. **A client to use now**, from code pinned to v4.34.1, in place of running `curl` as a subprocess.
2. **A connection layer whose decisions live in pure functions**, so that the properties the review showed matter ("no response without a request in flight", "close never causes a resend", "retiring never aborts the exchange in flight") can be checked on every interleaving and proved.

## Milestone 1: the smallest useful client

- One connection per request, `Connection: close`.  No pool, no reuse, so none of the stale-connection, idle-bytes or unread-body hazards can arise.
- `Client.request : Request ByteArray → Async (Except Error (Response ByteArray))`, with a throwing variant.  The body is read whole, up to a limit.
- The calling task does everything: DNS, connect, and then the exchange, whose writes and reads it performs for the exchange core, at most one of each in flight, racing them against the core's next deadline.  Other tasks exist only for those operations and the timers.
- DNS answers de-duplicated and interleaved by family; addresses tried with a per-attempt connect timeout and a short stagger between attempts; IPv6 literals bypass DNS; `TCP_NODELAY` on.
- Retries only of connects that failed, with exponential backoff and full jitter seeded from the operating system (the seed is logged so a run can be replayed), within a retry budget.
- One deadline for the whole call; a per-gap read timeout on top; a cap on interim (1xx) responses.
- No redirect following yet.

This is all a service needs that POSTs JSON to a plain-HTTP API with long timeouts, and it is small enough to review in one sitting.

## Milestone 2: pooling, redirects, streaming

Built: the pool, the per-call planner and its wiring into the client, and streamed response bodies.

### The caller drives its connection

Following httpcore (Python) rather than a task per connection: the task that makes a request owns the connection for the duration of the exchange.  An idle connection in the pool is a socket with no task attached and no operation pending.  When a connection is taken from the pool, it is first checked for bytes, end of input or an error that arrived while it was idle, and discarded if there are any; httpcore, urllib3 and curl do the same.  The check is a `waitReadable` bounded by a short timer (`Config.idleCheckMs`, default 0 ms), then `cancelRecv`, so that no receive is left pending: `recvSelector`'s non-blocking check misses most of what has arrived, because it looks before the event loop has polled the socket, whereas even a timer of 0 ms fires only after the loop has polled it once (`NOTES.md`).  This removes the race between a background loop and the caller's body stream, and with it most of the machinery the upstream loop needed.

A request that crosses the server's own close of an idle connection fails however careful the check.  The shell then sends it once more, on a fresh connection, when that is safe, without counting it against the planner's retries: when nothing of it was written; when the server answered 408 before any other response, which says it did not process the request (RFC 9110 section 15.5.9), whatever the method; and, for idempotent methods only, when the connection closed before any byte of a response, as Go's transport does.  A POST that may have reached the server is not sent again; its error says it may have been delivered.

### Two pure cores

1. **Pool core** (`LeanHttp.Pool`): which connections exist per origin, which are idle, which are checked out.  No timers and no I/O; connections are ids the pool allocates, and the shell keeps the sockets next to it; one mutex guards both, safely because every operation is a quick pure step and nothing waits while holding it.
   - `take` hands out the most recently returned idle connection of the origin, or a new id to connect under; `giveBack` takes a connection back with the exchange core's reuse verdict (reusable ones go idle, the rest are gone); `drop` lets a checked-out connection go (failed exchange, failed connect, failed idle check); `sweep` and `closeAll` let idle ones go.  Giving back or dropping a connection that is not checked out changes nothing.
   - Idle connections are capped per origin (default 4): a reusable connection that comes back to a full origin is closed, as Go and urllib3 do.  They expire after an idle timeout (default 4 s, below common server keep-alive timeouts), judged by the time passed to each operation, not by a timer.
   - Active connections are not capped by default.  With a cap, `take` refuses while the origin is at it, and the call waits, within its deadline, until a connection comes back.
   - `LeanHttp/Pool/Proofs.lean` proves, over every sequence of operations: every connection is idle, checked out or gone, and in only one of them; hand-outs and returns of a connection alternate, so each checkout ends in at most one `giveBack` or `drop`; a connection given back as not reusable, or dropped, is never handed out again; the caps hold; and `take` never hands out a connection that expired at the time it is given.
2. **Exchange core** (`LeanHttp.Exchange`): one request and response on one connection, as a pure step function over the response codec, `step : Exchange → ExchangeEvent → Exchange × Array ExchangeAction`, with `nextDeadline`.
   - Events: bytes read, end of input, bytes written (with a count), the caller asking for more body (with a size), a tick, the caller abandoning the response, a write or read failure.
   - Actions: write these bytes (one write in flight at a time), read up to this many bytes (or not now: the core says whether it wants input), deliver the response head, deliver body bytes, finish, fail with an error.
   - The codec delivers every body byte it is fed, so the core holds what the caller has not asked for, issues no read while it holds any, and hands everything it holds over once the caller asks for more: what it holds never exceeds one read, and a delivery exceeds the caller's request by at most that.
   - With pooling on (`Config.pool`, the default), requests say `Connection: keep-alive`; with it off, `Connection: close`, and every call has a connection of its own, as in milestone 1.
   - The core decides reuse at the end: the connection goes back to the pool only if the codec says the connection could carry another exchange (the response ended, framed with certainty, with nothing after it and before the end of input, and its heads allowed keep-alive), the caller has the whole body, and the request asked for keep-alive and was written in full.  A HEAD or 204/304 response followed by stray bytes, an early response to an unfinished upload, or a response whose body was abandoned all make the connection non-reusable; it is dropped, never pooled.  An early response is still read to its end and delivered.
   - No response can be due before the server has the request head, so the core asks for no read until the head has been written (bytes reported earlier anyway fail the exchange unparsed).  Bytes a server sent before it saw the request, such as a 408 on an idle connection, still wait in the socket and are read as the response; the idle check before reuse is what catches them.  From then on the core reads while the body is still going out, so an early response is heard even from a server that stops reading.  Once the request head is out, a failed write only stops the upload, since a response may already be waiting; once the final response head has arrived, so does a stalled one.  The read gap counts only once writing is over: a server is silent while it receives a request.
   - Errors carry a cause (`localClose`, `peerClosed`, `timeout`, `protocol`, `limit`) and the number of request bytes written.  "Nothing written" (no write ever issued: the bytes of a write in flight may already be on the wire) is the evidence that makes a retry safe for any method.  A 408 on a reused connection before any response byte counts as "nothing processed", as Go treats it.

A **per-call planner** (`LeanHttp.Call`) runs in the caller's task.  After each exchange it decides, as a pure function of the call's state, the time and the exchange's outcome (a response head, or a `Failure`), whether to deliver the response, follow a redirect with the next request, send the same request again after a delay, or fail.  This is the split Go makes between `Client` and `Transport`.

The client's loop is a thin driver of it (`Client.withResponse`, which `Client.request` uses):

- It starts the planner with the request, the kind of its body (none or bytes), the call's seed and its deadline, then sends the planner's current request: it takes a connection from the pool for the request's origin (or opens one, with one round of connect attempts, since the planner now owns retries and backoff), and drives the exchange until the final response head arrives or the exchange fails.
- It reports that outcome to the planner, before the response body is read, with the monotonic clock of the deadline and the wall clock (for a `Retry-After` date).  A failed connect is a failure with cause `connect` and nothing sent; name resolution, an invalid request, the deadline and a closed client are failures the planner never retries.  The pool's re-dispatch of an exchange whose pooled connection turned out closed happens below the planner: for it, that is one exchange.
- It does what the step says.  A response that is followed or retried has its body drained within the drain limit (the connection is kept) or its connection dropped, before the next request; a retry waits until the planner's delay has passed since it decided, never past the deadline; a delivered response is handed to the caller's callback; a failure becomes the call's `Error`.
- An `https` target, or a redirect to one, is refused with `invalidRequest` until the client has TLS.
- A call's `Error` says how far the call got (the furthest any of its requests got, so a call that followed a redirect or retried a request that may have arrived is never "not sent"), which hop failed, how many retries it made and why the planner did not retry.

Whether the loop really is that thin is checked, not proved: with `Config.observe` the client reports every step of a call (the start, each request as encoded and the origin it went to, each re-dispatch, each decision, each wait, the end), and `Call.validate` replays the record through a planner of its own and rejects any step, request, wait or error the planner did not call for (verification stage 4, below).  The record of a delivered call ends at the delivery; an error while the body is read comes after the planner's last step.  The record is the client's own account, so whether the outcomes it reports are the true ones is not checked by this.  The real-socket tests check every call they make this way.

- **Redirects** follow RFC 9110 section 15.4 with the Fetch standard's method rules: only 301, 302, 303, 307 and 308; 303 makes the request a GET (a HEAD stays a HEAD), 301 and 302 turn a POST into a GET, and every other case keeps the method, with its body, so a redirect that would have to send a streamed body again is delivered instead.  A method change drops the body and the content fields.  `Location` is resolved against the current URI, userinfo and fragment dropped, and only http and https are followed.  At most 10 redirects; one more fails the call with `tooManyRedirects` rather than delivering the last 3xx; there is no cycle detection keyed on URLs, since POST, 303, GET to the same URL is ordinary.
- **Origins** are compared by scheme, host and port, so https to http changes the origin.  Credential fields (`Authorization`, `Cookie`, `Proxy-Authorization`) go only to the origin of the call's first request: dropped on a hop to any other origin and given back on a hop that returns to it.  Go's client also judges each hop against the first request, but by host alone, with subdomains allowed.  A hop to another origin also drops `Referer` and the cache validators and rewrites `Host`; hop-by-hop fields never carry over.
- **Retries** are per hop and never cross a redirect.  A failure where nothing was sent may be retried whatever the method; once a byte may have reached the server, only an idempotent method with a replayable body; a response head received, a `localClose`, the call's deadline, a name that did not resolve, an invalid request, a malformed response and a limit, never.  Every retry after a failure waits the full-jitter backoff (`LeanHttp.Backoff`, drawn from the call's seed and its retry number).  Retries of 429 and 503 are opt-in, for requests that could be retried after bytes were sent, and wait what `Retry-After` asks (seconds, or an HTTP-date measured from the response's `Date`), up to a limit, or the backoff without it.  No wait reaches the call's deadline: a retry that would have to wait until it is not made.  At most 2 retries per hop and 4 per call.
- **Proved** (`LeanHttp/Call/Proofs.lean`): credentials never reach another origin; the hop limit holds and reaching it is an error; nothing that is not idempotent or replayable is retried after a byte may have been sent; `localClose` is never retried; every delay ends before the deadline and within its cap; 303 yields GET (or HEAD); a method change leaves no body and no content field, on that hop and the ones after it; a redirect never sends a streamed body again; a redirect that is not followed is delivered; a hop to another origin drops `Referer` and the cache validators; the target always addresses the hop's origin, which is http or https.  **Tested** (`call-tests`, `call-diff`): each rule, random calls checked step by step with planted bugs as positive controls, and a differential test against the vendored and toolchain redirect planners and the upstream client's redirect loop, in which every disagreement is one of the deliberate differences `NOTES.md` lists.

### Streaming

`Client.withResponse : Client → Request ByteArray → (Response BodyStream → Async α) → Async (Except Error α)`.  Redirects and retries happen before the callback is entered: it sees only the final response.  The body is pulled by the caller (`BodyStream.read`, at most a given number of bytes, `none` at the end), so backpressure is natural: a read that finds nothing held gives the exchange core credit for one more read from the socket, so the core reads only as fast as the caller does, and the shell never holds more than one read.  A streamed body has no size limit, but the call's deadline covers reading it.

Leaving the callback, normally or by an exception, abandons whatever is unread: the rest is read and discarded if it is within the drain limit (64 KiB, arriving within 100 ms) and the connection kept, or else the connection is closed, never pooled.  Lean cannot stop the stream escaping its scope; using it afterwards raises an error, and the connection has been released regardless.  A read still in progress in another task when the callback ends has its receive cancelled and is waited for, so no receive outlives the callback.  An error the stream raised (the connection closed early, a timeout) that leaves the callback becomes the call's `Error`; any other exception from the callback is raised again once the connection is released.  Holding a body open inside the callback while doing other slow work keeps one connection busy, and nothing else.

`Client.request` makes the call the same way, with a body limit (`Config.maxBodyBytes`) and a callback that reads the whole body in one loop.

Request bodies: bytes (replayable) today; a stream (not replayable, so never retried once any of it is written) is not built yet.

## What `Std.Http` provides

From v4.34.1: `Request`, `Response`, `Headers` (with validated names and values, which rules out header injection), `Method`, `Status`, the URI parser (IPv6 literals included) and the head encoder the request serialiser uses.  Responses are parsed by the library's own codec, whose functions are all total so that its properties can be proved; the HTTP/1.1 machine's `H1.lean` has 18 `partial def`s in v4.34.1, which no theorem can unfold.  The upstream stack's protocol layer, vendored under `LeanHttpProto` for the tests (v4.34.1's machine rejects a chunk-size line with extensions or a trailer section that arrives split across reads, which the stack fixes; `NOTES.md`), is the codec's test oracle.  It also holds a pure redirect planner (`Protocol/H1/Redirect.lean`, in v4.34.1 too), which the per-call planner was to use; using it would bring the vendored layer back into the library, so the planner has one of its own, written against `Std.Http`'s types, and the two copies of the upstream one are its test oracles.

## Socket lifecycle

v4.34.1's TCP client socket has `shutdown` (closing the write side) but no explicit close; the descriptor is released when the last reference is dropped.  The design therefore keeps references to a socket in exactly two places, the exchange in progress and the pool entry, and drops both when the connection ends.  An exit test checks that a process with connections closed in each way (end of response, abandoned body, timeout, error) exits promptly: the review saw processes hang at exit after a body was closed unread.  A pending receive can be cancelled, but a pending connect, write or name lookup cannot, and each holds its socket (or a thread of libuv's pool) until it ends: losing connect attempts are therefore abandoned rather than cancelled, and their sockets close when the kernel gives up on them.  `NOTES.md` records what each of these costs, measured.

## TLS

`https` targets are reached over TLS, which is a transport under the shell: the exchange core, the codec, the planner and the pool core see plaintext bytes and connection ids, as before, and none of them changes.

### How TLS is obtained: a thin binding to the toolchain's own OpenSSL

Every Lean toolchain from v4.34.1 to v4.36.0-rc1 ships the same static OpenSSL 3.6.0 (`lib/libssl.a`, `lib/libcrypto.a`), and `leanc` already links every executable with `-lssl -lcrypto`.  What it does not ship is OpenSSL's headers.  The library therefore carries a small C file (`native/tls.c`) that drives OpenSSL, compiled by Lake with the toolchain's own compiler, and declares by hand the few OpenSSL 3 functions and constants it uses (`native/openssl-min.h`, about 45 of them) instead of including OpenSSL's headers.  OpenSSL keeps its ABI stable across a major version (3.0 to 3.6 and later 3.x), and the binding uses only functions present since 3.0.  Two checks guard the hand-written declarations:

- CI compiles a check file that includes both the real OpenSSL headers and the declarations, with warnings as errors: a prototype that differs is a "conflicting types" error, and every constant is compared with OpenSSL's by a static assertion.  It runs against Ubuntu's 3.0 headers and against 3.6.0's, generated from the release tarball (fetched and checked against its SHA-256, never committed).
- At run time, the first TLS connection checks that the OpenSSL linked in is of major version 3, and fails with a TLS setup error otherwise, so a future toolchain that moves to OpenSSL 4 is refused clearly rather than called through a stale ABI.

So a user needs nothing beyond the toolchain to build with HTTPS: no headers, no system OpenSSL, no network at build time.

Options rejected:

- **OpenSSL headers fetched at build time.**  OpenSSL 3's public headers are partly generated (`ssl.h`, `x509.h`, `opensslv.h` and others come from `.h.in` templates that `Configure` expands with Perl), so every user's build would need the network and Perl.  CI does this once, for the check only.
- **The system's OpenSSL through `pkg-config`.**  Users would have to install development headers, and those describe the system's OpenSSL (3.0 on Ubuntu 24.04), while the linker resolves `-lssl -lcrypto` against the toolchain's 3.6.0 first: headers of one library over the code of another.
- **Vendoring the stack proposed for `Std`** (leanprover/lean4 #14064, #14065, #14066, unmerged).  It is C++ written as part of the runtime (its external classes are registered when the runtime initialises), it would need OpenSSL's headers too, and its names would collide with `Std`'s once it merges.  On Linux it trusts OpenSSL's default certificate paths, which in the toolchain's OpenSSL point into a Nix store path that exists on no user's machine, so certificate verification fails out of the box.  Its choices of protocol settings are sound, and this design shares them: memory BIOs, TLS 1.2 at least, no renegotiation, no compression, no partial wildcards.
- **A TLS of our own in Lean.**  The cryptography, X.509 path validation and interoperability are years of work and an attack surface of their own.
- **Other TLS libraries.**  rustls through rustls-ffi is memory-safe and has a small C API, but would add a Rust toolchain to every user's build; it is the fallback should OpenSSL leave the toolchain.  mbedTLS could be vendored as C sources (no build dependency, about 100,000 lines) but brings its own X.509 code and a slower security cadence; BoringSSL needs CMake and Go and promises no stable API; libcurl is a whole HTTP stack, which this library replaces.
- **Blocking OpenSSL calls on dedicated threads**, as lean-grpc does (`SSL_read` on a socket descriptor).  A pending operation would hold a thread, could not be cancelled through libuv, and could outlive the call.

### How TLS fits the shell

- **Memory BIOs.**  OpenSSL never touches the socket.  The shell feeds it the ciphertext the TCP socket received and sends the ciphertext it produces with the TCP socket's own asynchronous operations.  Every OpenSSL call returns at once (it either has the bytes it needs or says it wants more), so no thread ever blocks in TLS, and every wait is a wait on a TCP operation or a timer, as before.
- **A transport in the shell.**  `LeanHttp.Transport` is a TCP socket or a TLS connection over one, with the operations the shell uses: send, receive at most n bytes (`none` at a clean end of input), cancel the pending receive, the idle check, and release.  `Live`, the body stream, the pool's idle table and the client hold a transport where they held a socket.
- **One write and one read in flight, and the order of ciphertext.**  The exchange core may have a write and a read in flight at once, and their continuations may run on different threads.  Each TLS connection has a mutex held, briefly, around every OpenSSL call together with taking the ciphertext it produced and handing it to the TCP socket (`send` only queues a libuv write, in order), so ciphertext goes out in the order OpenSSL produced it whichever path produced it: a request write, or a reply that reading required (a TLS 1.3 key update).  The C side has its own mutex per session as well, so that no misuse from Lean can race OpenSSL.
- **No receive outlives a call.**  One plaintext receive may need several TCP receives: a record split over reads, or post-handshake messages such as session tickets before the response.  Each TCP receive is registered under the connection's mutex, after checking that the plaintext receive it serves has not been cancelled; `cancelRecv` marks it cancelled and cancels the TCP receive under the same mutex.  A cancel can therefore never be followed by a fresh registration, and the rule the exit-hang notes impose (no receive registration outlives a call) holds for TLS as it does for TCP.
- **The handshake** runs after the round of connect attempts has picked a socket and before the exchange, within `Config.tlsHandshakeTimeoutMs` (default 10 s) and the call's deadline; on time-out its receive is cancelled.  The TCP connect timeout and the stagger are unchanged and cover TCP only.
- **A clean close and a truncated one.**  The end of TCP input is passed to OpenSSL as such.  After the server's `close_notify` the transport reports a clean end of input; an end of input without it, or a reset, fails the receive as truncated, which the exchange core sees as a failed read.  A body framed by `Content-Length` or chunked coding that was complete is unaffected, since the exchange finished before reading further; a body delimited by the close, the case RFC 9112 section 9.8 warns about, fails instead of being delivered short.  There is no option to accept a truncated close.
- **The idle check** knows TLS: a connection with plaintext held in OpenSSL or the server's `close_notify` received is unclean; otherwise it waits for readability as the TCP check does, and if bytes arrived it reads them once and lets OpenSSL process them: records that carry only handshake messages (a session ticket sent late) leave the connection clean, anything else (application data, an alert, the end of input) makes it unclean.  No receive is pending when it returns.
- **Release.**  A connection the shell lets go after a clean exchange (a response with `Connection: close`, an idle connection that expired or did not fit the pool, a closed client) sends `close_notify`, best effort: one small write that nothing waits for, which a socket no longer referenced completes or abandons like any other write.  A connection that failed is dropped without it.

### Certificates and the protocol

- **Verification is on, and there is no switch to turn it off.**  A server with a private or self-signed certificate is reached by giving its CA certificate.
- **Trust.**  `Config.tls.caFile`, a PEM bundle, replaces the system's trust store when given.  Otherwise the client honours `SSL_CERT_FILE` and `SSL_CERT_DIR`, as OpenSSL does, and failing those uses the first bundle file or directory that exists among the well-known locations Go's `crypto/x509` probes (Debian and Ubuntu's `/etc/ssl/certs/ca-certificates.crt`, Fedora and RHEL's `/etc/pki/tls/certs/ca-bundle.crt` and `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem`, openSUSE's `/etc/ssl/ca-bundle.pem`, Alpine's and macOS's `/etc/ssl/cert.pem`, and the directories `/etc/ssl/certs` and `/etc/pki/tls/certs`).  Never OpenSSL's compiled-in default, the Nix store path.  If none exists, the call fails with a TLS setup error that names the setting and the variables.  The context, with its loaded trust store, is created by the client's first `https` call and kept.
- **The server's name.**  For a host name, the certificate must match it (`SSL_set1_host`, partial wildcards such as `f*.example.com` refused, as RFC 6125 section 6.4.3 says), and SNI carries it; for an IP literal, the certificate must carry the address (`X509_VERIFY_PARAM_set1_ip_asc`), and no SNI is sent, since RFC 6066 section 3 forbids literals there.  A trailing dot is removed from the name for both.
- **Protocol.**  TLS 1.2 at least (RFC 8996 deprecates 1.0 and 1.1), TLS 1.3 when the server has it; renegotiation and compression off; ALPN offers `http/1.1` only, and a server that selects anything else is refused.  No session resumption: the pool keeps connections open for reuse, and a resumed session is a cache whose keys and lifetimes would need a design of their own.
- **Pooling.**  The pool's origin key is `scheme://host:port` (as is every error's `target`), so a TLS connection and a plain one are never exchanged for each other, even to the same host and port.
- **Redirects.**  The planner already follows a redirect from `https` to `http`, as browsers and curl do, and drops the credential fields on it, since the origin changes; `Location` targets of either scheme are now reached.

### Errors

A TLS failure before any request byte is written is a new cause, `Cause.tls`, with delivery `notSent`, whose kind says what failed: `setup` (no trust store found, a CA file that cannot be read, an OpenSSL that is not version 3), `verify` (the certificate chain or the name, with OpenSSL's reason, such as "certificate has expired" or "hostname mismatch"), `handshake` (an alert or a protocol failure, such as no common protocol version), `closed` (the connection closed or was reset during the handshake) and `timeout` (the handshake did not finish in time).  The per-call planner retries `closed` and `timeout`, like a failed connect, and never the other three, which another attempt would only repeat.  A truncated close after the handshake is a failed read, so the call fails as a closed connection (`peerClosed`), with a detail that says the TLS connection was truncated: the exchange core's failure for a failed read, unchanged.

## Defaults

`TCP_NODELAY` on; connect timeout 10 s per attempt, with a 250 ms stagger between attempts; whole-call deadline 5 minutes, which alone bounds name resolution and covers reading a streamed body; read gap 30 s, which also bounds each 64 KiB slice of a request write; at most 10 interim responses; buffered body limit 64 MiB (a streamed body has none); up to 2 retries per hop and 4 per call (full jitter, base 100 ms, cap 5 s); 429 and 503 not retried unless asked for, and a `Retry-After` honoured up to 60 s; pooling on, with idle connections: 4 per origin, 4 s, checked for 0 ms (one turn of the event loop) before reuse, and no cap on active connections; an abandoned body is drained for reuse if the rest is at most 64 KiB and arrives within 100 ms; at most 10 redirects, then an error.  Slow upstream APIs (model calls that think for minutes before answering) need the deadline and the read gap raised; the defaults suit ordinary web APIs.

## Verification

In order of value per effort; each stage stands alone.

1. **Known defects as traces** against the exchange and pool cores (the review's defects plus the survey's cases: early response during an upload, stray bytes after HEAD).
2. **Properties at every step** on random event sequences (seeded generator; Plausible where it fits), shrinking failures:
   - no response head is delivered before the request head has been written (an early response may arrive while the body is still going out);
   - an error with cause `localClose` is never retried;
   - a connection returns to the pool only if its exchange ended with certain framing and fully read;
   - every checked-out connection is returned or dropped exactly once;
   - after the deadline, the call has ended.
3. **Bounded exhaustive exploration** of the pool core with several concurrent calls, and of the exchange core over a small alphabet, to a depth around 10.
4. **Trace validation**: record the events and actions of real-socket runs and replay them through the cores, checking that the shell did what the cores said.  Built for the per-call planner (`Call.validate` over the record `Config.observe` gives); the exchange and pool cores are not yet recorded.
5. **Fuzzing** the exchange core, with the codec inside it, under AFL++ (persistent mode through a small C entry point; assertions abort under `LEAN_ABORT_ON_PANIC=1`): response bytes split at fuzzer-chosen points, with split invariance and a check of the reuse decision, and the vendored machine driven directly as its differential oracle.  h11 as a differential oracle for the machine's framing.
6. **Ported cases** from curl, Go, hyper-util, OkHttp and h11 (`~/prog/lean-speed/notes/http-client-prior-art-tests.md`).
7. **Proofs** of the single-step properties (cheap, once the cores have the right types: cause-typed errors, an in-flight token), the pool invariant ("returned or dropped exactly once") and liveness under the deadline.  Veil only if the plain explorer cannot settle an invariant.
8. **Real-socket tests** on loopback for `TCP_NODELAY`, connect timeouts per address, IPv6 literals, idle connections closed by the server, and prompt exit.

## From fuzzed properties to proved ones

Every property the fuzzer or the random runs check should end up as a theorem, with fuzzing kept as the cheap first line (Matthias, 2026-10-28).  Most of the exchange core's properties hold whatever the response parser returns, so they are proved about `Exchange.step` directly, treating the parser as opaque.  `LeanHttp/Exchange/Proofs.lean` and `LeanHttp/Exchange/Liveness.lean` do so for the single-step properties, for "a live exchange has a deadline ahead", and for liveness under the deadline; liveness assumes only that the shell, whenever the exchange is live, eventually reports an event at or after its next deadline, which a shell that sleeps until that deadline and then ticks does, as long as its sleep returns.  The codec's properties (termination, body length within `Content-Length`, no body after HEAD, 204 or 304, split invariance, the response delivered being the response received) are proved about the codec itself (`LeanHttp/Codec/Proofs/`), with the vendored machine as its differential oracle (`codec-diff`, the fuzzer).  `LeanHttp/Exchange/Response.lean` joins the two: in every run of the core, its parser is the codec's run over the bytes received, so a finish proves that those bytes held a complete response, and a reusable finish that they held exactly one, whose body is the body delivered.

## Not yet
