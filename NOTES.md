# Notes

## The HTTP/1.1 codec: a vendored copy of the upstream protocol layer

Decided on 2026-10-27, by measurement.  Since 2026-10-28 the library no longer uses this copy: the exchange core parses responses with its own codec and encodes requests itself ("The codec inside the exchange core", below), and the copy is the oracle of the tests and the fuzzing harness only.

`DESIGN.md` planned to use the HTTP/1.1 machine that v4.34.1 ships (`Std.Http.Protocol.H1.Machine`, client direction).  Nothing in v4.34.1 drives that direction (the server uses only `.receiving`), so `Tests/Codec.lean` drives it through the exchange core over 37 response shapes, each fed whole, one byte at a time and split in two at every position.

Against the v4.34.1 machine, 31 of the 34 cases with an expected outcome pass (Content-Length, chunked, close-delimited, HEAD, 204 and 304 with framing fields, interim responses, malformed status lines, header and body limits, end of input at every stage).  Three fail, all the same way: when a chunk-size line with extensions, or a trailer section, arrives split across two reads, the response is rejected as a bad message (`logs/2026-10-27/codec-v4.34.1/out.txt`).  The cause is `manyItems` in `Protocol/H1/Parser.lean`: it wraps each item in `optional (attempt ...)`, which turns "ran out of input" into "no more items", and the parser then fails hard on the half-received item instead of asking for more bytes.  TCP may segment a response anywhere, so this is a spurious failure in real use, rare only because extensions and trailers are rare.

The upstream client stack (leanprover/lean4 PRs 14546-14548, head 3e6f42a58a955f7fd9a6df4213f3be4bb68e3e3b) fixes exactly this (`optionalItem`), and changes the machine's client direction in a few other ways this client benefits from: `101 Switching Protocols` is no longer treated as an interim response, the end of an interim response's body is not reported as the end of the body, and a request without content gets no `Content-Length: 0`.  With that protocol layer vendored, all 37 cases pass, and the request encodings are checked as well (`logs/2026-10-27/codec-vendored/out.txt`).

So the library uses a copy of the stack's `src/Std/Http/Protocol`, renamed to `LeanHttpProto.Http.Protocol`, generated into the ignored `vendor/` by `scripts/vendor.sh` from a lean4 clone at that commit; `vendor/SOURCE` records the commit.  Two choices differ from a whole-tree copy:

- **Only the protocol layer is copied, not `Data` and `Internal`.**  `Internal` is unchanged in the stack, and its `Data` changes are additive helpers, of which the protocol layer needs two (`Status.isInterim`, `Method.anticipatesContent`); `LeanHttp/VendorCompat.lean` supplies them.  Copying `Data` would fork `Request`, `Response` and `Headers`, and the client's API would no longer speak `Std.Http`'s types, which `DESIGN.md` relies on for moving code between this client, `Std.Http.Server` and a future `Std` client.
- **The copy is a separate Lake library** (`LeanHttpProto`, source directory `vendor/`), with the toolchain's default options; the client's own library builds with `autoImplicit` off.

The exchange core over this machine (now `Tests/Support/MachineCore.lean`) refused `101` itself and counted interim responses itself, since neither version of the machine limits them.  The copy can go, with `scripts/vendor.sh`, `LeanHttp/VendorCompat.lean` and the oracle core, once the tests no longer need the machine to compare with; a toolchain that ships these protocol changes would let the oracle point at `Std.Http.Protocol` instead.

The three informational cases record behaviour without asserting it: a status line without the space before an empty reason phrase, bare LF line endings and obsolete line folding are all rejected as bad messages, by both versions.

## A response parser written for proof

Built on 2026-10-28; the exchange core parses every response with it ("The codec inside the exchange core", below).  `LeanHttp/Codec/` parses an HTTP/1.1 response in the client direction, given the request method, and every function in it is total.  `Parser.stepByte` reads one byte with no loop and is the meaning of the parser; `Parser.feed` reads body bytes in bulk, slicing them out of its input, and is proved to compute the same (`feed_eq_run`).  `LeanHttp/Codec/Proofs.lean` lists what is proved, and `scripts/codec-axioms.lean` prints the axioms of the main theorems, which use `propext`, `Classical.choice` and `Quot.sound` at most.

Its rules and limits are those of the vendored machine, with the exchange core's interim limit, `101` refusal, body limit and refusal of a transfer coding other than chunked built in, except in these deliberate differences, each of which the differential test below finds and attributes:

- A chunk whose size line announces more than the body limit leaves is rejected at its size line.  The core rejects it only once the data arrives, so its outcome then depends on what the data holds and on how the bytes are cut: a bad message, still pending, a premature close, or the body limit.
- A chunk-size line longer than its limit is rejected at the byte that exceeds it.  The vendored machine measures an incomplete line only up to its last complete extension, and keeps waiting.
- Chunk extensions are counted at each `;`, so one too many is refused when its `;` arrives rather than when it is complete.
- `Connection: close` ends the connection whatever the version (RFC 9112 section 9.3).  The vendored machine looks for `close` only in HTTP/1.1, so it keeps an HTTP/1.0 connection whose response says both `keep-alive` and `close`.
- There is no `maxStartLineLength`: a status line is bounded by the reason-phrase limit, 527 bytes with the defaults, well inside the machine's default of 8192.

Measured on the build host (`logs/2026-10-28/codec/final/`, commit c94d1e6):

- The 37 response shapes of `Tests/Codec.lean` pass, each fed whole, byte by byte and split in two at every position (`response-codec-tests`).
- `codec-diff` ran 120,037 inputs for each of four seeds: the shapes, responses generated with deliberate faults, and mutations of both, with GET, HEAD or POST and default or partly small limits, each run whole and cut at random points, without and with the end of input.  Every disagreement with the core falls under one of the differences above (the tool finds the cause by relaxing one limit at a time until the two agree), and the codec's outcome never depended on the cut.  The core's did, on 43 inputs, all with a chunk beyond the body limit.  A control run with the codec's limits off by one shows the comparison sees disagreements.
- Parsing a 60 MB body fed in 64 KiB reads, the codec took 0.94 times the core's time for a `Content-Length` body, 0.93 with 16 KiB chunks and 0.75 with 1 KiB chunks (median per-block ratios over 100 randomised blocks on one pinned CPU of a loaded machine; the codec was faster in 60, 61 and 100 of the 100 blocks).  Body bytes are slices of the bytes fed, so nothing carried across calls grows with the body.

Left open:

- Completeness is not proved: no theorem says that a well-formed response within the limits is accepted.  The shape tests and the differential run are the evidence that it is.
- The interim heads' `Connection` fields enter the keep-alive verdict, but no theorem ties that to the bytes.
- CONNECT and protocol upgrades are not handled; the client sends neither.

## The codec inside the exchange core

Done on 2026-10-28 (`logs/2026-10-28/integrate/`, with `COMMAND` listing every run).  The exchange core feeds every byte read once the request head is written to `Codec.Parser`, and acts on its events: the head is delivered, body bytes are delivered as far as the caller has asked for them, and a rejection fails the exchange with the cause the core reported over the machine (`Exchange.causeOf`).  Requests are encoded by the client's own serialiser, so the library no longer depends on the vendored copy; the core over the machine is kept, unchanged, as a test oracle (`Tests/Support/MachineCore.lean`).

Decisions, and why:

- **Requests: a serialiser of our own** (`Codec.encodeRequest`).  What the client sends is small (a head, a `Content-Length` for the body or none for an empty body whose method does not anticipate content, `Connection: close` unless the connection is to be kept alive), and `Std.Http` encodes heads.  Keeping the vendored writer would have left the whole vendored layer in the library for that alone.  It changes the head's fields in the order the machine's writer did and decides the request's own keep-alive the way the machine did (no `close` in HTTP/1.1, a `keep-alive` option in HTTP/1.0), so its bytes are the machine's: `codec-diff` encodes 6,000 generated heads per seed with both (methods, versions, `Connection`, framing and other fields, empty and non-empty bodies, keep-alive on and off) and found no difference in bytes, head length or keep-alive, and `codec-tests` checks eight encodings exactly.  The machine never refused a head the client prepares (it refused only framing fields that contradict the body, which `prepare` removes), so `prepare` now cannot fail.
- **Body credit.**  The codec delivers every body byte it is fed, so the core holds what the caller has not asked for (`Exchange.held`) and issues no read while it holds any; what it holds is therefore never more than one read, and a feed replaces it rather than growing it across waits ("Nothing carried across a wait is updated in place", below).  Once the caller asks for more, everything held goes out at once.  Releasing one piece per request instead held bytes back that the machine would have handed over, as one buffered chunk, and a later abandon then found more held than the drain limit: the comparison of random runs below found that, and the change.
- **Reuse.**  The verdict is the codec's `Parser.reusable` (the response ended, framed with certainty, nothing after it, the input not ended, the keep-alive verdict of its heads) and the core's own conditions: keep-alive asked for and allowed by the request head, the request written in full before the response head, the whole body handed over, the peer not closed.

What the proofs now cover.  The theorems of `LeanHttp/Exchange/Proofs.lean` and `Liveness.lean` keep their statements, except that `Reusable`, which `step_finish_reusable` concludes, names the codec's verdict and the empty hold instead of the machine's keep-alive, framing, end of body and leftover input; their proofs treat the parser as opaque, as they did the machine.  `LeanHttp/Exchange/Response.lean` adds what the machine's opacity ruled out, in the terms of the checker's model (which now records the bytes received, the body delivered and the abandonment): in every run, until the exchange fails, the core's parser is the codec's run over the bytes received (`Observed.cinv`); a reusable finish means those bytes are exactly one response, interim heads, the head and a body of the kind its framing declares, with nothing after it, and the body delivered is that body's payload unless the caller abandoned it (`observed_finish_codec`); any finish the caller did not abandon comes after a complete response whose body was delivered whole (`observed_finish_complete`); and the body delivered is always a prefix of what the codec decoded (`observed_body_prefix`).  These are relative to the codec's reading of the bytes, which `Codec.response_sound`, `Codec.head_sound` and `Codec.HeadOK` tie to the bytes themselves.  `scripts/proof-axioms.lean` prints the 41 exchange theorems' axioms (as of `integrate` 25fb963): `propext`, `Classical.choice` and `Quot.sound`.

Behaviour against the core over the machine:

- The 41 response shapes of `codec-tests` give the same outcomes in every split, and the unit, trace and real-socket suites pass unchanged (76 checks, the one known limitation of `dns-timeout` as before).
- `codec-diff` compares the codec with the machine core exactly as it compared it with the core before, and finds the same classes with the same counts on the same seeds; the core and the codec alone agree on every input, whole and cut, open and at end of input (the reuse verdict compared over the whole input without end of input, where both see the same bytes).
- `core-tests compare` replays 200,000 random runs per seed on both cores: 198,315 and 198,368 end the same way (seeds 1 and 2), and every other run is attributed by lifting the smallest set of limits that makes the two agree.  About three quarters come from the body limit: the codec refuses a chunk announced beyond it at its size line, and a body over it as its bytes arrive, where the machine core refused either only once the caller pulled the bytes.  About a fifth come from the caller's credit: the core hands over everything held, the machine core one machine chunk per request.  The rest come from chunk data, which the codec delivers (and counts against the drain limit) as it arrives, where the machine waited for the chunk's terminator when the data came in one read.
- The random runs of `props` and the states of `explore` change in number, since the generator's choices follow the core's actions and the explorer's states are told apart by a fingerprint that now reads the parser instead of the machine; every property holds.

Fuzzing.  The harness drives the new core and keeps its direct driver of the machine as the oracle, started from the machine the oracle core encoded the request with (which must make the core's bytes).  The cross-check allows the codec's deliberate differences listed above, each attributed by running the codec alone with one limit lifted, and `fuzz-replay --allowances` counts which inputs rely on which.  The core is now required to be split-invariant outright, body limit included.  All 21,787 inputs of the earlier campaigns (the seeds, the 16,703 distinct inputs of the first campaigns, the 795 of `afl-cmin` and the 4,233 queue entries of the last one) pass; 454 rely on the allowance for a chunk announced beyond the body limit and 18 on the one for a chunk-size line measured more strictly.  The instrumented build covers the codec (every object carries AFL++'s guards; the map has 124,596 edges).  As a positive control, a Content-Length body ending one byte early when a read leaves one byte of it, planted in a copy of the codec on the build host, was found in 34 s.  A ten-minute campaign on one pinned CPU, from the `afl-cmin` set, ran 890,000 executions and found no crash and no hang.

Performance.  Parsing a 60 MB body fed in 64 KiB reads, driven as `Client.request` drives the core, the core took 0.95 times the former core's time for a `Content-Length` body (95% interval 0.90 to 0.98), 0.81 with 16 KiB chunks and 0.66 with 1 KiB chunks (median per-block ratios over 100 randomised blocks on one pinned CPU of the loaded build host; `codec-bench`, both cores in one binary).  Against main's own binary, in 40 alternating blocks, the ratios were 0.92, 0.85 and 0.76, and the oracle copy of the former core ran as fast as main's (1.00, 1.07 and 1.04).

Left open:

- The request head's length is measured by the serialiser; the checker finds it independently, as the first blank line, and no theorem says the two agree (it depends on `Std.Http`'s encoding of validated fields).
- A delivery can exceed what the caller asked for by up to one read.  A streaming body that wants exact backpressure would have to split the held pieces.
- The interim heads' part in the keep-alive verdict rests on the codec's code, not a theorem.
- The per-call planner of milestone 2 was to use the vendored redirect planner; that would bring the vendored layer back into the library, so it may need its own.

## What can outlive a call, and other limits of milestone 1

Measured on 2026-10-27 (`logs/2026-10-27/net/`); v4.34.1 can cancel a pending receive but not a pending connect, write or name lookup.

- **An abandoned connect attempt** keeps its socket until the kernel gives up on the SYN: about 127 s with Linux's default `tcp_syn_retries` of 6.  It holds no worker and does not delay exit (the blackhole scenarios exit within tens of milliseconds), and the tests see the descriptors released once the kernel gives up (with `tcp_syn_retries=2` to keep the run short).  A host whose first address drops SYNs therefore costs one descriptor per call for two minutes; at about 8 calls a second that reaches the common limit of 1024 descriptors.
- **A write the peer never accepts** keeps its socket while the peer keeps the connection open (zero-window probes can keep it alive indefinitely).  The call itself ends at the write gap or the deadline, or with an early response that completes, and exit is not delayed (`write-timeout`, `early-response`).
- **An abandoned name lookup** keeps running in libuv's thread pool (four threads by default) until the resolver gives up, and libuv joins that pool when the process exits: with a name server that never answers, the process waited 8 s at exit after a call that ended at its 2 s deadline (`dns-timeout`, reported as a known limitation).  Worse, when the lookup ends during exit the process often dies with a segmentation fault: 3 of 10 runs in `logs/2026-10-27/dns-exit/`, and 4 of 6 in an earlier unsaved batch.  The cause is not established; it looks like the runtime-shutdown race in which a libuv callback runs after Lean's task manager has been freed.  So the client bounds lookups only by the deadline and leaves the rest to the resolver's own timeouts (`/etc/resolv.conf`).
- **An early response during an upload is heard, unless a write fails first.**  Since the exchange core became a step function (2026-10-28), the response is read once the request head is written, while the body is still going out.  A server that answers 413 after the head and stops reading now gets its response delivered in about 24 ms of a 32 MB upload, where milestone 1 ended the call with a write timeout at the 1 s gap (`early-response` in `logs/2026-10-28/core/net/`, and the control against milestone 1's client in `logs/2026-10-28/core/early-response-control/`).  A server that answers and then closes can make the pending write fail before the response is read; the call then fails as a closed connection, maybe delivered, without the response, unless the response head arrived first.  That race is not tested over TCP.
- **The write gap is per slice.**  `readGapMs` bounds each 64 KiB slice of the request (`writeChunkBytes`), since a write's completion is the only progress the client can observe.
- **No cancellation.**  The exchange core fails with `Cause.localClose` when the caller abandons it before the response head, but `Client.request` never abandons; closing a client and cancelling a call come with connection reuse.

## The exit hang is a runtime bug, fixed by an open upstream PR

A process could hang at exit after leaving a `recvSelector` registration outstanding (`logs/2026-10-27/probes/`).  The cause is in Lean's task manager, not in sockets: a pool task blocked in `Task.get` on a `Task.map` of a promise that is resolved after `main` returns waits forever, because no worker is started during shutdown.  `recvSelector`'s registration callback blocks in exactly that way.  leanprover/lean4 #15743 ("fix: dead locks and memory leaks in task manager finalization", open on 2026-10-27) fixes both: with its toolchain (pr-release-15743, 0f2095f9b5) the socket-free program hung 0 of 5 times and the abandoned-selector loop 0 of 20, against 5 of 5 and 11 of 20 on v4.34.1 (`logs/2026-10-27/probes/out/issue-program-check.txt`).  Until that is in the toolchain we use, the library must end every receive registration it starts before a call returns (an extra alternative in the `Selectable.one` that closing resolves), or use a receive selector that does not block in its callback.

## Nothing carried across a wait is updated in place

Measured on 2026-10-28 (`logs/2026-10-28/core/bigbody/`).  A value that async code carries across a wait is captured by a continuation that another thread may run, so the runtime marks it as shared between threads, and `lean_is_exclusive` is false for every such object: updating it copies it.  Appending each chunk of a response body to one `ByteArray` therefore copied the whole body every time, in milestone 1 and in the first version of the new shell: 5.6 to 7.5 s for a 60 MB body over loopback, growing with the square of the size.  Keeping it in an `IO.Ref` does not help, since a value stored in a shared reference is marked as well.  The shell now keeps the chunks in a list and joins them once at the end, in a buffer allocated there: 70 to 100 ms.  Any state the shell accumulates across waits (a streaming body's buffer, a pool's tables) needs the same care; the exchange core is pure, but the shell holds its `Exchange` across waits, so the core must not grow a buffer in place either.  The body pieces it holds for a caller that has not asked for them are replaced at each read, never appended to across waits, and no read is issued while any are held, so they never exceed one read; the codec slices body bytes out of the bytes fed and keeps only the current line's bytes, bounded by its limits.

## Fuzzing the exchange core, and the machine before it

`Fuzz/Harness.lean` reads fuzzer bytes as one exchange: a control byte (request method, end of input or not, reads of one byte or by a table), a table of read lengths, then the response.  It drives the exchange core (and so the codec inside it) through `Exchange.begin` and `Exchange.step` as a shell would (the request in 16-byte writes, a POST with a body still going out when the response arrives, each dictated read reported while a read is in flight, then end of input), with keep-alive on over the response whole and in the dictated reads and with keep-alive off over the reads, and a direct, step-bounded driver of the vendored machine with keep-alive on, as its oracle.  It checks the invariants listed in its module comment: termination, a well-formed event sequence, no body where none is allowed, Content-Length and close-delimited bodies against the response bytes, the reuse decision of both drivers, split invariance and agreement between the two drivers, but for the codec's deliberate differences from the machine, which the cross-check attributes ("The codec inside the exchange core", above).  Every step of the core is also checked by the executable checker's `checkStep`, and after it the model's agreement with the core and the timers' invariant; once per run, `begin`'s write, bytes before any write completed, an event at the deadline and a shell that only waits.  The theorems in `LeanHttp/Exchange/` state each of these, so they should never fire; the fuzzer exercises them end to end.  A failed invariant panics, and `fuzz/afl-main.c` runs the check in AFL++'s persistent mode with `LEAN_ABORT_ON_PANIC=1`, so a failure is a crash.  Both drivers use lowered parser limits so that inputs of a few kilobytes reach them, and responses are cut at 2432 bytes, the machine's input buffer limit with those settings.

To run it (all on the build host, through the AFL++ image, pinned by digest):

    fuzz/run.sh fuzz/build.sh                        # lake build Fuzz, then the instrumented binaries
    PIN_CPUS=40-43 fuzz/run.sh fuzz/fuzz.sh .lake/fuzz/campaigns/<name> <seconds> 4
    PIN_CPUS=40-43 fuzz/run.sh env EXTRA_SEEDS=<dir> fuzz/fuzz.sh ...   # start from an earlier corpus
    fuzz/run.sh fuzz/triage.sh .lake/fuzz/campaigns/<name>
    scripts/remote.sh .lake/build/bin/fuzz-replay <file>...   # what both drivers did
    scripts/remote.sh .lake/build/bin/fuzz-replay --allowances <file>...   # the differences each input relies on

`fuzz/h11-diff.py` compares the machine's framing decisions over a queue with h11's (run with uv on the host, outside the containers); its allow-list rules say which differences are expected.

What it does not reach: the toolchain's `Std.Http` data layer (header names and values, `Parsec`) runs but is not instrumented, so AFL++ gets no coverage feedback from it.  The request is encoded by `Exchange.prepare`, its writes are checked against those bytes and the bytes against the machine's encoding of the same request, for the one request per method the harness sends (`codec-diff` compares encodings more widely); timers fire only once the reads are over; the caller always wants the whole body and never abandons it, and no write or read fails.  The shell (sockets), the pool and responses longer than 2432 bytes are outside the harness.

Measured on 2026-10-28 (`logs/2026-10-28/fuzz/`, with `commands.txt` listing every run): a three-hour campaign on four CPUs of the shared build host ran 145 million executions, reached 8,898 of the 77,427 instrumented edges (flat after the first hour) and found no crash; its one saved hang was an input that runs in a few milliseconds and timed out while the host was overloaded.  As positive controls, two defects were planted in scratch copies of the machine, each ending a Content-Length body one byte early when it arrives split at a particular point: one needing a single mutation of the seeds was found in 99 s; one needing a Content-Length of at least 10 with exactly 3 bytes outstanding after a partial read was not found in 2.5 hours (20 million executions), though the harness reports it when given such an input.  With a seed one byte away from it (a 26-byte Content-Length body, now among the seeds) it was still not found in 10 minutes, with or without AFL++'s deterministic stage, which in that time finished 2 of 1,290 queue entries: the search is limited by throughput (about 3,500 executions per second per CPU on the shared host), not by what the harness can see.  `fuzz/fuzz.sh` now runs the deterministic stage on its main instance, which pays off only over long campaigns.

The campaigns above, and the planted-defect runs, did not run on the CPUs `logs/2026-10-28/fuzz/commands.txt` lists: the AFL++ image sets `AFL_TRY_AFFINITY`, and with it each afl-fuzz bound itself to one of CPUs 124-127, replacing the `taskset` list (their `main.log` files say so).  `fuzz/run.sh` now unsets it.

The campaigns above, and the ones below, fuzzed the core over the machine; "The codec inside the exchange core" (above) records the replay of their inputs through the harness for the core over the codec.

The harness was then ported to the exchange core's step function, and the two findings below fixed (`logs/2026-10-28/fuzz2/`, with `commands.txt` listing every run).  All 16,703 distinct inputs of the earlier campaigns, crashes and hangs included, pass the ported harness.  Six mutants of the core, replayed over those inputs, are each caught: undoing either fix, a read before the request head is written, a deadline acted on only after it, reuse with bytes left over, a failure without its status.  Plant B was found again, after 4.8 s.  A one-hour campaign on four pinned CPUs, starting from the earlier inputs reduced with afl-cmin, ran 11.3 million executions and found no crash and no hang; it added 25 edges to the 13,334 its seeds reached, out of 94,947.  The host was saturated (load average about 150-250 on 128 CPUs), so it ran at 530-1,370 executions per second per instance.

What the campaign and the differential check against h11 (over its 6,161 distinct inputs) showed:

- **A response with a transfer coding other than chunked was accepted and returned still coded** (fixed).  `Transfer-Encoding: gzip, chunked` (or any unknown coding before `chunked`) completed with the chunked coding removed and the other left in place, and no error; h11 refuses it, as does Go's client.  Until the client decodes transfer codings, the exchange core and the response codec now refuse such a body once its head is delivered, with a protocol cause and the response received; a response without a body is not refused for the codings its head names.
- **A Content-Length above 2^62 failed without a status** (fixed).  The exchange core lifted the machine's body limit to 2^62, so a larger length was refused by the machine before it reported the head, and the body-limit error said the request may or may not have been delivered.  The machine's limit is now above any length it can parse (`Exchange.prepare`), and every length over the client's limit fails after the head, with its status.
- **Reuse needs more than the machine's `keepAlive`.**  It stays on after the peer has closed, and when bytes follow a response (a body after HEAD, 204 or 304, or stray bytes); a pool must also check that input has not ended and that nothing is left over.  It also only ever turns off, so an HTTP/1.0 interim response, or one with `Connection: close`, stops reuse even if the final response allows it, as does a `Connection` value that is not a list of tokens; both are safe.  An HTTP/1.0 response with `keep-alive` is reusable, as RFC 9112 section 9.3 allows (h11 never reuses HTTP/1.0).
- **Chunk data is streamed only when it arrives in pieces.**  Given a whole chunk in one read, the machine waits for its terminator before handing out its data; given it in pieces, it streams the data at once.  Outcomes agree, but a chunk over the body limit is refused at different points.
- Expected strictness, not defects: bytes 0x80-0xFF (obs-text) in a reason phrase or field value are refused (the upstream parser documents this, although RFC 9112 and 9110 allow them); bare LF, obsolete line folding, HTTP/1.0 with chunked and malformed chunk extensions are refused where h11 accepts them; whitespace before a chunk extension is accepted where h11 refuses it, as the RFC allows.  The machine treats a 101 nobody asked for as a final response; the exchange core refuses it.

## The per-call planner

Built on 2026-10-29, not yet wired into the client.  `LeanHttp.Call` decides what follows each exchange of a call (`Call.plan : State → Clock → Outcome → State × Step`), `LeanHttp.Call.Redirect` decides redirects and rewrites the next request, `LeanHttp.Call.RetryAfter` parses `Retry-After`, and `LeanHttp/Call/Proofs.lean` proves the rules.  The library does not import the vendored protocol layer again: the planner is written against `Std.Http`'s types, and the upstream redirect planner, in its PR-head copy (vendored) and its v4.34.1 copy, is the oracle of `call-diff`.

Deliberate differences from the upstream redirect planner and the upstream client's redirect loop, each of which `call-diff` neutralises to show that it explains the disagreements it is given for:

- **The hop limit is an error.**  The upstream loop delivers the last 3xx when its budget is spent, as if it were the answer; the planner fails with `tooManyRedirects`, as Go, curl and browsers do (the review, item 8).
- **No cycle detection keyed on URLs.**  The upstream loop delivers a 3xx whose origin, path and query it has already visited, ignoring the method, so POST, 303, GET to the same URL comes back as the bare 303.  The hop limit alone ends a real loop.
- **Only 301, 302, 303, 307 and 308 are followed.**  The upstream planner follows any other 3xx with a `Location` except 300, 304, 305 and 306; codes without defined redirect semantics are delivered, as the Fetch standard's "redirect status" list has it.
- **HTTP/1.0 responses are not treated differently.**  The upstream planner follows only 301 and 302 from an HTTP/1.0 server and keeps POST on them.  The Fetch standard does not look at the version either, and keeping POST on a 301 or 302 is what no user agent does.
- **301 and 302 keep every method but POST**, with its body if that is replayable, as the Fetch standard does; the upstream planner refuses 301 and 302 for methods other than GET, HEAD and POST.
- **A GET or HEAD body is not dropped silently.**  On a redirect that keeps the method, the upstream planner sends a GET or HEAD without its body; the planner sends the body again if it can, and otherwise delivers the redirect, like any other request whose body cannot be sent again.
- **Credentials are given back at the original origin.**  The upstream planner judges each hop against the previous one, so after A, B, A the request to A has lost its `Authorization`; the planner judges against the call's first request, as Go does (Go by host alone, subdomains allowed; the planner by scheme, host and port).
- **`Host` stays within its origin.**  A `Host` the first request gives is kept on hops within the same origin (a virtual host chosen on purpose) and rewritten on a hop to another; when there is none, the client writes one from the target.  A credential field the first request's `Connection` names is hop-by-hop, so it is neither carried over nor given back.
- **The digest fields go with a method change.**  RFC 9110 section 15.4 names `Digest` among the content fields to remove; the planner removes it, `Content-Digest` and `Repr-Digest` too.
- **No `onlySafeRedirects`.**  v4.34.1's planner has an option to refuse every method that is not safe; the PR head removed it, and `Policy.followRedirects` is the planner's only switch.
- v4.34.1's planner leaves dot segments and an empty path in an absolute `Location` as they are; the PR head and the planner resolve them (RFC 3986 section 5.2.2, RFC 9112 section 3.2.1).

Retry choices:

- **Every retry after a failure waits the backoff**, not only a failed connect: the n-th retry of the call waits `Backoff.delayMs` for draw n, so the whole schedule replays from the seed.
- **A wait must end before the deadline**, strictly: a retry that would start at the deadline would time out at once.
- **A 429 or 503 is retried only for a request that could be retried after bytes were sent** (idempotent, replayable), since the server has received the request.  This makes one theorem (`plan_no_resend`) cover every way a request is sent again.
- **A `Retry-After` date is measured from the response's `Date`**, when it has one, rather than from the local clock, so that clock skew between client and server does not change the wait; a stale `Date` can only make the wait longer, and `Policy.maxRetryAfterMs` and the deadline bound it.  `Clock.wallSec` has no default, so that a shell cannot leave it at 1970.
- A retry after a `notSent` failure may send a streamed body, which is safe only if nothing of the stream was read before the failure: an obligation on the streaming shell to come.

Two things learnt while proving it:

- `Std.Http`'s `Headers` can be reasoned about only by `import all` of `Std.Http.Data.Headers` and `Std.Http.Internal.IndexMultiMap`; `Headers.ofList` then gives back its list (`toList_ofList`), so the planner builds every next request's fields as a list and the theorems speak of `Headers.toList`, the entries the encoder writes.
- `import all LeanHttp.Backoff` in the proof module made the kernel give up with deep recursion on `rfl` about `State.backoff`: `LeanHttp.Call` was compiled without `Backoff`'s bodies, so its definitions' heights are lower than `Backoff.delayMs`'s, and the kernel unfolded the jitter's 64-bit arithmetic instead of `State.backoff`.  The cap lemmas therefore live in `Backoff.lean`, and the proofs import it normally.

What wiring the planner into the client needs:

- A loop in `Client.request` around the exchange: `Call.start` with the request (its target absolute, as now), the body's kind (`.none` for an empty body, `.bytes` otherwise; `.stream` when streaming bodies arrive) and the seed and deadline the call already has; then, for each step, send `State.current` (`follow` and `retry` both mean that), waiting `delayMs` first for a retry.  `Reachable.target` says the hop's target and `Hop.origin` agree, so the pool can key on either.
- `Clock`: `IO.monoMsNow` for `now`, on the clock of the deadline, and the wall clock in seconds for `wallSec`.
- Outcomes: the final response head as `.response` before its body is read; any `Failure` of the exchange as it is; a connect that failed as `{ cause := .connect attempts, delivery := .notSent }`, with `Connect.run` making one round only, since the planner now owns the retries and their backoff (or keeping its rounds and setting the planner's retries to zero for connects, which would leave two schedules).  Name resolution and invalid requests are never retried, so they may go to the planner or straight to the caller.
- A response that is followed or retried has its body read and discarded within the drain limit (keeping the connection) or its connection closed, before the next request.
- `Config` gains the policy's fields (`followRedirects`, `maxRedirects`, retries per hop and per call, `retry429`, `retry503`, `maxRetryAfterMs`), the backoff fields being shared; `Error` gains a cause for `tooManyRedirects` (with the last status) and a way to say which hop failed; `CallInfo` can record the hops and retries.
- `Client.plan` already writes `Host` from the target when the head has none, which the planner relies on after it drops a `Host` it cannot rewrite.
- `Cause.localClose` and `Cause.isConnect` have docstrings from milestone 1 ("never produces it", "the only cause the client retries") that the wiring will make wrong.
