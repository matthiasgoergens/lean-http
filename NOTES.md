# Notes

## The HTTP/1.1 codec: a vendored copy of the upstream protocol layer

Decided on 2026-10-27, by measurement.  Since 2026-10-28 the library no longer uses this copy: the exchange core parses responses with its own codec and encodes requests itself ("The codec inside the exchange core", below), and the copy is the oracle of the tests and the fuzzing harness only.

`DESIGN.md` planned to use the HTTP/1.1 machine that v4.34.1 ships (`Std.Http.Protocol.H1.Machine`, client direction).  Nothing in v4.34.1 drives that direction (the server uses only `.receiving`), so `Tests/Codec.lean` drives it through the exchange core over 37 response shapes, each fed whole, one byte at a time and split in two at every position.

Against the v4.34.1 machine, 31 of the 34 cases with an expected outcome pass (Content-Length, chunked, close-delimited, HEAD, 204 and 304 with framing fields, interim responses, malformed status lines, header and body limits, end of input at every stage).  Three fail, all the same way: when a chunk-size line with extensions, or a trailer section, arrives split across two reads, the response is rejected as a bad message (`logs/2026-10-27/codec-v4.34.1/out.txt`).  The cause is `manyItems` in `Protocol/H1/Parser.lean`: it wraps each item in `optional (attempt ...)`, which turns "ran out of input" into "no more items", and the parser then fails hard on the half-received item instead of asking for more bytes.  TCP may segment a response anywhere, so this is a spurious failure in real use, rare only because extensions and trailers are rare.

The upstream client stack (leanprover/lean4 PRs 14546-14548, head 3e6f42a58a955f7fd9a6df4213f3be4bb68e3e3b) fixes exactly this (`optionalItem`), and changes the machine's client direction in a few other ways this client benefits from: `101 Switching Protocols` is no longer treated as an interim response, the end of an interim response's body is not reported as the end of the body, and a request without content gets no `Content-Length: 0`.  With that protocol layer vendored, all 37 cases pass, and the request encodings are checked as well (`logs/2026-10-27/codec-vendored/out.txt`).

So the library uses a copy of the stack's `src/Std/Http/Protocol`, renamed to `LeanHttpProto.Http.Protocol`, generated into the ignored `vendor/` by `scripts/vendor.sh` from a lean4 clone at that commit; `vendor/SOURCE` records the commit.  Two choices differ from a whole-tree copy:

- **Only the protocol layer is copied, not `Data` and `Internal`.**  `Internal` is unchanged in the stack, and its `Data` changes are additive helpers, of which the protocol layer needs two (`Status.isInterim`, `Method.anticipatesContent`); `LeanHttp/VendorCompat.lean` supplies them.  Copying `Data` would fork `Request`, `Response` and `Headers`, and the client's API would no longer speak `Std.Http`'s types, which `DESIGN.md` relies on for moving code between this client, `Std.Http.Server` and a future `Std` client.
- **The copy is a separate Lake library** (`LeanHttpProto`, source directory `vendor/`), with the toolchain's default options; the client's own library builds with `autoImplicit` off.

The exchange core over this machine (now `Tests/Support/MachineCore.lean`) refused `101` itself and counted interim responses itself, since neither version of the machine limits them.  The copy can go, with `scripts/vendor.sh`, `LeanHttp/VendorCompat.lean` and the oracle core, once the tests no longer need the machine to compare with; a toolchain that ships these protocol changes would let the oracle point at `Std.Http.Protocol` instead.

The three informational cases record behaviour without asserting it: a status line without the space before an empty reason phrase, bare LF line endings and obsolete line folding are all rejected as bad messages, by both versions.

## A response parser written for proof

Built on 2026-10-28; the exchange core parses every response with it ("The codec inside the exchange core", below).  `LeanHttp/Codec/` parses an HTTP/1.1 response in the client direction, given the request method, and every function in it is total.  `Parser.stepByte` reads one byte with no loop and is the meaning of the parser; `Parser.feed` reads body bytes in bulk, slicing them out of its input, and is proved to compute the same (`feed_eq_run`).  `LeanHttp/Codec/Proofs.lean` lists what is proved, and `scripts/codec-axioms.lean` prints the axioms of the main theorems, which use `propext`, `Classical.choice` and `Quot.sound` at most.

Its rules and limits are those of the vendored machine, with the exchange core's interim limit, `101` refusal, body limit and refusal of a transfer coding other than chunked built in, except in these deliberate differences, each of which the differential test below finds and attributes:

- A chunk whose size line announces more than the body limit leaves is rejected at its size line.  The core rejects it only once the data arrives, so its outcome then depends on what the data holds and on how the bytes are cut: a bad message, still pending, a premature close, or the body limit.
- A chunk-size line longer than its limit is rejected at the byte that exceeds it.  The vendored machine measures an incomplete line only up to its last complete extension, and keeps waiting.
- Chunk extensions are counted at each `;`, so one too many is refused when its `;` arrives rather than when it is complete.
- `Connection: close` ends the connection whatever the version (RFC 9112 section 9.3).  The vendored machine looks for `close` only in HTTP/1.1, so it keeps an HTTP/1.0 connection whose response says both `keep-alive` and `close`.
- There is no `maxStartLineLength`: a status line is bounded by the reason-phrase limit, 527 bytes with the defaults, well inside the machine's default of 8192.

Measured on the build host (`logs/2026-10-28/codec/final/`, commit c94d1e6):

- The 37 response shapes of `Tests/Codec.lean` pass, each fed whole, byte by byte and split in two at every position (`response-codec-tests`).
- `codec-diff` ran 120,037 inputs for each of four seeds: the shapes, responses generated with deliberate faults, and mutations of both, with GET, HEAD or POST and default or partly small limits, each run whole and cut at random points, without and with the end of input.  Every disagreement with the core falls under one of the differences above (the tool finds the cause by relaxing one limit at a time until the two agree), and the codec's outcome never depended on the cut.  The core's did, on 43 inputs, all with a chunk beyond the body limit.  A control run with the codec's limits off by one shows the comparison sees disagreements.
- Parsing a 60 MB body fed in 64 KiB reads, the codec took 0.94 times the core's time for a `Content-Length` body, 0.93 with 16 KiB chunks and 0.75 with 1 KiB chunks (median per-block ratios over 100 randomised blocks on one pinned CPU of a loaded machine; the codec was faster in 60, 61 and 100 of the 100 blocks).  Body bytes are slices of the bytes fed, so nothing carried across calls grows with the body.

Left open:

- Completeness is not proved: no theorem says that a well-formed response within the limits is accepted.  The shape tests and the differential run are the evidence that it is.
- The interim heads' `Connection` fields enter the keep-alive verdict, but no theorem ties that to the bytes.
- CONNECT and protocol upgrades are not handled; the client sends neither.

## The codec inside the exchange core

Done on 2026-10-28 (`logs/2026-10-28/integrate/`, with `COMMAND` listing every run).  The exchange core feeds every byte read once the request head is written to `Codec.Parser`, and acts on its events: the head is delivered, body bytes are delivered as far as the caller has asked for them, and a rejection fails the exchange with the cause the core reported over the machine (`Exchange.causeOf`).  Requests are encoded by the client's own serialiser, so the library no longer depends on the vendored copy; the core over the machine is kept, unchanged, as a test oracle (`Tests/Support/MachineCore.lean`).

Decisions, and why:

- **Requests: a serialiser of our own** (`Codec.encodeRequest`).  What the client sends is small (a head, a `Content-Length` for the body or none for an empty body whose method does not anticipate content, `Connection: close` unless the connection is to be kept alive), and `Std.Http` encodes heads.  Keeping the vendored writer would have left the whole vendored layer in the library for that alone.  It changes the head's fields in the order the machine's writer did and decides the request's own keep-alive the way the machine did (no `close` in HTTP/1.1, a `keep-alive` option in HTTP/1.0), so its bytes are the machine's (since the pool, but for a `Connection: keep-alive` field the machine left out, which the comparisons remove; "The connection pool", below): `codec-diff` encodes 6,000 generated heads per seed with both (methods, versions, `Connection`, framing and other fields, empty and non-empty bodies, keep-alive on and off) and found no difference in bytes, head length or keep-alive, and `codec-tests` checks eight encodings exactly.  The machine never refused a head the client prepares (it refused only framing fields that contradict the body, which `prepare` removes), so `prepare` now cannot fail.
- **Body credit.**  The codec delivers every body byte it is fed, so the core holds what the caller has not asked for (`Exchange.held`) and issues no read while it holds any; what it holds is therefore never more than one read, and a feed replaces it rather than growing it across waits ("Nothing carried across a wait is updated in place", below).  Once the caller asks for more, everything held goes out at once.  Releasing one piece per request instead held bytes back that the machine would have handed over, as one buffered chunk, and a later abandon then found more held than the drain limit: the comparison of random runs below found that, and the change.
- **Reuse.**  The verdict is the codec's `Parser.reusable` (the response ended, framed with certainty, nothing after it, the input not ended, the keep-alive verdict of its heads) and the core's own conditions: keep-alive asked for and allowed by the request head, the request written in full before the response head, the whole body handed over, the peer not closed.

What the proofs now cover.  The theorems of `LeanHttp/Exchange/Proofs.lean` and `Liveness.lean` keep their statements, except that `Reusable`, which `step_finish_reusable` concludes, names the codec's verdict and the empty hold instead of the machine's keep-alive, framing, end of body and leftover input; their proofs treat the parser as opaque, as they did the machine.  `LeanHttp/Exchange/Response.lean` adds what the machine's opacity ruled out, in the terms of the checker's model (which now records the bytes received, the body delivered and the abandonment): in every run, until the exchange fails, the core's parser is the codec's run over the bytes received (`Observed.cinv`); a reusable finish means those bytes are exactly one response, interim heads, the head and a body of the kind its framing declares, with nothing after it, and the body delivered is that body's payload unless the caller abandoned it (`observed_finish_codec`); any finish the caller did not abandon comes after a complete response whose body was delivered whole (`observed_finish_complete`); and the body delivered is always a prefix of what the codec decoded (`observed_body_prefix`).  These are relative to the codec's reading of the bytes, which `Codec.response_sound`, `Codec.head_sound` and `Codec.HeadOK` tie to the bytes themselves.  `scripts/proof-axioms.lean` prints the 41 exchange theorems' axioms (as of `integrate` 25fb963): `propext`, `Classical.choice` and `Quot.sound`.

Behaviour against the core over the machine:

- The 41 response shapes of `codec-tests` give the same outcomes in every split, and the unit, trace and real-socket suites pass unchanged (76 checks, the one known limitation of `dns-timeout` as before).
- `codec-diff` compares the codec with the machine core exactly as it compared it with the core before, and finds the same classes with the same counts on the same seeds; the core and the codec alone agree on every input, whole and cut, open and at end of input (the reuse verdict compared over the whole input without end of input, where both see the same bytes).
- `core-tests compare` replays 200,000 random runs per seed on both cores: 198,315 and 198,368 end the same way (seeds 1 and 2), and every other run is attributed by lifting the smallest set of limits that makes the two agree.  About three quarters come from the body limit: the codec refuses a chunk announced beyond it at its size line, and a body over it as its bytes arrive, where the machine core refused either only once the caller pulled the bytes.  About a fifth come from the caller's credit: the core hands over everything held, the machine core one machine chunk per request.  The rest come from chunk data, which the codec delivers (and counts against the drain limit) as it arrives, where the machine waited for the chunk's terminator when the data came in one read.
- The random runs of `props` and the states of `explore` change in number, since the generator's choices follow the core's actions and the explorer's states are told apart by a fingerprint that now reads the parser instead of the machine; every property holds.

Fuzzing.  The harness drives the new core and keeps its direct driver of the machine as the oracle, started from the machine the oracle core encoded the request with (which must make the core's bytes).  The cross-check allows the codec's deliberate differences listed above, each attributed by running the codec alone with one limit lifted, and `fuzz-replay --allowances` counts which inputs rely on which.  The core is now required to be split-invariant outright, body limit included.  All 21,787 inputs of the earlier campaigns (the seeds, the 16,703 distinct inputs of the first campaigns, the 795 of `afl-cmin` and the 4,233 queue entries of the last one) pass; 454 rely on the allowance for a chunk announced beyond the body limit and 18 on the one for a chunk-size line measured more strictly.  The instrumented build covers the codec (every object carries AFL++'s guards; the map has 124,596 edges).  As a positive control, a Content-Length body ending one byte early when a read leaves one byte of it, planted in a copy of the codec on the build host, was found in 34 s.  A ten-minute campaign on one pinned CPU, from the `afl-cmin` set, ran 890,000 executions and found no crash and no hang.

Performance.  Parsing a 60 MB body fed in 64 KiB reads, driven as `Client.request` drives the core, the core took 0.95 times the former core's time for a `Content-Length` body (95% interval 0.90 to 0.98), 0.81 with 16 KiB chunks and 0.66 with 1 KiB chunks (median per-block ratios over 100 randomised blocks on one pinned CPU of the loaded build host; `codec-bench`, both cores in one binary).  Against main's own binary, in 40 alternating blocks, the ratios were 0.92, 0.85 and 0.76, and the oracle copy of the former core ran as fast as main's (1.00, 1.07 and 1.04).

Left open:

- The request head's length is measured by the serialiser; the checker finds it independently, as the first blank line, and no theorem says the two agree (it depends on `Std.Http`'s encoding of validated fields).
- A delivery can exceed what the caller asked for by up to one read.  The body stream splits what it is handed, so a caller's read never returns more than it asked for ("Wiring the planner into the client, and streaming", below).
- The interim heads' part in the keep-alive verdict rests on the codec's code, not a theorem.
- The per-call planner has a redirect planner of its own rather than the vendored one, which would have brought the vendored layer back into the library ("The per-call planner", below).

## What can outlive a call, and other limits of milestone 1

Measured on 2026-10-27 (`logs/2026-10-27/net/`); v4.34.1 can cancel a pending receive but not a pending connect, write or name lookup.

- **An abandoned connect attempt** keeps its socket until the kernel gives up on the SYN: about 127 s with Linux's default `tcp_syn_retries` of 6.  It holds no worker and does not delay exit (the blackhole scenarios exit within tens of milliseconds), and the tests see the descriptors released once the kernel gives up (with `tcp_syn_retries=2` to keep the run short).  A host whose first address drops SYNs therefore costs one descriptor per call for two minutes; at about 8 calls a second that reaches the common limit of 1024 descriptors.
- **A write the peer never accepts** keeps its socket while the peer keeps the connection open (zero-window probes can keep it alive indefinitely).  The call itself ends at the write gap or the deadline, or with an early response that completes, and exit is not delayed (`write-timeout`, `early-response`).
- **An abandoned name lookup** keeps running in libuv's thread pool (four threads by default) until the resolver gives up, and libuv joins that pool when the process exits: with a name server that never answers, the process waited 8 s at exit after a call that ended at its 2 s deadline (`dns-timeout`, reported as a known limitation).  Worse, when the lookup ends during exit the process often dies with a segmentation fault: 3 of 10 runs in `logs/2026-10-27/dns-exit/`, and 4 of 6 in an earlier unsaved batch.  The cause is not established; it looks like the runtime-shutdown race in which a libuv callback runs after Lean's task manager has been freed.  So the client bounds lookups only by the deadline and leaves the rest to the resolver's own timeouts (`/etc/resolv.conf`).
- **An early response during an upload is heard, unless a write fails first.**  Since the exchange core became a step function (2026-10-28), the response is read once the request head is written, while the body is still going out.  A server that answers 413 after the head and stops reading now gets its response delivered in about 24 ms of a 32 MB upload, where milestone 1 ended the call with a write timeout at the 1 s gap (`early-response` in `logs/2026-10-28/core/net/`, and the control against milestone 1's client in `logs/2026-10-28/core/early-response-control/`).  A server that answers and then closes can make the pending write fail before the response is read; the call then fails as a closed connection, maybe delivered, without the response, unless the response head arrived first.  That race is not tested over TCP.
- **The write gap is per slice.**  `readGapMs` bounds each 64 KiB slice of the request (`writeChunkBytes`), since a write's completion is the only progress the client can observe.
- **No cancellation.**  The exchange core fails with `Cause.localClose` when the caller abandons it before the response head, but the client abandons an exchange only after its head (a body left unread).  Closing a client came with the pool (`Client.close`); cancelling a call has not.

## The exit hang is a runtime bug, fixed by an open upstream PR

A process could hang at exit after leaving a `recvSelector` registration outstanding (`logs/2026-10-27/probes/`).  The cause is in Lean's task manager, not in sockets: a pool task blocked in `Task.get` on a `Task.map` of a promise that is resolved after `main` returns waits forever, because no worker is started during shutdown.  `recvSelector`'s registration callback blocks in exactly that way.  leanprover/lean4 #15743 ("fix: dead locks and memory leaks in task manager finalization", open on 2026-10-27) fixes both: with its toolchain (pr-release-15743, 0f2095f9b5) the socket-free program hung 0 of 5 times and the abandoned-selector loop 0 of 20, against 5 of 5 and 11 of 20 on v4.34.1 (`logs/2026-10-27/probes/out/issue-program-check.txt`).  Until that is in the toolchain we use, the library must end every receive registration it starts before a call returns (an extra alternative in the `Selectable.one` that closing resolves), or use a receive selector that does not block in its callback.

## Nothing carried across a wait is updated in place

Measured on 2026-10-28 (`logs/2026-10-28/core/bigbody/`).  A value that async code carries across a wait is captured by a continuation that another thread may run, so the runtime marks it as shared between threads, and `lean_is_exclusive` is false for every such object: updating it copies it.  Appending each chunk of a response body to one `ByteArray` therefore copied the whole body every time, in milestone 1 and in the first version of the new shell: 5.6 to 7.5 s for a 60 MB body over loopback, growing with the square of the size.  Keeping it in an `IO.Ref` does not help, since a value stored in a shared reference is marked as well.  The shell now keeps the chunks in a list and joins them once at the end, in a buffer allocated there: 70 to 100 ms.  Any state the shell accumulates across waits (a streaming body's buffer, a pool's tables) needs the same care; the exchange core is pure, but the shell holds its `Exchange` across waits, so the core must not grow a buffer in place either.  The body pieces it holds for a caller that has not asked for them are replaced at each read, never appended to across waits, and no read is issued while any are held, so they never exceed one read; the codec slices body bytes out of the bytes fed and keeps only the current line's bytes, bounded by its limits.

## Fuzzing the exchange core, and the machine before it

`Fuzz/Harness.lean` reads fuzzer bytes as one exchange: a control byte (request method, end of input or not, reads of one byte or by a table), a table of read lengths, then the response.  It drives the exchange core (and so the codec inside it) through `Exchange.begin` and `Exchange.step` as a shell would (the request in 16-byte writes, a POST with a body still going out when the response arrives, each dictated read reported while a read is in flight, then end of input), with keep-alive on over the response whole and in the dictated reads and with keep-alive off over the reads, and a direct, step-bounded driver of the vendored machine with keep-alive on, as its oracle.  It checks the invariants listed in its module comment: termination, a well-formed event sequence, no body where none is allowed, Content-Length and close-delimited bodies against the response bytes, the reuse decision of both drivers, split invariance and agreement between the two drivers, but for the codec's deliberate differences from the machine, which the cross-check attributes ("The codec inside the exchange core", above).  Every step of the core is also checked by the executable checker's `checkStep`, and after it the model's agreement with the core and the timers' invariant; once per run, `begin`'s write, bytes before any write completed, an event at the deadline and a shell that only waits.  The theorems in `LeanHttp/Exchange/` state each of these, so they should never fire; the fuzzer exercises them end to end.  A failed invariant panics, and `fuzz/afl-main.c` runs the check in AFL++'s persistent mode with `LEAN_ABORT_ON_PANIC=1`, so a failure is a crash.  Both drivers use lowered parser limits so that inputs of a few kilobytes reach them, and responses are cut at 2432 bytes, the machine's input buffer limit with those settings.

To run it (all on the build host, through the AFL++ image, pinned by digest):

    fuzz/run.sh fuzz/build.sh                        # lake build Fuzz, then the instrumented binaries
    PIN_CPUS=40-43 fuzz/run.sh fuzz/fuzz.sh .lake/fuzz/campaigns/<name> <seconds> 4
    PIN_CPUS=40-43 fuzz/run.sh env EXTRA_SEEDS=<dir> fuzz/fuzz.sh ...   # start from an earlier corpus
    fuzz/run.sh fuzz/triage.sh .lake/fuzz/campaigns/<name>
    scripts/remote.sh .lake/build/bin/fuzz-replay <file>...   # what both drivers did
    scripts/remote.sh .lake/build/bin/fuzz-replay --allowances <file>...   # the differences each input relies on

`fuzz/h11-diff.py` compares the machine's framing decisions over a queue with h11's (run with uv on the host, outside the containers); its allow-list rules say which differences are expected.

What it does not reach: the toolchain's `Std.Http` data layer (header names and values, `Parsec`) runs but is not instrumented, so AFL++ gets no coverage feedback from it.  The request is encoded by `Exchange.prepare`, its writes are checked against those bytes and the bytes against the machine's encoding of the same request (without the `Connection: keep-alive` field the machine leaves out), for the one request per method the harness sends (`codec-diff` compares encodings more widely); timers fire only once the reads are over; the caller always wants the whole body and never abandons it, and no write or read fails.  The shell (sockets), the pool and responses longer than 2432 bytes are outside the harness.

Measured on 2026-10-28 (`logs/2026-10-28/fuzz/`, with `commands.txt` listing every run): a three-hour campaign on four CPUs of the shared build host ran 145 million executions, reached 8,898 of the 77,427 instrumented edges (flat after the first hour) and found no crash; its one saved hang was an input that runs in a few milliseconds and timed out while the host was overloaded.  As positive controls, two defects were planted in scratch copies of the machine, each ending a Content-Length body one byte early when it arrives split at a particular point: one needing a single mutation of the seeds was found in 99 s; one needing a Content-Length of at least 10 with exactly 3 bytes outstanding after a partial read was not found in 2.5 hours (20 million executions), though the harness reports it when given such an input.  With a seed one byte away from it (a 26-byte Content-Length body, now among the seeds) it was still not found in 10 minutes, with or without AFL++'s deterministic stage, which in that time finished 2 of 1,290 queue entries: the search is limited by throughput (about 3,500 executions per second per CPU on the shared host), not by what the harness can see.  `fuzz/fuzz.sh` now runs the deterministic stage on its main instance, which pays off only over long campaigns.

The campaigns above, and the planted-defect runs, did not run on the CPUs `logs/2026-10-28/fuzz/commands.txt` lists: the AFL++ image sets `AFL_TRY_AFFINITY`, and with it each afl-fuzz bound itself to one of CPUs 124-127, replacing the `taskset` list (their `main.log` files say so).  `fuzz/run.sh` now unsets it.

The campaigns above, and the ones below, fuzzed the core over the machine; "The codec inside the exchange core" (above) records the replay of their inputs through the harness for the core over the codec.

The harness was then ported to the exchange core's step function, and the two findings below fixed (`logs/2026-10-28/fuzz2/`, with `commands.txt` listing every run).  All 16,703 distinct inputs of the earlier campaigns, crashes and hangs included, pass the ported harness.  Six mutants of the core, replayed over those inputs, are each caught: undoing either fix, a read before the request head is written, a deadline acted on only after it, reuse with bytes left over, a failure without its status.  Plant B was found again, after 4.8 s.  A one-hour campaign on four pinned CPUs, starting from the earlier inputs reduced with afl-cmin, ran 11.3 million executions and found no crash and no hang; it added 25 edges to the 13,334 its seeds reached, out of 94,947.  The host was saturated (load average about 150-250 on 128 CPUs), so it ran at 530-1,370 executions per second per instance.

What the campaign and the differential check against h11 (over its 6,161 distinct inputs) showed:

- **A response with a transfer coding other than chunked was accepted and returned still coded** (fixed).  `Transfer-Encoding: gzip, chunked` (or any unknown coding before `chunked`) completed with the chunked coding removed and the other left in place, and no error; h11 refuses it, as does Go's client.  Until the client decodes transfer codings, the exchange core and the response codec now refuse such a body once its head is delivered, with a protocol cause and the response received; a response without a body is not refused for the codings its head names.
- **A Content-Length above 2^62 failed without a status** (fixed).  The exchange core lifted the machine's body limit to 2^62, so a larger length was refused by the machine before it reported the head, and the body-limit error said the request may or may not have been delivered.  The machine's limit is now above any length it can parse (`Exchange.prepare`), and every length over the client's limit fails after the head, with its status.
- **Reuse needs more than the machine's `keepAlive`.**  It stays on after the peer has closed, and when bytes follow a response (a body after HEAD, 204 or 304, or stray bytes); a pool must also check that input has not ended and that nothing is left over.  It also only ever turns off, so an HTTP/1.0 interim response, or one with `Connection: close`, stops reuse even if the final response allows it, as does a `Connection` value that is not a list of tokens; both are safe.  An HTTP/1.0 response with `keep-alive` is reusable, as RFC 9112 section 9.3 allows (h11 never reuses HTTP/1.0).
- **Chunk data is streamed only when it arrives in pieces.**  Given a whole chunk in one read, the machine waits for its terminator before handing out its data; given it in pieces, it streams the data at once.  Outcomes agree, but a chunk over the body limit is refused at different points.
- Expected strictness, not defects: bytes 0x80-0xFF (obs-text) in a reason phrase or field value are refused (the upstream parser documents this, although RFC 9112 and 9110 allow them); bare LF, obsolete line folding, HTTP/1.0 with chunked and malformed chunk extensions are refused where h11 accepts them; whitespace before a chunk extension is accepted where h11 refuses it, as the RFC allows.  The machine treats a 101 nobody asked for as a final response; the exchange core refuses it.

## The per-call planner

Built on 2026-10-29, and wired into the client the same day ("Wiring the planner into the client, and streaming", below).  `LeanHttp.Call` decides what follows each exchange of a call (`Call.plan : State → Clock → Outcome → State × Step`), `LeanHttp.Call.Redirect` decides redirects and rewrites the next request, `LeanHttp.Call.RetryAfter` parses `Retry-After`, and `LeanHttp/Call/Proofs.lean` proves the rules.  The library does not import the vendored protocol layer again: the planner is written against `Std.Http`'s types, and the upstream redirect planner, in its PR-head copy (vendored) and its v4.34.1 copy, is the oracle of `call-diff`.

Deliberate differences from the upstream redirect planner and the upstream client's redirect loop, each of which `call-diff` neutralises to show that it explains the disagreements it is given for:

- **The hop limit is an error.**  The upstream loop delivers the last 3xx when its budget is spent, as if it were the answer; the planner fails with `tooManyRedirects`, as Go, curl and browsers do (the review, item 8).
- **No cycle detection keyed on URLs.**  The upstream loop delivers a 3xx whose origin, path and query it has already visited, ignoring the method, so POST, 303, GET to the same URL comes back as the bare 303.  The hop limit alone ends a real loop.
- **Only 301, 302, 303, 307 and 308 are followed.**  The upstream planner follows any other 3xx with a `Location` except 300, 304, 305 and 306; codes without defined redirect semantics are delivered, as the Fetch standard's "redirect status" list has it.
- **HTTP/1.0 responses are not treated differently.**  The upstream planner follows only 301 and 302 from an HTTP/1.0 server and keeps POST on them.  The Fetch standard does not look at the version either, and keeping POST on a 301 or 302 is what no user agent does.
- **301 and 302 keep every method but POST**, with its body if that is replayable, as the Fetch standard does; the upstream planner refuses 301 and 302 for methods other than GET, HEAD and POST.
- **A GET or HEAD body is not dropped silently.**  On a redirect that keeps the method, the upstream planner sends a GET or HEAD without its body; the planner sends the body again if it can, and otherwise delivers the redirect, like any other request whose body cannot be sent again.
- **Credentials are given back at the original origin.**  The upstream planner judges each hop against the previous one, so after A, B, A the request to A has lost its `Authorization`; the planner judges against the call's first request, as Go does (Go by host alone, subdomains allowed; the planner by scheme, host and port).
- **`Host` stays within its origin.**  A `Host` the first request gives is kept on hops within the same origin (a virtual host chosen on purpose) and rewritten on a hop to another; when there is none, the client writes one from the target.  A credential field the first request's `Connection` names is hop-by-hop, so it is neither carried over nor given back.
- **The digest fields go with a method change.**  RFC 9110 section 15.4 names `Digest` among the content fields to remove; the planner removes it, `Content-Digest` and `Repr-Digest` too.
- **No `onlySafeRedirects`.**  v4.34.1's planner has an option to refuse every method that is not safe; the PR head removed it, and `Policy.followRedirects` is the planner's only switch.
- v4.34.1's planner leaves dot segments and an empty path in an absolute `Location` as they are; the PR head and the planner resolve them (RFC 3986 section 5.2.2, RFC 9112 section 3.2.1).

Retry choices:

- **Every retry after a failure waits the backoff**, not only a failed connect: the n-th retry of the call waits `Backoff.delayMs` for draw n, so the whole schedule replays from the seed.
- **A wait must end before the deadline**, strictly: a retry that would start at the deadline would time out at once.
- **A 429 or 503 is retried only for a request that could be retried after bytes were sent** (idempotent, replayable), since the server has received the request.  This makes one theorem (`plan_no_resend`) cover every way a request is sent again.
- **A `Retry-After` date is measured from the response's `Date`**, when it has one, rather than from the local clock, so that clock skew between client and server does not change the wait; a stale `Date` can only make the wait longer, and `Policy.maxRetryAfterMs` and the deadline bound it.  `Clock.wallSec` has no default, so that a shell cannot leave it at 1970.
- A retry after a `notSent` failure may send a streamed body, which is safe only if nothing of the stream was read before the failure: an obligation on a shell with streamed request bodies, which the exchange core meets by pulling nothing before its first write ("Streamed request bodies", below).

Two things learnt while proving it:

- `Std.Http`'s `Headers` can be reasoned about only by `import all` of `Std.Http.Data.Headers` and `Std.Http.Internal.IndexMultiMap`; `Headers.ofList` then gives back its list (`toList_ofList`), so the planner builds every next request's fields as a list and the theorems speak of `Headers.toList`, the entries the encoder writes.
- `import all LeanHttp.Backoff` in the proof module made the kernel give up with deep recursion on `rfl` about `State.backoff`: `LeanHttp.Call` was compiled without `Backoff`'s bodies, so its definitions' heights are lower than `Backoff.delayMs`'s, and the kernel unfolded the jitter's 64-bit arithmetic instead of `State.backoff`.  The cap lemmas therefore live in `Backoff.lean`, and the proofs import it normally.

Measured on 2026-10-29 (`logs/2026-10-29/planner/`, with `run.sh` holding the commands), from scratch on the build host, on the code of b761dac:

- Every theorem in `scripts/call-axioms.lean` depends on no axiom beyond `propext`, `Classical.choice` and `Quot.sound`, and none on `sorryAx`.
- `call-tests` passes at both seeds; its 200,000 random calls take every kind of step and break no rule, and each of the nine planted bugs is caught.
- `call-diff`: about a quarter of the decisions differ from each oracle, every one explained by the differences above; each planted bug leaves disagreements unexplained; and every chain that differs from the upstream loop differs by the hop limit or by the absence of cycle detection.

## The connection pool

Built on 2026-10-29 (`logs/2026-10-29/pool/`, with `COMMAND` listing every run).  `Client` keeps a pool core (`LeanHttp.Pool`) and the sockets of its idle connections under one mutex; a call takes a connection of its origin (`host:port`), checks an idle one before use, runs the exchange on it and gives it back with the exchange core's verdict.  Pooling is on by default (`Config.pool`); with it off the client behaves as milestone 1 did.

Decisions, and why:

- **The pool core is pure and knows only ids.**  It allocates the ids, so that a connection being opened already counts against a cap on active connections, and a failed connect is a `drop`.  The shell keeps an idle connection's socket in a table next to the pool, and a checked-out connection's socket in the call using it, nowhere else.  Every operation takes the time as an argument and lets the expired idle connections go first, so no timer runs and the idle timeout is exactly as precise as the calls that use the pool.
- **Most recently returned first; a reusable connection that finds its origin's idle connections at the cap is closed**, as Go's transport and urllib3 do.  The older idle connections expire first that way.
- **Waiting at the active cap** (`Config.maxActivePerOrigin`, off by default) needs no queue in the core: `take` refuses, and the call waits for a promise the shell resolves, and replaces, whenever a connection is given back or dropped, then asks again, within its deadline.  Waiting calls are not served in order.
- **The idle check is a `waitReadable` bounded by a timer of `Config.idleCheckMs`, default 0 ms, then `cancelRecv`.**  `recvSelector`'s non-blocking check looks before the event loop has polled the socket: of 100 fresh connections each, 100 ms after the server sent bytes, closed or reset them, it reported 24, 2 and 8 (`logs/2026-10-27/probes/out/q1-first.txt`).  A timer of 0 ms does not: Lean's event loop runs libuv one iteration at a time (`UV_RUN_ONCE`), every registration interrupts it, and in such an iteration libuv polls for I/O before it runs the timers that are due (libuv's design overview, "The I/O loop").  The timer is started after `waitReadable`, so the iteration that fires it has polled the socket first, and bytes, the end of input or a reset that arrived while the connection was idle resolve the wait before the timer does.  Measured on fresh connections to `tests/net/idle.py`, 50 ms after the server sent bytes, closed or reset the connection (`idlecheck/`): with windows of 0, 1, 2 and 5 ms, 200 of 200 connections were found unclean in each case, and 200 of 200 idle ones clean; with 0 ms, 1,000 of 1,000 in each case.  A longer window catches only what arrives during it, and every reuse pays for it: against no check, reused calls on loopback took a median 0.13 ms longer with a 0 ms window (95% interval 0.09 to 0.16), 1.3 ms with 1 ms and 5.4 ms with 5 ms, where a reused call without the check took 0.28 ms (paired per block, 20 randomised blocks, server and client each pinned to a CPU; `bench/`).  The check never reads, so no receive is left pending when it returns.
- **A call is sent again on a fresh connection, once, when its pooled connection turns out to be closed and that is safe** (`Client.redispatch?`): nothing of it was written; the server answered 408 before any other response, which RFC 9110 section 15.5.9 says means it did not process the request, whatever the method; or the method is idempotent and the connection closed before any byte of a response, Go's rule for a server that closed an idle connection as the request went out.  It does not count against any retry budget.  A POST in that last race is not sent again: the server may have acted on it, so the call fails, maybe delivered.  The first rule rarely applies, since the exchange core counts a request as possibly delivered from its first write on; the idle check is what catches a connection the server closed before the request.
- **Requests say `Connection: keep-alive` when pooling is on.**  The serialiser wrote no `Connection` field for a kept-alive request, as the vendored machine's writer did, which in HTTP/1.1 asks for keep-alive too; but some HTTP/1.0 servers and proxies keep a connection open only when asked.  The tests that compare encodings with the machine remove that one field and compare the rest (`MachineCore.withoutKeepAlive`).
- **The pool's tables are copied by every operation.**  They live in the mutex's reference and are carried across waits, so the runtime never updates them in place ("Nothing carried across a wait is updated in place", below).  They hold a few connections per origin.

What is proved (`LeanHttp/Pool/Proofs.lean`; `scripts/pool-axioms.lean` prints the axioms of its main theorems: `propext`, `Classical.choice` and `Quot.sound` at most), over every sequence of operations from an empty pool: the invariant `WF` (no connection both idle and checked out or twice in either, every one allocated, the idle cap, the active cap, nothing idle once closed), so that each allocated connection is idle, checked out or gone and only one of them; that the hand-outs and returns of a connection alternate (`trace_alternates`), so that a checkout ends in at most one `giveBack` or `drop` and no return comes without a checkout; that `giveBack` and `drop` take back only a checked-out connection and otherwise leave the pool as `sweep` would; that a connection given back as not reusable, or dropped, is gone, and a gone connection is never handed out or taken back again; that `take` reuses only an idle connection of the origin that has not expired at the time it is given, and gives a new connection an id never allocated; that every connection an operation lets go (for the shell to close) was idle and is gone afterwards; and that a closed pool stays closed and hands nothing out.  The pool knows connections by id, not by the call that holds them, so "once per checkout" is the pool's half: that each call gives back or drops exactly the connection it took, and keeps a socket for exactly the idle ids, is the shell's, and is not proved.  Nor is the preference for the most recently returned connection, which `pool-tests` checks.

`pool-tests` checks the same properties by name, and every result against a model written separately from the pool, over traces, random runs and an exploration of every sequence over a small alphabet; planted bugs (the clock ignored, any give-back accepted, the idle cap off by one, the verdict ignored, a drop that keeps the connection) are each caught by the random runs and by the exploration, with the model and with the properties alone.

Real-socket scenarios (`tests/net/run.sh`; every one exits within tens of milliseconds of `main` returning, idle connections still open): a second and third call reuse the first call's connection, and the server sees one connection; with pooling off it sees one per call, each saying `Connection: close`; a server that closes idle connections after 200 ms has its closed connections caught by the idle check, and no call fails; without the check, the GET is sent again and the POST fails, maybe delivered; a server that closes the connection when the next request arrives (the race no check can see) gets the GET again on a fresh connection, and the POST fails, maybe delivered; a 408 sent on an idle connection is caught by the idle check, and without the check is read as the response and the POST sent again; responses with `Connection: close`, and a response to HEAD followed by stray bytes, are not reused; eight 300 ms calls at once through one client take about 300 ms, open eight connections and keep four, and the next eight reuse those four and open four more; with at most two active, six 200 ms calls take about 600 ms over two connections; closing the client closes its idle connections and refuses later calls; an expired idle connection is closed and not used.

An independent review of the theorems and the shell (a fresh Claude, and Gemini through `agy-readonly`; `reviews/`) found no defect in the pool core, and these in the shell, all fixed: `Client.close` did nothing with pooling off; an error after a re-dispatch said "not sent" when only the second attempt was not, though the first may have been delivered; an exception in the exchange could leave a receive pending, and an exception while waiting at the cap escaped `request`; the idle check did not stop at the deadline; a cap of zero active connections was accepted.  It also asked for the theorems on what operations let go and on closing, now proved, and for the headline "exactly once" to say whose half it is.

The re-dispatch sits below the per-call planner (`LeanHttp.Call`): for the planner it is part of one exchange, and it spends none of the planner's retries.  Each request the planner sends (the first, a redirect's, a retry) starts again from `take`.

Left open:

- A POST that crosses the server's close of an idle connection fails, maybe delivered.  Nothing short of the server's cooperation (or HTTP/2's GOAWAY) can tell whether it was processed.
- Origins are keyed by the host as written and the port: `localhost` and `127.0.0.1` are separate origins.
- Waiting calls at the active cap are not served in order, and there is no limit on connections over all origins.
- `Client.close` does not cancel calls in flight; their connections are closed when they end.

## Wiring the planner into the client, and streaming

Done on 2026-10-29 (`logs/2026-10-29/wire/`, with `COMMAND` listing every run).  `Client.withResponse` runs a call as a thin driver of the per-call planner and hands the final response to a callback that pulls its body (`BodyStream`); `Client.request` reads the whole body on top of the same loop.  `LeanHttp/Body.lean` drives an exchange in pieces (`Live`: until the head, one pull, or to the end), `LeanHttp/Wire.lean` holds the two pure parts the record of a call is checked against (`Client.plan`, `Client.redispatch?`), and `LeanHttp/Call/Trace.lean` the record and its check (`Call.validate`).

Decisions, and why:

- **The planner owns every retry; `Connect.run` makes one round.**  A failed round is a failure with cause `connect` and nothing sent, so the planner's backoff and budget cover connects too, with one schedule rather than two.  `Config.maxConnectRetries` became `Config.maxRetriesPerHop` (and `retryBudget`, `followRedirects`, `maxRedirects`, `retry429`, `retry503`, `maxRetryAfterMs`, `drainBytes`, `drainMs`).  Each round resolves the name again, as Go's dialer does for each dial: a retry then sees a changed answer, and a lookup costs little next to the backoff before it.  The seed's schedule is unchanged (the n-th retry of the call waits draw n), so recorded seeds replay as before.
- **The outcome is the final head, before the body.**  The planner decides on the head; the client then drains the body of a response it follows or retries (within `drainBytes` and `drainMs`, keeping the connection) or drops the connection.  A head and a body failure that arrive in the same read are reported as the head, which is what a later read would give too, so the outcome does not depend on how TCP cut the bytes; a body error surfaces in the read that meets it.
- **A call's error says how far the call got**, not its last exchange: the furthest any request got (a call that followed a redirect, retried a request that may have arrived, or re-dispatched one is never "not sent"), with the hop that failed, the retries made and the planner's reason for not retrying (`Error.hops`, `retries`, `notRetried`).  `Cause.tooManyRedirects` is new.
- **A retry waits from the time the planner decided, until that time plus the delay, measured by `IO.monoMsNow`.**  A libuv timer can fire up to a millisecond before its time by that clock (it measures from the time cached at the start of the loop's iteration), so the client sleeps again for any remainder.  The trace check found this: a retry went out 1 ms before its delay ended.
- **`https` is refused** with `invalidRequest`, for the first request and for a redirect, until there is TLS.
- **A read gives the core credit for one more read.**  The core then delivers what it holds, or reads once and delivers that, and holds nothing more, so between two reads nothing is in flight and the read gap is not armed while the caller is busy; the stream splits a piece longer than the caller asked for.  `readAll` (which `request` uses) gives credit for the whole body and reads in one loop with the wait in it.  Each layer of `Async` calls above a wait costs a continuation, and so a thread hop, per read: reading through `read` made `request` slower than before, and the single loop restored it (below).
- **Leaving the callback abandons the body**: drained within the limits, or the connection dropped; a stream used afterwards raises an error.  A read in progress in another task when the callback ends has its receive cancelled and is waited for, and whoever takes the stream's settle function owns the connection, so the release never touches a socket the reader has already given back.  An error the stream raised that leaves the callback becomes the call's `Error` (matched by its message); any other exception goes on.
- **The record of a call** (`Config.observe`, numbered per call) holds the start, each request as written (the origin and the encoded head) and when it went out, each re-dispatch, each decision with its clock and outcome, each wait, and the end.  `Call.validate` replays it through a planner of its own and recomputes each request with `Client.plan` and the request serialiser (`Codec.encodeHead`, split out of `encodeRequest` for this, with the same bytes).  The record is the client's own account; what the check rules out is a loop that decides anything itself.  `net-client` checks every call it makes; the unit tests check that mutated records are rejected (a retry sent early, a wait too short or missing, an old request sent after a redirect, a wrong body size, head or origin, a step or outcome the planner did not have, a re-dispatch `redispatch?` does not allow, two re-dispatches, wrong error causes, reasons, counts or deliveries, a refusal of a request the client can send).

Measured on 2026-10-29 (`logs/2026-10-29/wire/`, `run-final.sh` holding the commands), on the code of f5bf799, on the shared build host (load average 150-210 on 128 CPUs):

- From a clean build, without warnings: every theorem of the exchange core, the codec, the pool and the planner depends on `propext`, `Classical.choice` and `Quot.sound` at most, and none on `sorryAx`; unit (119 checks), codec, response-codec, traces, props and explore of the exchange core, codec-diff (the same classes as before, and every generated request encoded as the machine encodes it, through `encodeHead` now), the pool's and the planner's suites all pass.
- The real-socket suite: 291 checks pass, with the one known limitation of `dns-timeout` as before; the 743 calls it makes all replay through the planner.  The strace check still finds `TCP_NODELAY` set and a small request in one write.
- A 200 MB body read through `withResponse` in pulls of 4 KiB: peak resident memory 31.5 MB, against 480 MB when `request` reads the same body whole (the control).
- A 60 MB body over loopback, `request` against main's client, in 20 randomised blocks (each cell the median of five calls, client and server pinned to a CPU each): median ratio 0.98 (95% interval 0.85 to 1.10), so no slowdown was detected; the streamed read in 64 KiB pulls took 1.17 times main's whole read (0.95 to 1.23), the cost of a pull per read and no read-ahead.  Before `readAll` became one loop, `request` read through `read` and took about 1.4 times as long, and a profile showed the difference in the scheduler, not in copying.
- Planted defects the checks see: without keeping the bytes that came with the head, `stream-badchunk` fails; without taking a body that has arrived in full, `stream-unread-big` fails; the unit tests reject each mutated record listed above.

Two rounds of independent review of the shell (a fresh Claude and Gemini each time; `reviews/README` says what came of every finding) found, among smaller things: an error after a 408 re-dispatch whose fresh connection was refused said "not sent"; a read in another task could keep a receive pending, and the connection checked out, after the callback ended, and then release could cancel a receive on a connection already back in the pool; the record could not see re-dispatches and its request check compared the planner's head with itself; the stream could hold two reads and leave a read and its gap armed between pulls; bytes that came with the head were lost when the same read failed the body; a wall clock that threw would leak a connection.  All fixed.

Left open:

- Request bodies were bytes then ("Streamed request bodies", below).  A call cannot be cancelled.  (`https` was refused then; "TLS", below.)
- `request`'s body limit applies to the bodies of redirects and retried responses too, so with `maxBodyBytes` below `drainBytes` such a body costs its connection rather than being drained.
- The record covers the planner's steps only: the exchange and pool cores are not recorded, and the outcomes the client reports are taken as given.  A retry's real wake-up time has a lower bound in the check, not an upper one.  The record of a delivered call ends at the delivery.
- A read in flight through a long upload gained a continuation per write slice (the mailbox of "Streamed request bodies", below, removed that); after an early response head the write in flight stays in the race until the upload stops (at most the write gap).
- Reading a stream in small pulls costs a pull per read from the socket; a caller that wants throughput should pull large pieces or use `request`.
- Each retry of a connect resolves the name again; a lookup cut by the deadline still holds a thread of libuv's pool and can delay exit, as before.

## TLS: the design and its review

Designed on 2026-10-30 (`DESIGN.md`, "TLS").  Before anything was built, the design was reviewed by a fresh Claude and by Gemini through `agy-readonly`, each looking for ways it breaks and for better alternatives (`logs/2026-10-30/tls/reviews/`, the prompt in `design-prompt.txt`).  Both endorsed the choice of a thin binding to the toolchain's static OpenSSL over memory BIOs, and both rejected the first draft's split of the work.  What changed:

- **No TLS task, no Lean mutex.**  The draft made a TLS receive a task of its own that ran its TCP receives through its own continuations, with a per-connection mutex to keep ciphertext in order and a cancelled flag to stop a registration after a cancel.  The Claude review showed that the mutex deadlocks against the event loop's lock: `send` takes the loop's (recursive) lock, the loop thread holds it while it runs callbacks, and a continuation chained with `sync := true` (the shell's habit) runs inline there and would take the TLS mutex in the opposite order; `cancelRecv` resolves the dropped promise inline too, on the thread holding the TLS mutex.  Both reviews also found that a TCP receive that had completed when the cancel came would be lost or reordered.  Now the driver (`Live`) does the TLS work in its own steps, so the session is touched by one task at a time, and cancelling stays the TCP socket's `cancelRecv`.
- **A read takes every buffered record.**  Both reviews: `SSL_read` returns one record, so a response followed in the same TCP read by stray bytes or a `close_notify` would be finished as reusable while the rest sat in the read BIO, invisible to the idle check's `waitReadable`, and be read as the next response.  The read now loops to the size asked, and a connection whose session holds anything is never pooled.
- **The idle check does not read.**  The draft's refinement (read once, and stay clean if only a late session ticket arrived) could not tell a partial record from a consumed ticket (Gemini) and brought back the cancel race (Claude).  Any byte, or anything buffered, now makes a connection unclean.  (The design also said the client asks for no tickets; `SSL_OP_NO_TICKET` does that for TLS 1.2 only, as the implementation review pointed out, and TLS 1.3 servers send them anyway.)
- **The deadline is the deadline's timeout**, not a TLS time-out, during the handshake as elsewhere (Gemini: otherwise the planner could retry a call whose deadline had passed).  `tlsHandshakeTimeoutMs` must be positive.  The handshake waits for its last flight to be written.
- **OpenSSL's macros and inline functions** cannot be declared by hand: they are called through the `*_ctrl` functions with named constants the check compares, and `ERR_GET_REASON` is avoided by classifying truncation from what the transport fed.
- **Initialisation** without OpenSSL's exit handler and without its configuration file; the thread's error queue cleared before every operation.
- **Trust store directories** are used only after every bundle file is missing, and only if they hold OpenSSL's hashed names: a directory without them loads nothing and would turn a missing trust store into a verification failure.  Empty `SSL_CERT_FILE` and `SSL_CERT_DIR` are ignored; set but naming nothing usable is an error.
- **Host names**: an empty name would make `SSL_set1_host` turn the check off (Gemini).  It cannot arise: `Std.Http`'s URI parser refuses empty labels, so no name has a trailing dot or is empty (the unit tests check the parser does), and the C side refuses an empty name anyway.  A name that ends in a number is refused; partial wildcards must be refused explicitly (`X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS`); no fallback to the common name.
- **`close_notify` only from idle connections**, sent after the pool's mutex is released: after an exchange the shell cannot tell a clean end from a write still in flight.
- **Platforms**: only Linux toolchains pin OpenSSL 3.6.0 (Claude, from the toolchain's packaging scripts); the design now says so, and that the interpreter has no OpenSSL.

Rejected or corrected:

- Gemini's proposal of a Lean mutex around each OpenSSL call and the send of its output is the draft's design, which the deadlock rules out.
- Gemini said `BIO_set_mem_eof_return` expands to `BIO_ctrl(b, BIO_C_SET_FD, ...)`; OpenSSL's `bio.h` says `BIO_C_SET_BUF_MEM_EOF_RETURN` (130).
- A process-wide cache of contexts keyed by the trust settings (Claude) is not built: a context per client, made once.
- Reusing the upstream `session.cpp` with a Lean side of our own (Claude, as an alternative): its pending-write queue has no use with memory BIOs and its Lean side serialises reads and writes, which the exchange core's full duplex (an early response during an upload) rules out; `native/tls.c` keeps primitives of the same shape, so that it can give way to the upstream ones once a toolchain ships them.

## TLS: the implementation, and what was measured

Built on 2026-10-30 (`logs/2026-10-30/tls/`; each run directory holds the commit it ran and the diff on top of it).  `native/tls.c` is compiled by Lake with the toolchain's clang and Lean's own flags and linked into every executable that imports the library (Lake adds a library's `moreLinkObjs` to them); the executables carry OpenSSL 3.6.0 (`strings` finds its version, `nm` its symbols; `build/build5.txt`).  That compiler has only the freestanding headers in C mode, with no `stdio.h`, `string.h` or `pthread.h`, which the first build found: the C file uses a spin lock on a C11 atomic flag, its own string helpers, and declares `calloc` and `free` itself.

What the runs showed, on the shared build host (load average up to about 500 on 128 CPUs during the later runs):

- **Everything else unchanged.**  From a clean build on v4.34.1 (`ci/run1.txt`) and on v4.35.0 (`ci/v435.txt`, its own remote directory): no warning, the four axiom scripts at `propext`, `Classical.choice` and `Quot.sound`, and every pure suite passes; the planner's proofs needed no change for the new cause. The check itself, against OpenSSL 3.6.0's generated headers and the laptop's 3.5.5 ones, ran on the laptop (`abi/ci-tls-abi.txt`): the build container has no network to fetch the headers, and its stage says so and skips; GitHub CI requires it.
- **A public site.**  From the build container with network (`LEAN_HTTP_NETWORK=pasta`, `smoke/public.txt`): `example.com`, `www.google.com` and `github.com` over TLS 1.3, each with its second call on the same connection, verified against the trust store the client found in the image; a TLS 1.2 site of badssl.com works, and badssl.com's self-signed, expired, wrong-host, untrusted-root and TLS 1.1 servers are each refused with the matching reason, not retried, nothing sent.
- **The test server's Nagle algorithm**, not the client, made a first GET take about 80 ms: with `TCP_NODELAY` on the server's sockets it takes about 12 ms (`net/nagle.txt`, five pairs).  The server writes its TLS 1.3 session tickets before the response, and the small response then waited for the client's delayed ACK.  `tls.py` now sets it.
- **Exit times under load.**  In a run of the controls at load average about 480, four processes took 1.5 to 2.5 s to exit after `main`.  Rerun interleaved with plain HTTP scenarios at the same load (`net/exit-recheck.txt`), both kinds scattered (up to 163 ms plain, 746 ms TLS, most under 60 ms), and in the full runs their distributions matched; nothing points at TLS, but that rests on a small sample at an extreme load.

The implementation review (a fresh Claude and Gemini, `reviews/impl-*`; a second Gemini pass over the fixes, `reviews/impl2-*`, which found the test server's first version of the one-read route could uncork before `close_notify` was queued under load, now fixed) found no memory-safety, reference-counting or concurrency defect in the binding, and these, all fixed: a TCP receive whose ciphertext made no plaintext started the next one without telling the exchange core the time, so a peer keeping the socket busy with partial records could hold off the read gap and the deadline (Gemini); a handshake timer firing a millisecond early turned the call's deadline into a retryable TLS time-out (Gemini); after the end of input a session asking for more would have kept waiting; host names such as `0x7f000001` passed as names; an `SSL_CERT_DIR` that cannot be read, or of separators only, was accepted; `-Werror` in the package build would break users' builds on a future compiler's new warning; and test gaps: nothing exercised the pooling gate, SNI, TLS 1.2, the name-check flags, `SSL_CERT_DIR` or streaming over TLS.  Gemini's report also describes functions that do not exist (`Live.retire`, `RawRead`); those parts were set aside.

Left open:

- An ALPN protocol other than `http/1.1` is refused, but no test makes a server choose one: a conforming server chooses only among what the client offers.
- A TLS 1.3 key update that asks for one in return (`KeyUpdate` with `update_requested`) is handled by OpenSSL inside the read, and its reply sent; no test makes a server send one (Python's `ssl` cannot).
- Bytes that make no plaintext do not reset the read gap, so a response trickling in slower than about one TLS record per `readGapMs` times out over TLS where over TCP it would not.
- Each client makes its own context, so a client per request parses the trust store each time; a process-wide cache is not built.
- No session resumption, no client certificates; trust stores only from files (`SSL_CERT_DIR` split on colons, as on Unix); built and tested on Linux only.

## Streamed request bodies

Built on 2026-10-30 (`logs/2026-10-30/upload/`, with `COMMAND` listing every run).  `Client.upload` and `Client.withUpload` take a `Request RequestBody`, bytes or `RequestBody.stream (size : Option Nat) (next : Async (Option ByteArray))`, a body the caller makes while it is sent; `DESIGN.md` ("Streamed request bodies") describes the design.

Decisions, and why:

- **A pulled source.**  The calling task already races every operation it waits for against the core's deadlines, so a call of `next` is one more such operation, at most one in flight; backpressure is the pull itself, and an exchange that ends early simply stops pulling.  A pushed writer (`BodyWriter → Async Unit`) needs a task of its own for the producer, a rendezvous with the exchange, and a way to stop that task, which `Async` cannot cancel.
- **The core holds one segment.**  The request bytes the core writes are the head, then each framed chunk in turn, `segStart` bytes into the request; written counts stay counts of the whole request, so every statement about writes, reuse and delivery reads as before for a whole request, with `request.size` become `known`, the bytes known so far.
- **No pull before a write, and before the head is out.**  The pull's condition names both (`sentAny`, `headBytes ≤ written`), not only the head: a pull is then never in the run of an exchange that fails "not sent", so the planner's retry of such a failure, which it allows whatever the method, sends a stream nobody has read (`observed_notSent_unpulled`).  The client starts the planner with `RequestBody.kind`, `BodyKind.stream` for a stream, so its theorem that nothing unreplayable is retried after a byte may have gone out covers streams (`streamed_no_resend`); `redispatch?` takes the hop's replayability (`redispatch?_unreplayable`).
- **The declared size is checked on both sides of the wire.**  A chunk that would exceed it is refused before any of it is written, and an end short of it fails the exchange.  After the whole size, the producer is asked once more whether it has ended, as Go's transport reads a request body to its end after writing `ContentLength` bytes.  That answer races the response: the first version judged the request complete only at the producer's end, and the reuse scenario failed whenever the server's answer, which it can send as soon as the declared bytes arrive, came first (the response looked early, and the connection was dropped).  `Exchange.wireDone` now counts a declared size given in full as complete on the wire.  The cost is that a producer which would give more is not heard if the response ends the exchange first; asking before writing the last chunk would make the check certain, at the price of holding back the end of the request until the producer has ended, and of a pull in flight with bytes unwritten, which the invariants rule out today.
- **Each operation reports once, to a mailbox.**  `awaitFirst` adds a continuation to every task of each race, holding the race's promise and so its winner's result.  A read stays pending through an upload and loses a race per write and per pull, so a streamed upload kept every chunk until the response came: a 256 MiB upload in 16 KiB chunks peaked at about 365 MB of resident memory.  Resolving each race with the winner's index instead (an intermediate version) left the continuations themselves: 29 to 31 MB in 16 KiB chunks but 207 to 210 MB in 1 KiB chunks, against 550 to 570 MB with the result.  With the mailbox (each operation chains one continuation when it starts, which files its completion and rings a bell that each wait replaces), 17 to 30 MB and 27 to 30 MB (`rss/run.sh`, `rss/out.txt`, two runs per cell, cells alternating).  The mailbox also orders completions that arrive together: a write before a pull before a read, so that a response is never judged early only because the shell heard of the read before the write that preceded it.  An earlier set of these measurements built the working tree in every variant (`scripts/remote.sh` copies it over the directory) and is kept under `rss/discarded/` with a note.
- **A producer's error or a broken size fails the exchange** with `Cause.requestBody`, never retried; while an abandoned body is drained nobody waits for an error, so the exchange finishes with the connection dropped instead (`step_broken`).

What is proved.  The exchange core's theorems keep their statements for whole requests; the ones that named `request.size` now name `known` (`Inv`, `Reusable`, `step_deliverHead`'s `early`, `step_writes`' slice, which starts at `written - segStart`), `Reusable` asks for `wireDone`, `Fixed` and `Agree` carry the new fields, and the checker's model (`Obs`) builds the request bytes from the chunks the producer returned with framing of its own, so `observed_write` says every write is the next slice of those bytes, and `observed_finish_reusable` that a reusable finish wrote all of them.  `Observed.begin` starts from `Obs.init`.  New: `step_pulls`, `PullRun.inFlight`, `observed_pull`, `observed_notSent_unpulled`, `Observed.framed`, `observed_length_written`, `observed_finish_body`, `accept_length`, `step_broken` (exchange core), and `ReachableWith.bodyKind`, `streamed_no_resend`, `streamed_follow_empty`, `streamed_no_follow_same_method`, `redispatch?_unreplayable` (planner and re-dispatch).  The head `prepareStream` encodes is checked by the unit tests, not proved: no theorem looks inside `Std.Http`'s encoder.

What the runs showed, on the shared build host (load average about 180 to 340 on 128 CPUs throughout):

- **The full CI script** on the merged tree (`ci/final/`, commit ba7b2a7, v4.34.1): a build without warnings; the four axiom scripts at `propext`, `Classical.choice` and `Quot.sound` (50 exchange theorems, 34 of the planner and streamed bodies); unit (179 checks), the core's 65 traces, 50,000 random runs and 14 bounded searches to depth 10 (three of them streamed uploads), the pool's and the planner's suites, codec-diff with its control, the fuzzing seeds, the README's eight Lean blocks and the examples (the upload example's two bodies arrive as framed: 98,890 bytes chunked, 24 with a `Content-Length`).  The real-socket suite: 521 checks pass, the known limitation of `dns-timeout` as before, and one failure, `stream-drain` (a body's last 7 bytes coming 30 ms after the first 3 must arrive within the 100 ms drain limit); 829 calls replay through the planner.  An earlier run on the merge commit (`ci/merge/console.txt`, load about 330) failed eight timing checks of older scenarios instead, all of which passed in the final run; `ab/` runs the failing scenarios on main and on this branch in alternation (three rounds each, cells alternating, at load about 100 to 140: every check passes on both).
- **The upload scenarios** (83 checks, plus `tls-upload`) pass in every run: a body of known size and one of unknown size, every byte in order and the connection reused after each, over TCP and over TLS; 256 MiB in 16 KiB chunks at a peak resident memory of 21 to 23 MB in the final run, against 562 MB for the same body as bytes; an early 413 delivered within the write gap (5 ms in the final run), with two 64 KiB chunks of the 32 MB body produced; producers that raise or break their declared size; a PUT whose server closes mid-upload, not retried (the byte-array control is sent three times); a 307 delivered, not followed (the control follows it with the body); a refused connect retried with nothing pulled; a pooled connection closing as a streamed PUT is sent, and a 408 of an idle connection, neither sent again (the controls are); a producer that never answers, the call ending at its 500 ms deadline and the process exiting promptly.
- **Positive controls** (`controls/`): each of seven planted defects in the core is caught by the traces and by the random runs, and all but two by the exploration too: a pull with a write in flight, a pull before the head is out, a declared size exceeded by a byte, an end short of the size accepted, chunks without their CRLF, the request counted complete from the start, a refused chunk or a producer's failure ignored.  An eighth, dropping only the condition that everything known was written before a pull, changes nothing: the write is scheduled first in the same step, so a write is in flight whenever bytes are unwritten.  Likewise the conditions on the head alone (`sentAny`, `headBytes ≤ written`) are implied, for a request `prepareStream` made, by the others; they stay because the theorems are about any prepared request.
- **Lean v4.35.0** (`v435/`): the same tree, with one change: v4.35.0 parses `given` as a clause of a def's contract (`NOTES.md`, the compatibility work), so `net-client`'s producer names its counter `produced`.  Build without warnings, the axiom scripts, the pure suites and the examples all pass, and so do the upload scenarios and `tls-upload` (83 checks).

Two independent reviews of the core and the theorem statements (a fresh Claude and Gemini through `agy-readonly`; `reviews/`) agreed that no pull can come before a write or the head, that nothing beyond a declared size goes out, that the chunked framing is right and that retries, re-dispatches and redirects never send a partly read stream.  Their findings, and what came of them:

- The continuations a pending read gathers per race still grow with the number of chunks once each race keeps only an index (Claude): measured, and replaced by the mailbox (above).
- The checker's property "a broken streamed body fails the exchange" demanded a failure where the core, draining an abandoned body, finishes instead (both): the property now accepts that, and a trace covers it.
- No theorem said that a broken body ends the exchange; the checker alone did (both): `step_broken` and `accept_length`.
- The README overclaimed the final check of a declared size (both): it now says that the answer is not waited for once the response has ended the call.
- `observed_length_written` suggested more about the encoded head than it states (Claude): its docstring now says what it does.
- No chunk size in the tests had a hex letter (Claude): sizes 26 (`1a`) and 4000 (`fa0`) now.
- No real-socket test re-dispatched a streamed exchange (Claude): `upload-redispatch`, with byte-array controls.
- Gemini also reported `Framed` as "nearly a tautology" of the model: it is a property of the model, which is separate from the core (it frames with `Codec.encodeChunk`, not the core's `Codec.chunkFrame`), and what binds the core is `observed_write`; the missing piece it pointed at was the broken-body theorem, now proved.  Some of its file references named functions that do not exist (`Call.Machine.step`, `freshAfterPooledLoss`); its conclusions about them were checked against the actual code.

Left open:

- A producer still running when its exchange ends is left to finish, and what it returns is dropped: Lean cannot cancel an `Async` computation.  It cannot keep the process from exiting (`upload-exit`).
- With `withUpload`, a callback that does not read the response body stalls the rest of an upload the server answered early, within the call's deadline.
- No `Expect: 100-continue`: a server that refuses a large upload hears all of it unless it answers early and closes.
- No timer covers the producer but the call's deadline.
